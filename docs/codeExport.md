# Exporting a simulation as standalone code

The "Export simulation code" button in the title bar (next to "Export results as CSV") turns the currently loaded model into a self-contained `.cpp`/`.py` file, or a real compiled `.fmu`, that reproduces a full simulation run with no runtime dependency on the Konjugate GUI. Both formats read the same flattened `nodes`/`edges` document the engine itself validates and runs against (`executionProjectDocument()` + `stripEdgeGroups()`) and share the same graph-building/expression-transpiling code (`src/codeExport.mjs`, reused by `src/fmiCodeGen.mjs`). The standalone-program format is generated entirely in JS with no engine involvement; the FMU format does need the engine binary, but only to compile the generated C++ into a real shared library (its generic `buildSharedLibrary` command — see "Exporting as an FMU" below) — there is still no engine-side knowledge of the model's own math, no "codegen mode" baked into the engine itself.

## What is reproduced

The generator targets exact numerical fidelity with the engine's own solver, for the method the active run configuration chooses: Explicit Euler node by node (the default), described first, or Runge–Kutta 4, Adaptive (Dormand–Prince 5(4)), Stiff (Rodas4) or BDF for the whole model, described after the list:

- **Fixed-step, multi-rate integration.** Each node advances at `globalTimeStep / substepsPerGlobalStep`. A binding into a *different* node's state always reads a frozen snapshot taken at the start of the current global step; a binding into the *same* node's own state (or any source-term binding) reads that node's live, substep-updated value.
- **Contribution order.** Contributions to the same state are summed in the same order the engine uses — a node's own source terms in their JSON order, then edges touching that node in document order — since floating-point addition is not associative.
- **Bidirectional edges** apply the same evaluated expression to both endpoints, negated on the other side.
- **Disabled nodes/edges** are excluded exactly as the engine excludes them.
- **Live parameters** (`mode: "live"`) are emitted as plain constants using their stored value — a runtime control-message override only matters for the interactive GUI, which the exported program has no equivalent of.
- **Ownership.** When the project names an owner, a copyright notice or a license (its `ownership` block, see [Project schema](projectSchema.md)), the generated `.cpp`/`.py` opens with comment lines giving them (`{year}` worked out at export), and an FMU's `modelDescription.xml` carries them as the `author`, `copyright` and `license` attributes FMI has for exactly these. Nothing is written for a project that names none, and line breaks in the text are replaced so a notice cannot end the comment it is in.
- **Scheduled parameters** (a shared parameter with a stored `schedule`, see [Project schema](projectSchema.md)) are emitted as one table per schedule and a `scheduleValue` (C++) / `schedule_value` (Python) lookup, read at the same instants the engine reads them (a derivative at its substep's start, an algebraic term at its algebraic instant), with the same linear or held interpolation and edge-holding. In an FMU, a scheduled parameter is computed the same way inside the FMU and is not exposed as an FMI variable.
- **Same-language inline providers** (C++ or Python relationship/source-term/computational-node providers) are embedded by pasting their raw source into the generated file, alongside a small vendored copy of the SDK the provider's own source already targets: the program SDK (`konjugate/sdk/v2/program.hpp`, `konjugate.v2`) for a program in the current format, or the older format's types (`ScalarPort`, `EvaluationContext`, `OutputCollector`, etc.). Provider instances are created once and persist for the whole run — not recreated per step — since a stateful provider (e.g. a PI controller's integral term) depends on that.

**Verlet** (a node's `numerics.integration: "verlet"`, see [Integrators, Verlet, node by node](proposals/integrators.md#verlet-node-by-node)) is written as the engine steps such a node: within each substep its first part moves half a step with its rates at the substep's start, its second part a whole step with its rates at the middle, and its first part the other half with its rates at the end, which are the next substep's rates at its start; a term written as a program is held from the substep's start. Each move sets the time its terms and schedules read. The same code goes into an FMU. A node whose rates do not split into the two parts is refused in the engine's words.

**Runge–Kutta 4** (the run configuration's `method: "rungeKutta4"`, see [Integrators](proposals/integrators.md)) steps the whole model at once, as the engine does. The C++ program contains the engine's own stepping code, `engine/include/konjugate/integrators/rungeKutta4.hpp`, pasted in byte for byte (`src/integratorSources.mjs` carries its text, and `tests/codeExport.test.mjs` fails if the copy differs from the header); the Python program contains a line-for-line port of it. At each of the method's four stages every node works out its rates from every node's stage values, its own and its neighbours' alike, and the method combines them state by state in the engine's order; `stepsPerGlobalStep` steps of the method make each global step. A node's substeps and integration do not apply, so a semi-implicit node exports. A term written as a program is evaluated once per global step, at its start, with the global step as its step size, and held through the stages, as the engine holds it. Values set from other states are worked out at each global step's end. In every parallelism mode the nodes' work is dispatched once per stage rather than once per step, and under MPI the ranks gather the stage's rates, each rank then combining the same stages.

**Adaptive** (`method: "dormandPrince54"`, or `"tsit5"` for Tsitouras's coefficients, whose `tsit5.hpp` is pasted in after `dormandPrince54.hpp` with a line-for-line Python port after Dormand–Prince's) is exported the same way, with the engine's `engine/include/konjugate/integrators/dormandPrince54.hpp` pasted in byte for byte and a line-for-line Python port: its error control with the run configuration's tolerances and each state's own absolute tolerance (`numerics.absoluteTolerance`), its error norm summed node by node in the engine's order, the controller's memory carried from one global step to the next, every step landing on the global step's end and on the times where a stored schedule's samples fall inside it, as the engine lands them; a term written as a program is evaluated at each global step's start and held. A run configuration that gives it `stepsPerGlobalStep` exports its fixed-step form, error control off.

**Switches** (event location, [Integrators](proposals/integrators.md#event-location-built-the-stage-after-adaptive)): under Runge–Kutta 4, Adaptive and Stiff, each comparison inside a `Which` condition of a Rate equation is written as a switching function, the term reads the condition from `switching.latches` instead of comparing, and the program locates each change with the engine's own `engine/include/konjugate/integrators/events.hpp` pasted in byte for byte (and its line-for-line Python port), retaking a step that crosses a switch to end on it, as the engine does. Under Euler, node by node, conditions are compared at each substep, as before. The C++ export reproduces the engine's arithmetic; the compiler may fuse a multiply and an add where the engine's build did not, or the reverse, so the exported program agrees with the engine to rounding, and an adaptive step decision a rounding apart can, rarely, give a different, equally valid step sequence within the tolerance.

**Stiff** (`method: "rodas4"`, or `"rodas5p"` for its fifth-order form, whose `rodas5p.hpp` is pasted in after `rodas4.hpp` with a line-for-line Python port after Rodas4's) is exported the same way, with the engine's `engine/include/konjugate/integrators/linearSolve.hpp` and `rodas4.hpp` pasted in byte for byte and a line-for-line Python port of both: the Jacobian's structure from the model's graph (the states each state's derivative reads, written into the program as `stageReads`), the Jacobian exactly from each equation's derivatives (written into the program as the engine works them out: `src/expressionDerivative.mjs` differentiates each equation by the engine's own rules, operation for operation, and the program adds each derivative into its entry in the engine's order; with the run's `jacobian: "finiteDifference"`, the coloured finite differences instead), df/dt where an equation reads the time or a scheduled parameter, Konjugate's own dense LU (and, above 200 integrated states, its sparse LU with the same minimum-degree ordering), the error control with the run's tolerances and each state's own absolute tolerance, and every step landing as Adaptive's do. The exact Jacobian is the engine's to the last bit wherever the rates are; a finite-difference Jacobian (`jacobian: "finiteDifference"`) divides a last-bit difference in a rate by a perturbation of about √ε of the state, so an exported expression that rounds differently from the engine's gives a Jacobian different in about its eighth digit: at fixed steps the exported program agrees with the engine to about 1e-12 (Python, which never fuses, to about 1e-10), and across a corner no step lands on (a rate that switches with a state) an error-controlled run may take different, equally valid steps, agreeing within the tolerance's reach.

**BDF** (`method: "bdf"`) is exported the same way, with `engine/include/konjugate/integrators/bdf.hpp` pasted in beside the stiff methods' shared `stiffSystem.hpp` and `linearSolve.hpp`, and their Python ports: its table of differences carried from one global step to the next, its Jacobian and factorisation kept from step to step, and its table started again at order 1 where the engine starts it (a schedule's corner, inside a step or at a global step, and a state that changed between global steps, as an Update does). Its Newton iteration and error control make the same kind of decision Stiff's do, so the exported program agrees with the engine as Stiff's does: to rounding when the step sequence is the same, within the tolerance's reach where a last-bit difference tips a decision.

### Programs in the current format

**Programs in the current format** ([Writing a program](programs.md)) are written as the engine calls them: the program SDK (`program.hpp`, or the `konjugate.v2` module) pasted in once, each program one `ProgramInstance` that keeps its memory as the engine does (whole 8-byte slots in C++, the SDK's own store in Python), started before the run from the initial states, its clock's first tick and its Update values set before the run's Updates are settled, as the engine starts a run. Under Euler node by node `advance()` follows every substep, reading the states it reached; under Runge–Kutta 4 the global step is taken as its internal steps one at a time with `advance()` between them, and under Adaptive, Stiff and BDF it is called from the methods' own `accepted` hook (in the pasted headers and their Python ports), never for a step rejected or taken again to land on an event; a program's `OutOfDomain`, or a value that is not a finite number, rejects the step as the engine's `StageRejected` does. At each global step's end the clocks that land there tick, and a node's program sets its Update states, reading the states as the engine's update phase reads them (Rate states at the step's end, Update states at its start). `tests/engine/programExportFidelity.mjs` checks the digital PID example, a latching thermostat and a two-way relationship that remembers, under every method, against the engine: to every digit each export writes, and under Stiff and BDF within the tolerance's reach, as for any model.

## What is not supported

Export is blocked outright, with an error naming the offending node or edge, when:

- **A provider is implemented in the other language.** A model with a C++ provider cannot be exported to Python, and vice versa — provider source is never auto-translated.
- **A provider is an installed plugin reference** (`implementation.kind: "plugin"`), which has no embeddable source to paste in.
- **A computational-node provider is exported to C++.** C++ computational-node execution does not exist in the engine either, so there is no C++ shape to generate.
- **A node is a program of its own in the older program format under a whole-model method** (Runge–Kutta 4, Adaptive, Stiff or BDF). The engine steps such a node on its own when it is not pure; code export does not write that yet. A node's program in the current format takes part in the stages, as in the engine.
- **A program in the current format does something export does not write yet** ([Writing a program](programs.md#in-the-web-edition-and-in-exports)): its own `jacobian()` under Stiff or BDF, a clock on a value term (an Update), several outputs on a relationship, or a parallel mode other than serial when it remembers something or the method is a whole-model one; each is refused by name.
- **A node is integrated semi-implicitly** (`numerics.integration: "semiImplicit"`) under Euler, node by node; this applies to FMU export too.
- **The run configuration names a method this version does not know**, refused by name.
- **An FMU is exported from a run configuration that chooses Runge–Kutta 4 or Adaptive.** FMI export steps with Euler node by node or, under Stiff, with Rodas4 or BDF (below); the other whole-model methods inside `fmi2DoStep`/`fmi3DoStep` are a later stage of [Integrators](proposals/integrators.md).

Beyond blocking, a few things are deliberately out of scope for the generated program itself:

- **No restart/checkpoint support.** Export reproduces one fresh run from the model's initial values; a computational-node provider's `checkpoint()`/`restore()` methods are never called.
- **`Sqrt`/`Log`/`Power` domain divergence.** `std::sqrt`/`std::log`/`std::pow` return `NaN` on an out-of-domain input (e.g. a negative square root); Python's `math.sqrt`/`math.log`/`math.pow` raise a `ValueError` in the same situation instead. Both fail loudly rather than silently continuing with bad data, so this is a documented divergence, not a wrong-physics bug.
- **The Python export has no thread-based parallel option.** `openmp`/`stdThread` are rejected outright for a Python export: Python's GIL means threads would not actually run this CPU-bound loop in parallel, so offering them would be misleading rather than merely unoptimized. `mpi` *is* available for Python (via `mpi4py`) — see below.

## Parallelism

The export dialog's "Execution" choice picks how the generated program dispatches its per-global-step node work. Every mode runs the *exact same math* (verified — see below) — each node's computation only ever reads the frozen `snapshot` (for other nodes) or its own live local state, and only ever writes its own states back into the global state list, so nothing about correctness depends on execution order or concurrency. C++ offers all four modes; Python offers only `serial` and `mpi` (see above for why threading is excluded).

- **Serial** (default): a plain sequential loop over the nodes. Simplest, no build flags needed.
- **OpenMP**: `#pragma omp parallel for` over the same nodes. Mirrors the real engine's own thread-pool backend (see [Parallel execution](parallelExecution.md)) — genuinely just a flag on top of the serial structure. Needs `-fopenmp` (Linux/MSVC `/openmp`); **macOS's shipped `clang++` has no bundled OpenMP** — `brew install libomp` once, then compile with `-Xpreprocessor -fopenmp -I"$(brew --prefix libomp)/include" -L"$(brew --prefix libomp)/lib" -lomp` (libomp is keg-only, so the `-I`/`-L` paths must be given explicitly — a bare `-lomp` will fail to link).
- **`std::thread`**: the same parallel dispatch, spawning and joining one `std::thread` per node every global step instead of using an OpenMP pragma. No special compiler flag beyond `-pthread` (harmless/unneeded on Windows), at the cost of a fresh thread spawn every step rather than a reused worker pool — the simplest correct option when a project can't or doesn't want to depend on OpenMP.
- **MPI**: genuinely new territory, not mirroring existing engine code — the real engine's own "partitioned" backend explicitly stops at one process ("not multi-process, distributed or multi-machine execution yet," per [Parallel execution](parallelExecution.md)). Nodes are split into **contiguous blocks by node count** across ranks (computed at runtime from `MPI_Comm_size`, since the rank count is an `mpirun -n` choice) — a simple, unweighted partition, unlike the engine's own METIS/communication-aware partitioner, so a lopsided model could load-balance poorly. Each rank integrates only its own block, then one `MPI_Allgatherv(MPI_IN_PLACE, ...)` per step reconciles the full state vector across ranks (contiguous-by-node-order blocks give every rank a contiguous global-state-index range, which is what makes a single collective call sufficient). Only rank 0 writes the output CSV. Needs an MPI implementation (OpenMPI, MPICH, …); build with `mpic++` and run with `mpirun -n <ranks>`, exactly like any other compiled program. The **Python** `mpi` export is the same algorithm via `mpi4py` (`pip install mpi4py`, needing the same system MPI install) — `comm.allgather()` on each rank's own contiguous state slice, concatenated in rank order, stands in for `MPI_Allgatherv` (mpi4py's fast buffer-based API would need NumPy arrays, which the Python export otherwise has no reason to depend on).

## Exporting as an FMU

Choosing "FMU (FMI 2.0 Co-Simulation)" (the default) or "FMU (FMI 3.0 Co-Simulation)" as the export dialog's Format produces a real, ready-to-use `.fmu` — not source the user has to compile themselves — that drops straight into any FMI 2.0 or FMI 3.0 Co-Simulation host (Simulink, Dymola, OpenModelica, GT-Suite, …). It is always C++ (an FMU is a compiled binary by definition — the Format choice hides the Python option) and always sequential (the Execution row is hidden too: `fmi2DoStep`/`fmi3DoStep` runs a plain per-node loop, matching the C++ export's `serial` mode — no OpenMP/`std::thread`/MPI option for FMUs in this version). Both versions are made from the same generated model, with the same variables, value references, methods and refusals, so an FMI 3.0 FMU gives the FMI 2.0 one's numbers bit for bit; what differs is the FMI layer (below). Everything this section says of FMI 2.0's functions holds for their FMI 3.0 counterparts (`fmi2SetReal` ↔ `fmi3SetFloat64`, `fmi2Get/SetFMUstate` ↔ `fmi3Get/SetFMUState`, and so on).

**FMI 3.0** ([FMI 3.0.2](https://fmi-standard.org/docs/3.0.2/)). `modelDescription.xml` has `fmiVersion="3.0"` and an `instantiationToken` (section 2.4.1) made like the FMI 2.0 guid, as a hash of the model identifier and the generated source; the FMI 3.0 source differs from the FMI 2.0 one by the constants appended to it (below), so the two exports of a model never share an identity, which installs and "Merge platform FMUs…" rely on. The variables are typed `<Float64>` elements (section 2.4.7) with the FMI 2.0 export's names, value references, causality, variability, `initial` and `start`; FMI 3.0 asks for exactly one independent variable (section 2.4.7.4), so `time` is added, with the value reference after the model's last one, and reads the current time. Units are declared: a `<Unit>` needs only its name, its `<BaseUnit>` being optional (section 2.4.3), so each unit string of the model is declared as written in `<UnitDefinitions>` and referred to by its variables. `<ModelStructure>` lists every output as an `<Output>`; the outputs have `initial="exact"`, so none is an `<InitialUnknown>` (section 2.4.8: those are the outputs with `initial` approx or calculated). `<CoSimulation>` states `fixedInternalStepSize` (the global step, of which a communication step must be a whole number), and declares no Event Mode, no early return and no intermediate update (`hasEventMode`, `mightReturnEarlyFromDoStep`, `canReturnEarlyAfterIntermediateUpdate`, `providesIntermediateUpdate` all false): `fmi3DoStep` always takes the whole step (section 4.2.1), answering `eventHandlingNeeded`, `terminateSimulation` and `earlyReturn` false and `lastSuccessfulTime` the step's end, or refuses it with `fmi3Error`. Every refusal (another model's instantiation token, a step that is not a whole number of global steps, setting `time` or an output, a function of a capability the FMU does not declare) is reported through the host's logger in the `logStatusError` category (section 2.4.5) with what was wrong. The binary goes under FMI 3.0's platform tuple (`binaries/aarch64-darwin/`, `x86_64-linux/`, `x86_64-windows/`, …; section 2.5.1.4). The FMU state (section 2.2.7.4) also holds the time, so `time` reads back as it was; it is serialized as that time followed by the model's captured values. Every function of the FMI 3.0 API is exported, those of undeclared capabilities refusing, since a host may bind them all by name when it loads the binary (FMPy does).

**Model Exchange is deliberately not offered, only Co-Simulation.** Model Exchange would hand the integrator to the host tool, which would pick its own (likely adaptive, non-Euler) solver — breaking the exact numerical-fidelity guarantee this whole feature is built on. Co-Simulation keeps Konjugate's own solver (Euler node by node by default, or Stiff, below) fully in control: the host just calls `fmi2DoStep(t, communicationStepSize, ...)` at whatever cadence it likes, and internally that steps Konjugate's own `globalTimeStep` however many whole ticks `communicationStepSize` covers (an integer-multiple requirement, same shape as the schema's existing `outputInterval`/`globalTimeStep` rule — a non-multiple step size is rejected with `fmi2Error`).

**Every parameter gets *real* fidelity here, unlike the plain export.** A standalone program has no runtime control stream at all, so the plain export bakes every parameter — live or constant — to a literal. An FMI host's `fmi2SetReal` calls (between `fmi2DoStep`s, or during initialization) are exactly that control stream: a `mode: "live"` parameter becomes a genuine FMI `causality="input"`/`variability="continuous"` variable, and a constant parameter becomes `causality="parameter"`/`variability="tunable"` — still defaulting to its stored value, so a host that never touches it reproduces today's constant behavior exactly, but a host that wants to sweep or tune it can. States are exposed as `causality="output"` variables. `fmi2GetReal` answers for any of these (reading back a state, or reading back whatever was last set on a parameter/input) — not just states.

**Variable names.** Each state is an output named by its node and its own name (`Tank.Pressure`), and each parameter is named by its symbol (`k`). FMI requires every name to be unique, so when two parameters share a symbol (a spring's `mass` and a damper's `mass`, each a parameter of its own relationship) those two are named by their relationship or node as well (`Spring force.mass`, `Damper force.mass`), and a name still used twice (two nodes of the same name) has its value reference after it (`Tank.Pressure [3]`). The generated C++ never names a variable, so this changes `modelDescription.xml` alone. The example FMUs of the [FMI compatibility page](../examples/fmi/README.md) show these names, with reference results.

**Under Stiff** (the run configuration's `method: "rodas4"`, `"rodas5p"` or `"bdf"`), each global step inside `fmi2DoStep`/`fmi3DoStep` is taken as the engine takes it: the engine's `stiffSystem.hpp`, `linearSolve.hpp` and `rodas4.hpp` (and `rodas5p.hpp`) or `bdf.hpp` pasted in, every node evaluated at each stage, the exact Jacobian, the error control with the run's tolerances, switches located, and the Updates set at the step's end, as the plain C++ export writes them. The solver's memory between steps (Rodas4's controller, BDF's table of differences, the conditions' latches) lives in the FMU instance; a host that sets an input between steps starts BDF's table again, as the engine does when a live parameter changes. `tests/engine/fmiExportFidelity.mjs` runs the fidelity fixture under both through FMPy against the engine (Rodas4 to about 1e-12, the FMU's step times being summed as the host steps; BDF to about 1e-15). Such an FMU does not offer rollback: the solver's memory is not in the state it captures.

**Rollback (`fmi2Get/SetFMUstate`, FMI 3.0's `fmi3Get/SetFMUState`) is supported when the model has no embedded C++ provider in the older program format.** Such a provider can carry arbitrary internal state across `evaluate()` calls with no generic way to serialize it, so a model using one still declines rollback (`canGetAndSetFMUstate="false"`, FMI 3.0 `canGetAndSetFMUState="false"`); a program in the current format keeps its state in declared memory, which the FMU state carries word by word beside the states and parameters, so a run restored from it continues to the bit (the FMU fidelity check restores the digital PID example mid-run). Such programs are written into the FMU as code export writes them under Euler, node by node ([Programs in the current format](#programs-in-the-current-format)): started when the FMU is instantiated, and again from the initial states if the host sets a parameter before the first step, since `initialize()` reads its constants; an FMU under Stiff does not take such programs yet, and refuses them by name — but a plain equation-based model supports it fully, including `fmi2Serialize`/`DeSerializeFMUstate` for saving a snapshot to bytes (e.g. for a host's own restart/DOE workflow).

**How it's actually built** (`src/fmiCodeGen.mjs` + `src/fmiExport.mjs`): the model's C++ source becomes a class implementing `konjugate::sdk::v1::SimulationModel` (`engine/include/konjugate/simulationModel.hpp`) instead of the plain export's `main()` loop — same per-node Euler/snapshot bodies, same provider-embedding rules (a Python provider blocks FMU export exactly like it blocks a cross-language plain export). A providerless model additionally overrides `SimulationModel`'s `supportsStateCapture()`/`captureState()`/`restoreState()` (the state vector plus every parameter member, in value-reference order) — a model with a provider leaves these at the base class's "unsupported" default. That source, plus `engine/src/fmiGlue.cpp` (the FMI 2.0 C API implemented over `SimulationModel` — `fmi2Instantiate`, `fmi2SetReal`/`fmi2GetReal`, `fmi2DoStep`, `fmi2Get/SetFMUstate`, etc.) or `engine/src/fmi3Glue.cpp` (FMI 3.0's, over the same interface; the FMI 3.0 source has its instantiation token, the value reference of `time` and the number of outputs appended as constants the glue reads, since `buildSharedLibrary` compiles exactly two files), are compiled together into a shared library by the engine binary's `buildSharedLibrary` command — a small, FMI-agnostic native-build capability (`engine/include/cppToolchain.hpp`/`engine/src/cppToolchain.cpp`, extracted from the exact compiler-discovery logic `buildCppProvider()` already used for inline providers, so this reuses real, already-hardened per-platform/per-compiler logic rather than re-deriving it). The result is zipped together with a generated `modelDescription.xml` (`fflate`'s `zipSync`, the same library already used for `.kja`/`.kjp` packages) into the `.fmu`.

**Each export only ever contains one platform's binary** (whichever OS Konjugate is running on when you export) — Konjugate never cross-compiles. To ship one `.fmu` that works everywhere, export the same project separately on each target platform, then combine those single-platform files with "Merge platform FMUs…" in the same export dialog (`src/fmiExport.mjs`'s `mergeFmuPackages`): pure zip surgery, no compiler involved, that unions each file's `binaries/<platform-dir>/` entry into one archive around a shared `modelDescription.xml`. This only works because the `.fmu`'s `guid` is *deterministic* — a hash of the model identifier and the generated C++ source, not a random UUID — so two exports of the identical project on different machines land on the same guid, which is exactly what lets the merge step confirm the files it's combining are really the same model before trusting their binaries together; exports of two different models (or the same model edited in between) get different guids and are refused with a clear error rather than silently merged.

**Scope for this version**: an FMI 2.0 export declares no units (a validator (FMPy) rejects a `unit=` that `<UnitDefinitions>` does not declare, and FMI 2.0 exports are kept exactly as they were); an FMI 3.0 export declares each unit by its name (above), without the SI decomposition (`<BaseUnit>`) Konjugate's free-form unit strings do not give. Model Exchange stays out of scope for *export* permanently, for the fidelity reason above; so do FMI 3.0's Scheduled Execution, Event Mode, early return, clocks and arrays.

**Verifying fidelity, two ways.** `npm run test:fmiExportFidelity` (`tests/engine/fmiExportFidelity.mjs`) builds a real `.fmu` from a fixture (`tests/engine/fixtures/fmuFidelityFixture.mjs`, shared with the check below) with a live parameter, stored parameter schedules, a tunable constant parameter, a cross-node edge, a bidirectional edge and a multi-substep node, then simulates it with [FMPy](https://github.com/CATIA-Systems/FMPy) (`pip install fmpy`) — an independent, standard-compliant FMI simulator, not just this project's own driver. It compares every state against the real engine's own run at every sampled time, exercises rollback via FMPy's low-level `FMU2Slave` API (capture, step further, restore, confirm an exact match — plus a serialize/deserialize byte round-trip), and confirms the tunable constant parameter is genuinely tunable by re-running the real engine with a different value for it and checking the FMU matches *that* run once the same value is set via `fmi2SetReal`. Skipped (not a failure) when FMPy isn't importable.

`npm run test:fmi3ExportFidelity` (`tests/engine/fmi3ExportFidelity.mjs`, a release check beside the FMI 2.0 one) exports the three example models of the [FMI compatibility page](../examples/fmi/README.md), the fixture, and the fixture under Rodas4, Rodas5P and BDF, both as FMI 2.0 and as FMI 3.0, and has FMPy validate every FMI 3.0 FMU and simulate both: every output at every communication point of the FMI 3.0 FMU must equal the FMI 2.0 FMU's bit for bit, and the engine's run bit for bit for the examples (and for one with a tunable parameter set through `fmi3SetFloat64`), to within 1e-15 for the fixture (whose scheduled and algebraic states the FMI 2.0 export, and so the FMI 3.0 one, gives with a last-bit difference at a few points) and to the FMI 2.0 check's bound under Stiff. Through FMPy's `FMU3Slave` it takes an FMU state mid-run, serializes and deserializes it, checks the outputs and `time` come back exactly and that the run continued from it repeats the original to the bit, and checks a step that is not a whole number of global steps is refused with the reason logged.

`npm run test:fmiRoundTrip` (`tests/engine/fmiRoundTrip.mjs`) checks the same fixture without any third-party FMI tool at all: it extracts the built FMU's own compiled shared library and drives it through the real FMI 2.0 C API via a new, narrow engine capability — `konjugateEngine runFmu <sharedLibraryPath> --state-count N --configuration run.json --output result.csv [--verify-rollback]` (`engine/src/fmiImport.cpp` — the complementary half of `fmiGlue.cpp`: that file answers FMI2 calls, this one places them) — which loads the library via `dlopen`/`LoadLibrary` (mirroring `providerRuntime.cpp`'s `InProcessProviderBackend` exactly) and resolves the FMI2 function pointers directly, no XML parsing needed on either side since the state count and value-reference order are already known by construction. `--verify-rollback` exercises `fmi2Get/SetFMUstate` entirely on the engine side (capture mid-run, step further, restore, compare) and skips cleanly, rather than failing, when the model declines rollback. This needs nothing beyond a C++ compiler (the same requirement building the FMU already has), so unlike the FMPy check it has no optional-dependency skip logic — it always runs. The honest tradeoff: it can't catch a spec misunderstanding shared between Konjugate's own exporter and this same dlopen-based driver, since they're not independent of each other the way FMPy is — that's specifically what the FMPy check is for. This predates and is independent of general FMI import (below): it only ever loads a shared library Konjugate's own exporter just built, and shares only the underlying dlopen/FMI2-driving pattern (`engine/include/konjugate/fmiDynamicLoad.hpp`) with it.

## Importing an FMU

The mirror direction: a node's `implementation` can reference an *installed* FMU (FMI 2.0 or 3.0 Co-Simulation, third-party or Konjugate-exported) instead of authored source — `kind: "fmi"`, see [Project schema](projectSchema.md) for the exact shape and [Interaction providers](interactionProviders.md) for the underlying computational-node-provider mechanism it resolves into. In brief:

- **Add** an FMU to a model with the Add menu's **FMU…** (a file picked), by dropping a `.fmu` on the canvas (the node lands where it is dropped), from the FMUs already in the library listed under FMU…, or with **Add to model** on its page in Extensions › FMUs: each places a new node built from the FMU (below), selected with its card open, ready to run. A new FMU is installed on the way (`packageAddFmu` in `src/main.mjs`), with no review to confirm, since choosing the file is the choice; one whose binaries cannot run on this computer is refused in words before anything is installed, and one already in the library (the same guid, which for Konjugate's own exports is a hash of the model) is used as it is. Extensions › FMUs › Install… installs one without placing it, and says so by the FMU's name. Every installed FMU is identified by its own `modelDescription.xml` guid (FMI 2.0) or `instantiationToken` (FMI 3.0) and stored under `userData/packages/fmus/<id>/<version>/`; its page in Extensions says what it is (FMI version, generation tool, description, how many outputs, parameters and inputs, which binary runs here) in place of the permissions an add-on asks for. The web edition keeps FMU… in the Add menu, and it and a dropped `.fmu` say that FMUs run in the desktop app, with where to get it.
- **Use** it in a node from the node editor's Program, choosing "Installed FMU": the node is built from the FMU, a state per output (named, with its unit and start value, set by the FMU) and every input and parameter listed at the FMU's own start value, so it runs with no wiring; each input or parameter can be given a value of its own, shared as a project parameter, or bound to a state (the project JSON's `fmuId`, `fmuVersion`, `bindings`, `outputs`). Under the FMU's name the editor says which binary runs here, which parameters are fixed when the run starts, which ports are converted and how, and which variables are not wired, and About this FMU says what the FMU says of itself (description, author, generation tool, binaries, step, default experiment, whether it can save its state); the install dialog says which binary this computer will run, or why none can.
- **Which binary runs** (`src/fmiBinary.mjs`): FMI 2.0 names a binary's directory by operating system and bitness (`binaries/darwin64`, `linux64`, `win64`, `win32`), FMI 3.0 by a platform tuple, architecture then system (`binaries/aarch64-darwin`, `x86_64-darwin`, `x86_64-linux`, `aarch64-linux`, `x86_64-windows`, `x86-windows`). An FMU is looked for under its own standard's name first and then under the other's, and a binary is taken only when its own header (Mach-O, ELF or PE) says it is built for this machine's processor. The other standard's name is accepted because FMI 2.0's names predate Apple Silicon: the FMI 2.0 Reference FMUs, for one, carry their Apple Silicon binary only as `aarch64-darwin`, and a `darwin64` binary may be built for Intel only. When none fits, the error names this machine (`aarch64-darwin`, say) and what each binary found is built for.
- **Resolution** (`src/fmiResolver.mjs`) turns that reference into an ordinary `kind: "cpp"` computational-node-provider implementation before the engine ever sees it — the engine itself has no FMI-specific knowledge, exactly as it has none of plugin-specific knowledge once `kind: "plugin"` is resolved. The generated source is only the FMU's variable table, handed to one driver written once in `engine/include/konjugate/fmiImportedNode.hpp`, which loads the chosen binary and runs it through the real FMI 2.0 or 3.0 C API, in the in-process computational-node-provider path (`engine/src/providerInProcessNodeShim.cpp`) — no worker-process fallback exists for a `cpp` node provider, so a run involving one automatically uses the in-process provider execution mode.
- **Co-Simulation only.** An FMU is run in Co-Simulation: it integrates its own equations within each step. An FMU that offers only Model Exchange is refused when installed, saying so, since running it would need Konjugate to integrate the FMU's equations itself; an FMU offering both is run in Co-Simulation. One communication step is one substep of the node: `fmi2DoStep`/`fmi3DoStep` from the substep's start over its length.
- **As the standard orders it.** The FMU is instantiated with a logger and its resources directory — FMI 2.0 a `file:` URI, FMI 3.0 an absolute path ending in a separator, or none when the FMU has no resources — and initialized at the run's first step, when its start time and the node's input values are known: every input and parameter is set inside initialization mode, the one place a fixed parameter may be set. From then on each input is set before every step, a tunable parameter only when its value has changed, and a fixed parameter never again: if what a fixed parameter is bound to changes during the run, the run stops and says so, naming the parameter, rather than letting the FMU go on with the old value unnoticed.
- **Types.** Real and Float64 variables pass through unchanged and Float32 as the nearest single-precision number; Integer, Int8 to UInt64 and Enumeration variables take the nearest whole number when set (refused, naming the variable and its type's range, when outside it) and are read as numbers; a Boolean is set true for anything other than 0 and read as 1 or 0. String, Binary and Clock variables and arrays are not wired: the FMU keeps its own values for them, and the node editor lists them. Every output must appear in `outputs`. An input or parameter left unbound keeps the FMU's own start value (a Boolean's `true`/`false` as 1/0), and one given a value in the file (`kind: "value"`) is set to it in initialization mode and never again; `npm run test:fmiStartValues` (`tests/engine/fmiStartValues.mjs`) checks with every Reference FMU of both FMI versions that leaving them to the FMU equals binding them to their start values bit for bit, and that the cases' values given in the file equal FMPy's runs bit for bit.
- **Events and the end of a simulation.** In Co-Simulation an FMU handles its own events inside each step (a bouncing ball's bounce, a time event) — Konjugate does not ask for event mode or early return. An FMU that asks to end the simulation (FMI 3.0's `terminateSimulation`; FMI 2.0's `fmi2Discard` with `fmi2Terminated`) is terminated there, says so on the engine's log, and its outputs keep their last values for the rest of the run, since one node cannot end the whole model's run.
- **An FMU's errors in plain words.** A call the FMU refuses stops the run with the FMU's name, the call, what it was doing and when, and whatever the FMU said through its logger: "The FMU 'Dahlquist' refused fmi3SetFloat64 (setting 'k') at t = 0: …". The app shows why a run stopped under the status chip, until it is closed or the next run starts (`src/runFailure.mjs`): it names the node running the FMU, says the call in plain words ("refused the value given to Enumeration_input", "refused its step"), quotes the FMU, and gives the value the refused variable started from, or every parameter's when a step was refused, pointing at any left at 0; **Open the node** opens it. Every other run failure is shown there too, with a hint for a value that became infinite or not a number.
- **An FMU output is a value, not a rate** — so the resolver marks every generated `outputs[]` entry `setsValue: true` (see [Project schema](projectSchema.md) and [Interaction providers](interactionProviders.md)'s `addGradient` section), the engine's real DAE-style algebraic-state mechanism: the FMU's reported value is written directly into the target state every substep, with zero approximation error and no dependency on any particular solver's arithmetic. An earlier version of this resolver instead contributed `(fmuValue - stateBeforeThisSubstep) / stepSize` — exact only because Explicit Euler's specific single-stage arithmetic happens to cancel that back to `fmuValue`, the same Euler-specific trick `setsValue` itself replaced elsewhere — before being migrated to `setsValue`. See `src/fmiResolver.mjs`'s file header for the full history.
- **Verifying fidelity**: `npm run test:fmiImportFidelity` round-trips through Konjugate's own exporter (build → install → import → compare against the real engine's own run of the un-exported model). `npm run test:fmi3ImportFidelity` does the same against a hand-authored real FMI 3.0 shared library (`tests/engine/fixtures/fmi3DecayFixture.cpp`), standing in for a third-party FMU, and against Konjugate's own FMI 3.0 export of a decay model (equal to the engine's run of the model, bit for bit). Both then import the [FMI Reference FMUs](https://github.com/modelica/Reference-FMUs) 0.0.42 of their FMI version — BouncingBall, Dahlquist, VanDerPol, Stair, Resource and Feedthrough — and compare every output at every communication point, bit for bit, with what [FMPy](https://github.com/CATIA-Systems/FMPy) 0.3.21 computes for the same FMU (`tests/engine/fixtures/referenceFmus/`: the cases, FMPy's results and the script that wrote them). The release zip is downloaded once and checked against its SHA-256 (or read from `KONJUGATE_REFERENCE_FMUS_ZIP`), not kept in the repository.

## Run configuration

`globalTimeStep` and `outputInterval` are baked in from the model's active run configuration. `targetTime` is a transient launch parameter, not part of the project schema, so the generated program exposes it (and the output CSV path) as a command-line flag with a default taken from whatever the "Run" dialog's target time was set to at export time:

```
./exported --target-time 10 --output results.csv
python3 exported.py --target-time 10 --output results.csv
```

The output CSV uses the same `time (s)`, `NodeName — StateName (unit)` header convention as Konjugate's own "Export results as CSV" button. In the Python program the header's non-ASCII characters (that dash, and any in a node's or a state's name) are written as `\uXXXX` escapes, so the source line is plain ASCII and the CSV it writes is the same: Python 3.9, still the system Python on macOS, refuses a source line of several thousand bytes with a non-ASCII character in it, and the header is one line naming every state.

## Verifying fidelity against the real engine

`tests/codeExport.test.mjs` only checks the generated source's shape (structural fragments, brace balance) — it can't compile or run C++/Python, so it can't confirm the numbers are actually right. That confirmation is `npm run test:codeExportFidelity` (`tests/engine/codeExportFidelity.mjs`): it builds a fixture exercising cross-node snapshot reads, stored parameter schedules (held and linear, one linked twice), a bidirectional edge, a multi-substep node, `Add`/`Multiply`/`Power`/`Sqrt`/`Abs`, and a live parameter, runs it through the real `konjugateEngine` binary, then separately generates, compiles and runs the plain Python export plus every C++ parallelism variant (serial, openmp, stdThread — mpi too when `mpic++`/`mpirun` are found on `PATH`, skipped with a console note otherwise), and asserts every state from every variant matches the real engine's own result at every sampled time to within `1e-6`. The Python `mpi` variant is checked the same way when both `mpirun` and an importable `mpi4py` are available, skipped otherwise. It needs a C++ compiler (`CXX` env var, default `c++`) and `python3` (`PYTHON` env var) in addition to the built engine binary, so — unlike `npm run test:engine` — it is not wired into the automatic CI test chain and must be run explicitly.
