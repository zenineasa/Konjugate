# Project document schema, version 1

The decoded `.kjt` payload is UTF-8 JSON with these top-level fields:

- `format`: literal `konjugate`
- `version`: integer `1`
- `copyright`: legacy optional attribution string. Konjugate used to write the same notice into every project it saved, which was never a claim a person made, so that string is not read as one; any other value is read as the copyright notice when there is no `ownership`, and a save writes only `ownership`
- `metadata.units`: unit-system identifier
- `nodes`: array of node records
- `edges`: array of relationship records
- `subsystems`: array of authoring-hierarchy records grouping nodes into navigable containers, each an instance of a component definition -- see [Subsystems](subsystems.md)
- `subsystemDefinitions`: array of component definitions the subsystems are instances of -- see below and [Subsystems](subsystems.md#components)
- `component`: present only in a component (a subsystem saved as a file of its own) -- see below
- `resultComponents`: present only in a project saved with its results: the components each result ran with -- see [Embedded binary result storage](resultFileFormat.md#components-a-result-ran-with)
- `edgeGroups`: array of shared-relationship records that expand into a mesh of edges across a live member-node set -- see [Edge groups](edgeGroups.md)
- `sharedParameters`: optional array of project-level parameters that relationship and source-term parameters link to -- see below
- `ownership`: optional object naming who made the project, its copyright notice, license and contact, and when it was first and last saved -- see below
- `addonData`: optional object of data add-ons keep with the project, keyed by add-on id -- see below
- `tuningSetup`: optional object holding the Parameter tuning card's setup, so a tuning can be run again after the model changes -- see below
- `scenarios`: optional array of the scenarios tried in a live twin's sandbox -- see below
- `twin`: optional object holding the twin's setup, made in the twin's own window -- see below

`ownership` (optional top-level object) is a notice for whoever receives the file, not an enforcement: anyone with the file can change or remove it, and encrypting the file is what keeps a model private. Every field is optional and the object is left out when empty: `owner` (a person or organisation), `copyright` (the notice text; a `{year}` token is replaced with the year of the save when the project is saved, so a file never holds the token), `license`, `contact` (an email or web address), `confidential`, `derivedFrom` (the work this one comes from and its license, so attribution survives remixing), `revision` (a string the user sets, never changed automatically), `title`, `description` (of the project as a whole), and `publicNotice`. `license` is `{ id }` with an SPDX identifier (`MIT`, `Apache-2.0`, `MPL-2.0`, `CC-BY-4.0`, `CC-BY-SA-4.0`, `CC0-1.0`, `0BSD`) or Konjugate's own `all-rights-reserved`, or `{ id: "custom", text, url }` with the terms in the user's words, an address, or both. `confidential` (default `false`) is a flag for Konjugate's own behaviour: it asks before the model is described to a hosted AI assistant, and it does not restrict the file. `publicNotice` is short text (at most 300 characters) the owner chose to show without the password: when the project is saved encrypted, Konjugate also writes it into the container header (see [KJT container format](kjtFormat.md)), which is the only part of the block outside the encrypted payload, and it is never written to an unencrypted file, whose header is readable anyway. Konjugate also keeps three fields itself, which the user cannot edit: `firstSavedAt` (the computer's clock at the project's first save, written once and kept by every later save and copy), `lastSavedAt` (the clock at every save), both ISO 8601 in UTC to the second, and `savedWith` (the Konjugate version). The times come from the clock and are not verified. Konjugate never fills the user-written fields from the operating system account, the machine name or any signed-in service. Like `addonData` the canvas keeps the block beside the model, writes it when the project is saved and reads it when the project is opened, and it never reaches the engine, validation, the AI assistant, copy and paste, or undo, so the engine ignores it and a project carrying it runs from the command line as any other; a save from the command line (`--output-kjt`) leaves it as it was except for `lastSavedAt`, `firstSavedAt` (if it had none) and `savedWith`. A value that cannot be used is dropped when the project is opened. Code export and FMU export write the owner, copyright and license into what they produce (see [Code export](codeExport.md)), and a copy saved with "Strip ownership details" carries none of it. The design is in [Model ownership and license metadata](proposals/modelOwnership.md).

`addonData` (optional top-level object) holds what add-ons keep with a project, one entry per add-on id: a launcher with the `project.data` permission writes its entry when it opens a model in the canvas, and reads it back to restore its window, and a result visualizer with it writes its own data whenever it changes and reads it back when it opens (see [Add-on development](addonDevelopment.md)). Konjugate does not interpret an entry. It is not part of the model: the canvas keeps it beside the model, writes it when the project is saved and reads it when the project is opened, and it never reaches the engine, validation, copy and paste, or undo. The engine ignores it, so a project carrying it runs from the command line as any other. An entry written by Konjugate's launcher host is `{ version: 1, addonVersion, savedAt, window, inputs }`: `window` is the launcher window's own state, and `inputs` the files its model was built from (`role`, `name`, `text`, `encoding`, `sha256`, `bytes`, and for a fetched file its `url` and `retrievedAt`), so the session reopens without choosing or fetching anything again. A file's path on the computer that chose it is never written. An entry written for a result visualizer is `{ version: 1, addonVersion, savedAt, data }`, `data` being whatever JSON the visualizer gave.

`tuningSetup` (optional top-level object) is what the Parameter tuning card was last run with: `{ version: 1, goal, backend, maxSimulations, maxMinutes, csvFileName, objective }`. `goal` is `"data"` (fit measured data), `"objective"` or `"replay"` (replay a data log, or run it as a live twin); `backend` is the optimiser's id; `maxSimulations` and `maxMinutes` are the limits (`maxMinutes` is left out when there is none); `csvFileName` is the name of the measured file used, never its contents, so the card can say which file to choose again; `objective`, present for the `"objective"` goal only, is `{ expression, direction, targetTime, timeStep, constraints, program }` (each constraint `{ expression, latex, relation, limit }`, or `{ report, relation, limit }` for a number the objective program reports) with `direction` `"minimise"` or `"maximise"` and the expression written in the names the card lists (see [Parameter tuning with a custom objective](proposals/parameterTuningObjectives.md)). It is not part of the model: like `addonData` the canvas keeps it beside the model, writes it when the project is saved and reads it when the project is opened, and it never reaches the engine, validation, copy and paste, or undo, so the engine ignores it and a project carrying it runs from the command line as any other. A running tuning writes it when it starts, which counts as unsaved work until the project is saved. A value that cannot be used is dropped when the project is opened. For the `"replay"` goal it carries `replay: { logFileName, timeStep, anchor, mapping, tolerances, live }`: the log's name (never its contents), the step and whether measured states start at their first reading, `mapping` as `[{ signal, role, target }]` with `role` `"input"` or `"output"` and `target` the shared parameter's or state's id (or null for a signal left out), `tolerances` as `{ signal: tolerance }`, and `logger`, for another logger's file, as how it is read (`{ delimiter, decimal, missing, time: { columns, format, zone }, signals: [{ column, name, role, unit, scale, offset, values }] }`, see [Connecting a data source](connectingADataSource.md#reading-another-loggers-file)). A file written before the live twin moved to its own window may also hold `corrections` and `live` here, the card's live twin settings; they are read and ignored, and no longer written (the twin's settings are in `twin.live`). When the same log is chosen again, signals are matched by name as always, and what is kept here fills in what the person had changed. See [Connecting a data source](connectingADataSource.md).

`twin` (optional top-level object) is the twin's setup, made in its own window ([The twin's control room](proposals/controlRoom.md)): `{ source, mapping, live }`. `source` is where the readings come from, `{ kind: "file", fileName }` (the name only, never the contents or the path), `{ kind: "mqtt", url }`, `{ kind: "opcua", url, security }` or `{ kind: "push" }`. `mapping` is one entry for each signal the source offered, `{ source, name, role, target, unit, conversion }`: `source` is what the source calls it (a column, a topic, a tag's node id, a pushed signal), `name` the identifier the twin uses for it, `role` `"input"` or `"output"` (null for a signal not used), `target` `{ kind: "parameter" | "state", id }` (a shared parameter for an input, a state for a measured signal), `unit` the source's, and `conversion` `{ scale, offset }` taking the source's unit to the model's (value × scale + offset), or null. `live` is the twin's settings, the engineer's to change: `{ window, stride, horizon, speed, alert, timeStep, corrections, members, untracked, drift }`, times in seconds; `alert` the drift warning in the first measured signal's unit a move (0 for none); `corrections` `{ name: { gain } | { estimate: true, noise } }` what a move does with each measured signal, by the twin's name for it (a signal left out resets to its reading); `members` the estimator's ensemble; `untracked` the ids of tunable parameters the estimator leaves alone (every other tunable parameter is tracked when a signal is estimated); `drift` `{ stateId: how far it may drift in an hour }`; `inputs` `{ name: { forecast, span, damping, period, plan, state } }` how each input is carried past now in the forecast, by the twin's name for it: `forecast` one of `hold`, `mean`, `trend`, `trend2`, `day`, `automatic`, `plan` and `model`, the spans in seconds and each optional (an input left out is held); `plan` `{ repeat: "daily" | "weekly", timeZone, points: [{ day, at, value }] }`, `at` seconds into the day, `day` 0 (Monday) to 6 when weekly, the values in the model's unit; `state` the id of the state the input follows past now with `model` (one in the input's unit, or, with no unit to check, a controller's output or any state for an input with no unit, that no signal measures and no input sets; another stops the twin when it starts, saying why); a `plan` or `state` is kept with any choice, used only with its own; `inputUncertainty` `false` to leave the inputs' uncertainty out of the estimator's band. `layout` is the control room's: `{ order, wide, pinned, hidden, bounds }`, the tiles by measured signal's name, in order, drawn twice as wide, pinned first and hidden, and the window's place, `{ x, y, width, height, maximized }`, kept by the project window when the twin's window closes and used when it opens again (clamped onto a screen that is there). `record` is the last run's events, `{ startedAt, events: [{ at, kind, text, detail }] }`, newest first, at most 500, `kind` being `info`, `good`, `lean` or `bad`. When the source's signals are found again, the mapping comes back for those it names. Like `tuningSetup` it sits beside the model and never reaches the engine, validation or undo; a change made in the twin's window counts as unsaved work in the project. A value that cannot be used is dropped when the project is opened (src/twinSetup.mjs).

`scenarios` (optional top-level array) holds what was tried in a live twin's sandbox ([Digital twin connections](proposals/digitalTwinConnections.md), "Detaching to try things"). Each is `{ id, name, createdAt, logFileName, startedAt, ranFor, settings: { window, stride, horizon }, tried: [{ time, signal, value }], modelFingerprint }`: when it began (seconds into the log), how far it ran ahead, each input set and when, and a fingerprint of the model it was tried with, so the card can say when the model has changed since. Results are not kept; they are computed again. A sandbox in which something was tried is added as a draft when the person goes back to live, with no question asked, which counts as unsaved work; the card's list renames and deletes them. At most 50 are kept, the oldest going first, and the person is told which. Like `tuningSetup` it sits beside the model and never reaches the engine, validation or undo.

Every persistent model entity uses a project-scoped positive integer `id` from 1 through `Number.MAX_SAFE_INTEGER` (`9,007,199,254,740,991`). IDs are unique across nodes, states, source terms, edges, parameters, run configurations, subsystems, subsystem definitions and edge groups in one project. Ids inside a subsystem definition's `document` are in that document's own space, not the project's. User-facing names are mutable and must never be references. Version 1 does not accept legacy UUID identifiers.

`sharedParameters` (optional top-level array) holds project-level parameters that any number of relationship or source-term parameters can link to. A shared parameter has `id`, `name`, `symbol`, `value`, optional `unit`, `mode` (`"constant"` or `"live"`) and, when live, optional `control` -- the same shapes as an edge parameter, including an optional `tuning` block that makes it a digital-twin fitting target. A relationship or source-term parameter opts in with `sharedParameterId`, referencing a shared parameter's `id`. A linked parameter still has its own `id`, `name` and `symbol` (the symbol is what its own equation refers to), but its value, mode and live-control range come from the shared definition: the engine ignores the linked parameter's own `value` and `mode`. Live-control commands and parameter interventions are addressed to the shared parameter's `id`, so one value or one schedule reaches every parameter linked to it -- for example the reserves leg and the matching liability leg of one lending facility, which must always move together. A shared parameter may carry `tuning` (fitting it is one optimization variable however many parameters link to it, and moves all of them together); the linked parameter itself may not (`sharedParameterTuningUnsupported`), since the shared definition owns the value. Validation also rejects a link to a missing shared parameter (`sharedParameterMissing`) and applies the same id, symbol, mode and bounds rules as for any other parameter. Shared parameter ids share the project-wide id space. Standalone code export and FMU export have no runtime notion of sharing and bake each link to the shared definition's value.

A shared parameter may carry a stored `schedule`, `{ "interpolation": "linear" | "hold", "samples": [[time, value], ...] }`: its value then follows the samples over simulation time instead of being a constant, in every run (the canvas, the engine CLI, headless launcher runs, and the code and FMU exports), from step 0 and through the settle before it. Times are simulation time in the model's own units, at least one sample, all finite, strictly increasing. `linear` interpolates between samples; `hold` keeps each sample's value until the next sample's time (a staircase, for a series of per-period rates whose totals must be kept). Before the first sample and after the last, the nearest sample's value holds. The parameter's `value` is kept, and becomes the constant again if the schedule is removed (in the Parameters table, a shared parameter's ⏱ button gives it a schedule, typed or pasted as a time and a value per line with linear or hold interpolation; a scheduled parameter shows the schedule's summary in place of the value, which opens it for editing, with a button to remove it). A live shared parameter with a schedule follows it until a live value is set, and a recorded intervention (a scenario fork's step, ramp, pulse or path) takes over from the schedule when it begins, exactly as either takes over from a constant. The engine reads a scheduled parameter at the same instants as any time-varying input: every substep's start for a derivative, the algebraic instant for a `setsValue` term. A scheduled parameter cannot also be a fitting target (`parameterScheduleTuned`), and a malformed schedule is `parameterScheduleInvalid`. Code export emits each schedule once as a table with the same lookup; FMU export computes a scheduled parameter inside the FMU, so it is not an FMI variable.

Unlike an [edge group](edgeGroups.md), which shares one whole relationship definition across a mesh of edges, a shared parameter shares a single value across otherwise unrelated relationships and source terms.

A node contains `id`, `name`, optional `shortName` (the name it goes by in other nodes' equations, as y_A, when a person gives it one on its Details tab; derived from its name otherwise, and written only when set), optional `type`, optional `description` (free-form text documenting what the node represents; omitted when empty, and placing a library template copies the template's own description in), three-number `position`, `states`, `sourceTerms`, `numerics`, `appearance`, and optional `enabled`. It may also contain three-number `rotation` (Euler angles in radians, XYZ order) and `scale`, both purely cosmetic canvas placement -- neither affects simulation. A node's `appearance` may hold `parts`, an additive array of `{ prefix, mesh: { position, normal, index }, color }`: the shapes of bodies whose pose the node reports among its states (a robot's links, each with states `<prefix>X`, `<prefix>Y`, `<prefix>Z` and an orientation such as `<prefix>Qw` to `<prefix>Qz`), each mesh in metres in the frame of its body. The canvas edits them under Body parts on a node's Appearance tab (each part added or its mesh replaced from an STL or STEP file, in millimetres or metres, with its prefix and colour, and a note when the node has no states to place it) and hands them to result visualizers (Pose Visualizer draws each body with its part); it draws the node's own shape, not the parts, itself. Both are additive fields: omitted entirely when at their identity value (`[0,0,0]` for rotation, `[1,1,1]` for scale), and older readers that don't know about them can safely ignore them, per the additive-field rule above. State symbols are unique lower-camel-case identifiers within their node. A state may carry `tuning: { minimum, maximum }`, as a parameter does, to make its `initialValue` a fitting target (the ◎ beside the state in the node editor): a tuning finds it with the parameters, and a live twin's refit finds the state's value at the window's anchor. `minimum < maximum` and `initialValue` within them are validated (`stateTuningInvalid`); a measured state in a replay or calibration starts at its first reading instead, and is not fitted. Source terms identify their updated state by symbol in version 1. A state may carry `numerics.absoluteTolerance`, a finite number above 0 in the state's own unit, which Adaptive uses for that state in place of the run's absolute tolerance (`stateAbsoluteToleranceInvalid` otherwise); it is written only when set, and edited on the node's Numerics tab when the active run configuration chooses Adaptive. `numerics.substepsPerGlobalStep` is an integer from 1 through 10,000 and defaults to 1. `numerics.integration` is `explicit` (the default: every state is updated together from the substep's starting values), `semiImplicit`: the node's states are updated one after another in the order the node lists them, each from contributions evaluated with the states already updated before it, so a position listed after the speed that moves it uses the new speed (semi-implicit, or symplectic, Euler, which keeps an oscillation's energy bounded where explicit Euler lets it grow), or `verlet`, written only when chosen: Störmer–Verlet, second order and symplectic. Its states, in their listed order, fall in two parts, split at the first state whose rate reads one listed before it; each substep moves the first part half a step, the second a whole step from the first's new values, and the first the other half from the second's (a speed before its position gives velocity Verlet, a position before its speed position Verlet). Each rate's equations may read only states of the other part, so a rate reading its own state (damping, decay) is refused, naming the states (`nodeIntegrationInvalid`); a term written as a program is held, evaluated once at each substep's start, and other nodes are read from the step's snapshot, so between nodes it stays first order ([Integrators](proposals/integrators.md#verlet-node-by-node)). A node with a computational-node provider is integrated explicitly (`nodeIntegrationInvalid`). A node may also contain an `implementation` object, additive alongside `sourceTerms`, declaring a computational-node provider that owns the node's dynamics -- see below. A state may say its `kind`, and a node how its updates are worked out (`updates`, `updatesLimit`), as described next.

**Rates and updates.** Every state is either a **Rate** -- what reaches it is a rate of change, summed and integrated over the step, $\dot x_i = \sum_j f_{ij} + s_i$ -- or an **Update** -- what reaches it is its new value, summed and put in place at the end of the step, $x_i^{+} = \sum_j f_{ij} + s_i$. A state says which with `kind: "rate" | "update"` (`stateKindInvalid` otherwise). A state that says no kind is an Update when a `setsValue` source term, a computational-node provider's `setsValue` output or a relationship's several equations set it, and a Rate otherwise -- so a node placed or pasted from an older file keeps what its terms make it. Each global step, from $t$ to $t + h$, is worked out in three parts: every state is read at $t$; Rate states are integrated over the step (each node in its own substeps, a term reading its own node's Rate states as they advance and everything else, every Update included, as it was at $t$); then every Update is worked out from the Rate states as they are at $t + h$, the Update states as they were at $t$, and the time $t + h$. Every Update reads the same values, so the order they are worked out in never matters, and no graph shape is refused: an Update reading another reads it a step back, and an Update may read itself (a counter, `n = n + 1`). Nothing may add a rate to an Update state (`rateIntoUpdateState`) or set the value of a Rate state (`valueIntoRateState`). A node may instead ask for its Updates to **settle within the step**, `updates: "settle"` (absent or `"oncePerStep"` otherwise; `nodeUpdatesInvalid` for any other): its Updates then read each other as worked out in the same step, in dependency order, so a chain settles in one pass; a ring of them is swept, every sweep reading only the previous sweep's values, until no value changes by more than one part in $10^{12}$, or for at most `updatesLimit` sweeps (a positive whole number, default 1000; a ring spanning several nodes takes the largest of theirs), after which the run carries on with the last sweep's values. Validation warns of each such ring (`updatesRing`), naming its states, and a run in which one did not settle holds one finding for it in its result (`ringDidNotSettle`, among the run's numerical stability findings), at the first instant it did not, naming its states, the one still changing most and by how much, and how many steps it did not settle in. An Update worked out once per step starts at its initial value, as a Rate does. A settling node's Updates are also worked out at the run's start (from the initial states and the start time, so a stored initial value is a placeholder), when a run resumes from a checkpoint, and again before a step whenever a parameter has been set or scheduled since, as below. **A file whose states say no kind** -- every file written before Rates and Updates -- is read as it always ran: a state set by a `setsValue` source term or by a relationship's several equations is an Update, every other a Rate, and every node settles, which gives the numbers earlier versions gave (measured over every run of the bundled examples and both toolboxes' engine tests, all identical to the sample). The one exception is a node with substeps whose rates read its own Update: earlier versions worked that Update out again at each substep, and it now holds from the start of the step. Standalone code export writes a model that says its kinds when it means what a file that says none means -- every node holding an Update settling, no relationship's single equation setting a value, no Update reading itself -- and refuses any other, saying which; FMU export does not yet write one. In the canvas, a node's Equations tab shows each state as one line (its name, symbol, start value and unit, opening its fields when clicked) and its whole equation, $\frac{dx}{dt} =$ or $x =$, assembled from every part reaching it: the node's own part (its source terms on that state) typed straight into a field, every other part (a relationship's, written in this node's names: its own states bare and another node's with that node's short name, as $y_A$; a program's) a chip that opens what it belongs to, and "set by program" in place of the equation for a state the node's program sets. A file holding several source terms on one state shows them as one sum, made one term, their parameters with them, by the first edit; a part typed into a state that is an Update in a file that says no kinds sets its value, as the state's other parts do. States nothing changes fold into one line while they come together with the same start value and unit ("Roll, pitch, yaw · stay at 0 rad"). The parameters of a node's own parts are on its Parameters tab, by state. Clicking the equation's left-hand side offers both kinds as their equations to choose between; choosing one in a file that says no kind makes it say every state's kind, as the engine read it, with every node that holds an Update settling, as one undoable step, so nothing else changes. A disabled node's or relationship's own terms count in that, as they would once switched back on, and a node switched off shows its own parts in its states' equations, marked off. Content put into a model -- a node made or placed from the library, a pasted graph, a library assembly, a component -- says its kinds as the model does: where one says them and the other none, the one that says none is made to say them the same way, in the same undoable step as the content going in, so neither's numbers change (one state saying its kind anywhere is enough for the engine to read the whole file by the rules above). A node's Numerics tab holds its Updates setting and its limit on sweeps; its name, type, subsystem and description are on its Details tab. A source term's and a relationship's editors open on where the term lands: each state it reaches, its kind, and its equation with this term in it, which goes back to the state's node; a relationship's name, description and ends are on its Details tab, and its direction is the One way · Both ways switch at the top of its Equations tab, beside where it lands (the Details tab says which, and goes to it).

A node may also carry `subsystemId`, referencing an entry in the top-level `subsystems` array -- pure authoring hierarchy with no effect on simulation. Before validation and execution, the host strips `subsystems` and every node's `subsystemId`, so the engine always sees the same flat node-and-edge graph regardless of hierarchy. A `subsystems` entry is `{ id, name, parentSubsystemId, position, terminalPositions, definitionId, parameterValues, definitionKey }`, with `parentSubsystemId` null at the top level. `definitionId` names the entry of `subsystemDefinitions` the subsystem is an instance of; `parameterValues` (optional) lists the instance's exposed parameters that differ from the component's defaults, each `{ parameterKey, value }` or `{ parameterKey, sharedParameterId }` (bound to a shared parameter of the project), `parameterKey` being the exposed shared parameter's id in the definition's document (named `Key` so copying never renumbers it); a subsystem nested inside an instance has `definitionKey`, its id in the outer definition's document, and no `definitionId`. `terminalPositions` (optional, omitted when empty) is where the person has dragged the terminals drawn inside the subsystem, as a list of `{ edgeId, position }` entries, `position` three numbers in the canvas's coordinates; a crossing with no entry is laid out automatically. Only edges that cross the subsystem's boundary when the project is saved are written, and an entry that cannot be used (no positive integer `edgeId`, or not three numbers) is dropped when the project is opened. The entries name their edge in an `...Id` field so that copying renumbers them as it does any reference. A field a subsystem carries that this version does not know is kept and written back. Its boundary is not stored: the relationships crossing it are derived from the edges and every node's `subsystemId` when it is shown. A file written by an earlier version may also carry a `ports` array on each subsystem; it is read past, unchecked, and not written again. A `subsystemDefinitions` entry is `{ id, document, link? }`: `document` is a complete component document (a project with `format`, `version`, `nodes`, `edges`, `sharedParameters`, `edgeGroups`, its own `subsystems` and `subsystemDefinitions`, and a `component` block), sealed in its own id space; `link`, only for a linked component, is `{ kind: "file", fileName, path, relativePath, sha256, savedAt, encrypted? }` or `{ kind: "library", templateId, templateName, sha256, savedAt }`, plus `behind: { sha256, savedAt }` when a newer version was seen and the old one kept. Only the definitions the project's subsystems use are written. Every entity in the flat graph made from a definition (nodes, states, source terms, parameters, edges, edge groups, shared parameters, nested subsystems) carries `definitionKey`, its id in the definition's document, which keeps its project id when the definition is expanded again; a shared parameter made from a definition also carries `subsystemId`, the instance it belongs to, and `exposed: true` marks a component's exposed parameters. The host strips `subsystemDefinitions`, `component`, `definitionKey`, and shared parameters' `subsystemId` and `exposed` before validation and execution. A `component` block is `{ name, description?, ports }`, each port `{ key, stateId, name?, direction? }`: `key` a positive integer unique among the component's ports and never reused, `stateId` the state it offers, `direction` `in`, `out` or (the default, left out) `both`. See [Subsystems](subsystems.md) for the full record shape.

An edge contains `id`, `name`, optional `description` (free-form text documenting what the relationship represents; omitted when empty, and ignored by the engine), source and target node/state references, directionality, LaTeX equation, optional normalized `equationModel`, parameters, appearance, and optional `enabled`. Parameter symbols are unique lower-camel-case identifiers within their edge. Normalized equation bindings and outputs use numeric entity references.

A relationship may have several equations, each **setting** a state of one of its two nodes, in place of one equation adding a rate: `equationModel: { bindings, definitions, outputs }`. `bindings` are as for any equation (states of either endpoint, the edge's parameters, time). `definitions` is an optional ordered list of named intermediate quantities, `{ symbol, mathJson, latex? }`, each reading the bindings and the definitions before it. `outputs` lists the equations, `{ role, stateId, mathJson, latex?, setsValue: true }`, each naming a state of the source or target node and reading the bindings and definitions; every one sets its state's value (`relationshipOutputNotAlgebraic` otherwise), and a relationship sets each state once (`relationshipOutputDuplicate`). Such a relationship is directed and written as equations, not a program (`relationshipOutputsInvalid`). A state set this way is an Update (see Rates and updates above): it takes no rate (`rateIntoUpdateState`), and when several relationships or source terms set it, its value is the sum of what each gives, as currents add at a junction. They are worked out with every other Update, after each step; in a settling node (every node of a file that says no kind), in dependency order -- every equation setting a state before any equation reading it -- so a chain of them across many nodes settles within the step, and every node reads the values from the step's synchronization snapshot. Only the definitions an equation needs are worked out for it, and each once an instant however many of the relationship's equations need it (every state it reads is settled by the time the first of them is reached). A definition read only in a `Which` value, or in a condition after its first, is worked out only when that branch is reached, so a toolbox can put work that matters only some of the time (a contact that touches, a row of a solve that is active) behind a choice and pay for it only then; a long chain of definitions is worked out in order, never by recursing down it. Relationships whose equations set values in a ring are valid: once per step, the ring goes round once a step; settling, it is swept to its fixed point, or up to its limit. This is how a toolbox writes, for example, the articulated-body method of a robot: each joint one relationship between two solids, carrying the child's pose and velocity outward, the inertia it passes to its parent inward, and the child's acceleration outward again. In the canvas, a relationship's Implementation "Equations that set values" edits these: a row per intermediate quantity (its name and value) and per equation (the state it sets and its value), each added, removed, moved (the ↑ and ↓ buttons, or Alt with an arrow key) and checked on its own row, with the references a field may read inserted from chips. Switching a single equation to this keeps it as the first equation, now setting its state, and makes the relationship directed; switching back keeps the first equation, with the intermediate quantities it reads written into it. The canvas keeps the LaTeX of every item it writes, works out its MathJSON, and binds only the states, parameters and time the equations read; an item it was given with MathJSON is kept exactly as it was until the user types into it, and is shown as LaTeX written from that MathJSON when its own LaTeX does not read back. Standalone code export and FMU export do not write such models yet and say so.

Each entry in an edge's `parameters` array contains `id`, `name`, `symbol`, `value`, optional `unit`, and `mode` (`"constant"` or `"live"`, default `"constant"`). It may also carry `displaySymbol`, LaTeX for how the canvas writes it in equations (`\omega` for a parameter whose symbol is `angularVelocity`), written only when a person sets one and ignored by the engine, which reads `symbol`; a source term's parameter and a shared parameter may carry it the same way. What is typed with it is stored with `symbol`. Two further fields may accompany it:

- `control`: `{ minimum, maximum, step }`, present only when `mode` is `"live"`: the parameter's live range, shown in the editors as Live minimum, Live maximum and Live step. While a run is going the parameter can be set only within `[minimum, maximum]` (a value typed outside it is held to the nearest end, and the controls say so), and `step` is how far the slider and the − and + buttons move it. `minimum < maximum`, `step > 0`, and `value` must fall within `[minimum, maximum]`. A waveform around the parameter may swing beyond the range; the preview says when it does. (The key is called `control` for historical reasons and stays so that files keep opening.)
- `tuning`: `{ minimum, maximum }`, marking the parameter as a fitting target for the digital-twin parameter-tuning feature (see [Causal inference](causalInference.md) for the related, but distinct, structure-discovery feature). Presence of `tuning` is what makes a parameter tunable. `minimum < maximum` and `value` must fall within `[minimum, maximum]`; both are validated the same way `control`'s bounds are. Mutually exclusive with `mode: "live"` — a live parameter is adjusted interactively during a run and has no fixed baseline worth calibrating beforehand, so the authoring UI disables tuning while a parameter is live, and clears any existing `tuning` the moment `mode` becomes `"live"`.

`enabled` (boolean, default `true` when absent) marks a node or edge as disabled without removing it: unlike a UI delete, a disabled entity is written to the file and round-trips through save and load. The engine treats a disabled node or edge exactly as if it had been deleted — its states are not part of the state vector, and it contributes nothing — but its definition, bindings and equations are preserved and are not validated while disabled. An edge is inert if it is disabled itself, or if either endpoint node is disabled, even if the edge's own `enabled` is `true`; re-enabling the node alone is enough to restore that edge without needing to touch it directly.

For an executable relationship, `equationModel` is required and contains:

- `latex`: the editable presentation expression.
- `bindings`: integer-ID-backed state and parameter bindings with stable expression symbols, plus an optional time binding `{ kind: "time", symbol }` (symbol `t` by default) giving the simulation time in seconds: the substep's start time for an ordinary contribution, and for an algebraic (`setsValue`) term the instant of the states it is computed from (see below). Source terms accept the same time binding.
- `output`: the state receiving the expression's derivative contribution.
- `mathJson`: the executable expression tree. Version 1 supports numeric literals, bound symbols, `Add`, `Multiply`, `Negate`, `Divide`, `Power`, `Sqrt`, `Abs`, `Exp`, `Ln`, `Log`, `Sin`, `Cos`, `Tan`, `Arcsin`, `Arccos`, `Arctan`, `Arctan2` (two arguments, `y` then `x`: the angle of the point (x, y), from -π to π), `Tanh`, `Min`, `Max`, and `Which`. `Which` is a piecewise value (LaTeX `\begin{cases}`): `(condition, value)` pairs where the first true condition's value is used and only that value is evaluated. Its last condition must be `True` (`\text{otherwise}`). Conditions are `Less`, `LessEqual`, `Greater`, `GreaterEqual`, `Equal`, `NotEqual` (chained comparisons such as `0 < x < 1` require every adjacent pair to hold) combined with `And`, `Or` and `Not`, and are only valid as `Which` conditions, never as values. The canvas writes typed LaTeX in these terms: `\operatorname{atan2}(y, x)` and `\arctan(y, x)` as `Arctan2`, `\exp(x)` and `e^{x}` as `Exp`, `e` and `\pi` as numbers, a fraction of two numbers as `Divide`, `\sqrt[n]{x}` as a power and a subtraction as adding the negation; a number with more digits than a double holds is rounded to one, and an expression the parser folds to no number (a division by zero) is refused.

LaTeX is never executed directly. Multiple relationships targeting the same state contribute additively to its derivative.

Source terms use the same structure under `expressionModel`: integer-ID-backed local-state and parameter bindings, an output state, editable LaTeX, and executable MathJSON. A source term may contain its own `parameters` array using exactly the relationship parameter shape described above, including mutually exclusive live-control and tuning bounds. Parameter ownership is local to that source term; symbols need only be unique within it. Source terms and relationships targeting the same state are summed before each integration step.

A source term may additionally carry a top-level `setsValue` boolean (default `false`, absent for every existing project — a pure opt-in with no migration). It sits alongside `expressionModel`/`implementation` rather than inside either, so it survives switching a source term between Equation and a program. By default (`setsValue` absent or `false`) a source term's computed value is a *derivative* contribution, summed with every other contribution to its state and Euler-integrated, exactly as described above.

When `setsValue` is `true`, the state it targets is an **Update** (see Rates and updates above): its value is never integrated; the source term's expression (or, for a programmable source term, the value passed to its provider's `addGradient` call -- no SDK change, the same wire value is just reinterpreted) is its new value, worked out after each step, from the Rate states the step reached and the step's end time, a plain replacement never divided by the timestep. On a state whose `kind` is `update`, every source term sets its value whether or not it says `setsValue`. Every reader sees the same value during a step, the owning node and other nodes alike, which keeps a bidirectional edge that reads an Update conservative. Code export and FMU export of a file that says no kind work out such values as earlier versions did (an FMU settles at instantiation and after every parameter set until its first step). Because there is no derivative or timestep-dependent arithmetic anywhere in this computation, it composes with any solver, not just Explicit Euler (see [Interaction providers](interactionProviders.md), [the causal-inference input-replay proposal](proposals/causalInferenceInputReplay.md) and [Rates and updates](proposals/ratesAndUpdates.md)).

A `setsValue` source term's expression may reference other states, another Update among them (e.g. `y` set directly, `z` set from `y + 1`): once per step it reads them as they stood at the step's start; in a settling node, in dependency order, and a ring of them is swept as above. In a file that says no kind it may not reference its own state (`setsValueSelfReference`): an Update reading itself needs its `kind` said, so that it is read a step back. A state a `setsValue` source term sets takes no rate from another source term or an edge (`rateIntoUpdateState`); a computational-node provider's `setsValue` output must still be its state's only contributor (`setsValueNotSoleContributor`). A single-equation edge does not support `setsValue`: it adds a rate, unless its target state's `kind` is `update`, when it adds to its value. An edge with several equations (above) sets values instead.

An edge or source term may be programmable instead of an equation: it carries an `implementation` object (in place of `equationModel`/`expressionModel`) and its own top-level `expression`/`equation` field is left empty. `implementation` contains:

- `kind`: `cpp` or `python`.
- `providerApiVersion`: integer, currently `1`.
- `source`: the inline C++ or Python source text the user authored in the Provider Editor, or (for Python) a path to a standalone script.
- `bindings`: an array naming the provider's own port keys. A state binding is `{ key, kind: "state", nodeId, stateId }`; an edge or source term may also bind `{ key, kind: "parameter", parameterId }` to one of its own parameters. No `role` is needed on a binding (unlike `equationModel`/`expressionModel` bindings) — it just names which state or parameter feeds that port key, for either a source term's one local side or either of an edge's two endpoints.
- `output`: `{ key, stateId }` for a source term, or `{ key, role, stateId }` for an edge — the port key the provider's `addGradient()` call fills, mapped to the state receiving the contribution (`role` disambiguates a bidirectional edge's two endpoints, exactly as it does for `equationModel`'s output).

An installed provider may be referenced without embedding its source by using `kind: "plugin"`, `pluginId`, `pluginVersion` and `providerId` instead of `source`. Before validation and execution, the host resolves that reference to the installed plugin's declared `cpp` or `python` provider artifact. In the canvas, an edge's, a source term's or an edge group's Implementation "Installed plugin provider" writes this reference, choosing among the providers the installed plugins contribute, pinned to the installed version. The version is required so numerical behavior is not silently changed by an upgrade. Plugin packages and their installation rules are documented in [Plugin development](pluginDevelopment.md).

At run time, the engine compiles `source` (for `cpp`) into a native provider artifact and evaluates it out-of-process or in-process depending on the configured transport; see [Provider execution transports](providerExecution.md). The C++ authoring API lives in `engine/include/konjugate/relationshipProvider.hpp`.

A node may itself carry an `implementation` object: a computational-node provider that owns the node's own dynamics, evaluated once per substep alongside (or instead of) equation-based `sourceTerms`. `kind` is `python` or `cpp` -- a `cpp` computational-node provider only ever runs through the in-process execution transport (no worker-process fallback exists for it; see [Provider execution transports](providerExecution.md)). `providerApiVersion` and `source` follow the same shape as a source term's. `bindings` are `{ key, kind: "state", stateId }` entries, with an optional `nodeId` naming the state's node, or `{ key, kind: "parameter", sharedParameterId }` entries reading a project-level shared parameter: a node has no parameters of its own, so its provider reads shared ones (`providerBindingParameterNotShared` otherwise, `sharedParameterMissing` for one that does not exist). A shared parameter reaches the provider as it reaches any linked parameter, at the substep's start: its value, a live override, a recorded intervention or its stored schedule, and a fitting run's candidate when it is tuned. In the canvas, a node's Program (in the node editor) writes this: the language, the source (starting from a template naming every input and output, and opening in the code editor), each input's key and what it reads (this node's states, another node's, or a shared parameter), and each output's key, the state it changes and whether it sets that state's value. The canvas counts such a binding as a use of its shared parameter. A binding may read one of the node's own states, as the node advances (like a source term), or another node's state, from the step's synchronization snapshot (like an edge): the value at the start of the global step, whatever that node does during it. The other node must exist and be enabled (`providerBindingMissing`, `providerBindingStateDisabled`); it may be listed after this one. Unlike an edge or source term's single `output`, a node's `implementation` declares `outputs`: a non-empty array of `{ key, stateId, setsValue }` entries, each naming one of the node's own states and the named gradient key the provider's `add_gradient(key, value)` call contributes to it. `setsValue` (default `false`) is the exact per-output counterpart to a source term's own top-level `setsValue` described above -- when `true`, that output's target state becomes a genuine algebraic state (recomputed directly from the returned value every substep, never integrated) rather than a derivative contribution, and is subject to the same rules: sole-contributor (`setsValueNotSoleContributor`) and no self-reference through this provider's own `bindings` (`setsValueSelfReference`) -- checked against every binding, not per-output, since a node provider's bindings are shared across all of its outputs, not scoped to one. A node provider is evaluated once per substep, at its start time `t` with step `h`, and a `setsValue` output is the provider's value at `t + h`: a co-simulation step, advancing over `[t, t + h]` on inputs read at `t` and then reporting, as an imported FMU's `fmi2DoStep` does. The engine writes it after the substep's other contributions have been evaluated, so they read the value from before it, and the node records it beside its other states at `t + h`. Unlike a `setsValue` source term's, it is not recomputed after the step's last update or settled before the first step, since either would call the provider again for an interval it has already advanced over: the state's initial value is its value at the start. Unlike ordinary `setsValue` source terms, a node provider's own outputs are never checked against each other for a dependency cycle: one `evaluate()` call computes every declared output together from the same frozen pre-call state, so there is no sequential ordering between them to resolve. A computational-node provider is checkpointable; see the checkpoint and `startCheckpoint` paragraphs below.

A node's `implementation` may also use `kind: "fmi"` with `fmuId`, `fmuVersion`, `bindings` and `outputs` in place of `source` -- referencing an installed FMU (FMI 2.0 or 3.0 Co-Simulation) instead of authored code, structurally parallel to an edge's `kind: "plugin"` reference above. `fmuId` is the FMU's own identity string from `modelDescription.xml` -- its `guid` attribute for FMI 2.0, or its `instantiationToken` attribute for FMI 3.0 (the same role, renamed by the standard; Konjugate normalizes both under one `fmuId`/`guid` field everywhere outside the XML parser itself). `fmuVersion` is a Konjugate-assigned version string chosen at import time (FMI itself has no package-version concept). Before validation and execution, the host resolves this reference to a generated `cpp` computational-node-provider implementation that loads the installed FMU's platform binary and drives it through the real FMI C API -- the engine itself has no FMI-specific knowledge at all, exactly as it has no plugin-specific knowledge once `kind: "plugin"` is resolved. Every exposed input and parameter of the FMU is a binding key and every output an `outputs` key, each named from the FMU's variable name in lower camel case; String, Binary and Clock variables and arrays are not exposed. Which of the FMU's binaries runs, when its parameters and inputs are set (a fixed parameter only when the run starts), how integer, Boolean and enumeration variables are converted, and how an FMU's events, its request to end the simulation and its errors are handled are described in [Code export](codeExport.md#importing-an-fmu).

Every causality-`input`/`parameter` FMU variable becomes a bindable input port (a binding is required for every one -- an FMI implementation does not support the general "some inputs left unbound" allowance other node providers have, since there is no well-defined default to fall back to for an arbitrary vendor variable); every causality-`output` variable requires exactly one entry in `outputs`, targeting the state that variable's value should drive. Since an FMU's own variable names (e.g. `Decay.Level`) are not necessarily valid Konjugate binding keys (which must be lower camel case, like every other provider port key), each `bindings[]`/`outputs[]` key is the FMU variable's name run through a fixed sanitization rule -- split on any run of non-alphanumeric characters, lowercase the first piece, capitalize and concatenate the rest (`Decay.Level` -> `decayLevel`) -- rather than the raw name itself; resolution rejects the reference outright if two differently-named variables would sanitize to the same key. An FMU output's value is algebraic (e.g. a reported temperature), not a rate, so the resolver marks every generated `outputs[]` entry `setsValue: true` (the general node-provider mechanism described above) rather than folding it into Konjugate's derivative-based state update; the engine writes the FMU's reported value directly into the target state every substep, with zero approximation error and no dependency on any particular solver's arithmetic.

In the canvas, choosing Installed FMU as a node's Program, then the FMU, writes this: an input for each of the FMU's inputs and parameters and an output for each of its outputs, under the sanitized keys, which the user wires to what each reads and the state each sets (keeping what earlier wiring read and wrote under the same keys when the FMU is changed). The desktop reads an installed FMU's ports from its modelDescription.xml for this; the web edition has no FMUs. See [Code export](codeExport.md) for FMU export, which this mirrors.

An edge may also carry `groupId`, referencing an entry in the top-level `edgeGroups` array: `{ id, name, memberNodeIds, color, definition }`. `definition` holds one shared relationship definition -- an `equation` or `implementation`, plus `parameters`, using the same shapes as an edge's own -- except its bindings are **symbol-keyed** rather than ID-keyed, since the definition has no fixed pair of nodes to bind against: `output` is just `{ symbol }` (every generated edge contributes to its own target by construction, so there is no role to store), and an implementation binding is `{ role, symbol }` in place of `{ nodeId, stateId }`. It expands into a complete mesh across `memberNodeIds`: one **directed** edge for every ordered pair of members -- both A → B and B → A, never a single bidirectional edge; see [Edge and relationship directionality](edgeDirectionality.md) for why -- each an ordinary edge record carrying `groupId` and its own fully resolved, ID-keyed bindings (resolved the same way a Component Library edge template auto-binds, by exact state-symbol match on each pair's two nodes). Editing a group's `definition` re-resolves and overwrites every member edge; no member edge may diverge from it independently. Like subsystems, this is authoring/editing-layer structure: the host strips `edgeGroups` and every edge's `groupId` before validation and execution, so the engine sees only ordinary, individually-resolved edges. See [Edge groups](edgeGroups.md) for the full design.

Projects may contain named numerical `runConfigurations` and an `activeRunConfigurationId`. A numerical configuration contains `globalTimeStep` and `outputInterval` in seconds; output interval is an integer multiple of the global timestep. It may also contain the `execution` settings described in [Parallel execution](parallelExecution.md), and the integration `method` ([Integrators](proposals/integrators.md)): absent, Euler node by node, as below; `"rungeKutta4"`, the classical Runge–Kutta 4 applied to the whole model at once, every node evaluated at each of four stages from every node's stage values, with `stepsPerGlobalStep` (an integer from 1 through 10,000, absent meaning 1) steps of it in each global step; or `"dormandPrince54"`, Adaptive: Dormand–Prince 5(4) applied the same way, choosing its own steps to keep each step's error within `tolerance` (`relative`, above 0 and below 1, absent meaning 1e-6, and `absolute`, above 0, absent meaning 1e-9), every step landing on the global step's end and on the times a schedule jumps or turns within it. `method` is written only when it is not `"nodeByNode"`, `stepsPerGlobalStep` only when the method uses it and it is not 1, and each of `tolerance`'s two numbers only under Adaptive and when it is not its default, so a model that chooses none of them saves exactly as before. (Given `stepsPerGlobalStep`, `dormandPrince54` takes that many equal steps with its error control off, for checking its order; the Run dialog does not offer it.) Under a whole-model method a node's `numerics.substepsPerGlobalStep` and `numerics.integration` apply only if the node is stepped on its own (a node that is a program of its own), and a term written as a program is evaluated once per global step and held; an engine refuses a method it does not know, by name. A project may also contain `requires`, a list of named features the model needs that change its numbers: an engine refuses, by name, any entry it does not know. It is written only when a model needs one; no feature writes it yet. Target time and pacing belong to the transient launch request rather than the model. Pacing selects `fastest`, `realTime`, or `limitedRatio`; limited pacing also supplies a positive `simulationSecondsPerWallSecond`. Pacing limits wall-clock execution and does not alter numerical timesteps. During each global step, every node advances with `globalTimeStep / substepsPerGlobalStep`. References to the advancing node use its latest local state; references to other nodes use the frozen state snapshot from the start of the global step. Nodes synchronize at the global boundary.

Engine results distinguish display `samples` from restart `checkpoints`. Each checkpoint has a UUID, simulation time, complete state vector, and solver identity. Explicit Euler currently has no additional hidden solver state; future integrators extend the checkpoint record rather than treating plot samples as restart data. A node carrying a computational-node provider is the first case of *provider-owned*, not solver-owned, hidden checkpoint state: each checkpoint additionally carries a `providerStates` array of `{ nodeId, payload }` entries, one per node with an `implementation`, where `payload` is that provider instance's opaque `checkpoint()` output (base64-encoded when it appears in a plain-JSON launch request, raw bytes in the binary result format).

The engine accepts an optional `startCheckpoint` in a launch request. Its complete state vector replaces model initial values and its time becomes the segment start. If the model contains any computational-node provider, `startCheckpoint` must also carry a `providerStates` array with exactly one `{ nodeId, payload }` entry per such node; a restart is rejected outright if any is missing, rather than silently resetting a provider's internal state to its `initialize()` default. `targetTime` is absolute and must be later than that checkpoint. The canvas uses it to extend a run from its latest checkpoint ("Extend simulation") and to fork one from any checkpoint ("Fork here"). An extension also gives `continuesResult`, the path of the result file of the run it continues: the engine reads that run's samples, checkpoints and interventions from before `startCheckpoint`'s time and writes them first in its own result, so the result holds the whole run from its start, once each, rather than only the part since the restart. What is exported, saved with the project, forked from or read back of an extended run is then all of it (a fork, by contrast, keeps only its own part, and the branch it came from keeps the rest). Its states are matched by id; a file that cannot be read, or one from a model with other states, is refused. The app copies the file into the run's own folder before it starts, so the run it continues can be released at once.

Unknown fields must be preserved when possible. Readers reject unsupported major schema versions. Additive fields may be introduced within a schema version when older readers can safely ignore them.
