# Causal inference: replaying recorded values for marked input columns

**Status: shipped.** This documents a bug found while reviewing causal inference's committed output against what actually happens when the model is run, and the feature built to fix it -- letting a user mark specific columns as inputs, whose recorded CSV trajectory is then replayed exactly via a generated C++ provider, rather than left with no dynamics at all. See [Causal inference](../causalInference.md) and [Interaction terms](causalInferenceInteractionTerms.md) for the surrounding feature; this proposal's "Non-goals" section explicitly deferred "exogenous input" to a later proposal -- this is that proposal. Implemented in `src/providerTemplate.mjs` (`replayProviderSource`), `src/assistantOperations.mjs` (`addSourceTerm` gained an `implementation` path alongside its existing `latex` one), and `src/renderer/renderer.mjs`/`index.html` (the new "Inputs" review section, reactive uncovered-column detection, and the `initialValue: 0` fix). Covered by `tests/providerTemplate.test.mjs` and `tests/assistantOperations.test.mjs`.

**One real bug was found and fixed during verification, not anticipated in the original design.** The "exact at any substep count" claim below assumed comparing `simulationTime` directly against recorded knot times was reliable; it isn't. A standalone Euler-integration harness (compiling the generated provider against the real SDK header, not a reimplementation) showed that at substep counts where `1/substepsPerRow` isn't exactly representable in binary floating point (5, 37, 1000 -- anything not a power of 2), the accumulated `simulationTime` drifts a hair off the exact recorded knot time, and a raw `t >= kTimes[i]` comparison misclassifies one substep per row boundary into the wrong interval -- producing errors of 0.4-0.5 in a toy 4-sample series, not a rounding-noise-sized discrepancy. The fix: derive both range checks and the interval index from one shared, nudged, dimensionless `position = (t - kTimes[0])/rowTimeStep + 1e-6` value, rather than two independently-tuned comparisons against raw time. Re-verified after the fix: errors at machine-epsilon level (~1e-13 to 1e-15) across substep counts 1, 2, 3, 5, 37, and 1000, including the post-recorded-range hold behavior. See `replayProviderSource`'s inline comments for the fixed logic.

## The bug: root columns get no dynamics at all, not even a frozen value

A `SelfTerm` is only ever emitted for a target with at least one accepted *incoming* edge -- `engine/include/causalInference.hpp:112`'s own comment says so ("one entry per target with at least one accepted lagged edge"), and `engine/src/causalInference.cpp:306`'s `if (sources.empty()) continue;` enforces it structurally, before the `result.selfTerms.push_back(...)` at line 442 is ever reached. A root column -- one nothing in the dataset predicts -- has an empty `sources` list by construction, so it gets **no self-term and no incoming edge**.

`commitCausalInference()` (`src/renderer/renderer.mjs`) only emits `addSourceTerm` for accepted self-terms (line 5277), so a root column gets none. Worse, the new state it does create is hardcoded `initialValue: 0` regardless of what the CSV actually contains (line 5252). Net effect: **a committed root node's state has zero total derivative and sits frozen at 0 forever** when the model is actually run -- not at its last historical value, at a hardcoded zero.

This is structurally identical to how the component library represents a genuinely constant boundary condition (`temperatureBoundary.json`: "nothing feeds heat into it"; `voltageSource.json`: constant "unless something else drives it"). That's correct for an actual constant. It's wrong here: a causal-inference root column isn't constant, it's just unpredicted *by the other columns in this dataset* -- `ambientTemperature`/`motorLoad`/`solarIrradiance` in the 8-node validation system are independent AR(1) processes with real, substantial variance.

The regression test (`tests/engine/continuousTimeDrift.mjs`) never surfaces this because it doesn't run the committed model through the real engine at all for its forward-simulation step -- it hand-rolls a JS Euler loop and explicitly forces root columns to interpolate along their *true historical trajectory*, a capability the real committed model has no way to reproduce today. See the session history in this repo's commit log for the full investigation.

## The feature: mark columns as inputs, replay their recorded values exactly

**UI**: the review-before-commit step gains a new list, alongside the existing candidate-edges and self-terms lists: **every mapped column**, each with a checkbox: "Treat as input -- replay this column's recorded values." Unchecked by default, consistent with "user-selectable, not silently automatic" ([Causal inference (proposal)](causalInference.md)'s decision for `candidateDegrees`).

**Revision, made while implementing:** the first version of this design filtered that list down to only columns with no accepted incoming edge, on the theory that a column already explained by real structure has no need to be replayed instead. Dropped after rereading [the causal-inference blog post](https://www.konjugate.com/2026/08/recovering-causal-graph-from-system.html), which frames root columns as a modeling choice (`amb[t] = 0.5·amb[t-1] + noise`) and explicitly flags, in the original author's own words, that a forward run "will have some error compounding as it would not have access to any source of truth" -- an open caveat, not something already solved, and not a basis for restricting who gets to fix it. There's no principled reason a user can't want *any* column held to ground truth -- isolating one part of the system, distrusting a particular fit for a column that does have real predictors, or just wanting a clean baseline comparison -- so the filter was removed. Every mapped column gets the checkbox now, not just structurally rootless ones.

This also means checking "input" for a column can now supersede either a self term *or* real accepted edges *or* both, not only a self term -- the mutual-exclusion rule below generalizes accordingly, and was verified against exactly this case (see "Verification," below).

**Nothing left unchecked commits silently** -- the "Inputs" section's own hint text explains the tradeoff up front (a self-term-only column settles toward equilibrium; a column with neither stays frozen at its initial value), so the choice is informed before commit rather than surfaced only after. This is deliberately not a blocking gate -- a user may genuinely intend to wire something else into an unchecked column later (e.g. an edge from a node not in this CSV at all).

**Mechanism**: for each checked column, generate a C++ source term (`addSourceTerm` with `implementation.kind: "cpp"`, not an `equationModel`) whose provider embeds that column's own `(time, value)` samples from the CSV and, each `evaluate()` call, emits the exact local slope:

```cpp
// index = floor((simulationTime - t0) / rowTimeStep), clamped to [0, sampleCount - 2]
outputs.addGradient((values[index + 1] - values[index]) / rowTimeStep);
```

This is exact, not approximate, and exact *at any substep count* -- a constant-rate segment integrates exactly under Euler regardless of how finely it's substepped, because the true solution of `dx/dt = constant` genuinely is linear. This sidesteps the whole substep-drift problem (`docs/causalInference.md`'s "one honest limitation") entirely for these specific nodes; it does not need the rate/Δt transform derivation that lagged/interaction terms need, because it isn't derived from a discrete fit at all -- it's the CSV's own recorded slope, used directly.

**No bindings needed** -- the provider only needs `context.simulationTime` (passed regardless of bindings), not any bound state. This is the same no-bindings, time-driven pattern already used for the "Crank pin B" kinematic-driver source term in the component library (confirmed live in-app) -- not a novel pattern for the codebase, just a new generator producing it.

**Language: C++ by default.** `RelationshipProvider`'s single-output shape (which source terms share -- confirmed via `modelValidator.cpp:252`'s `"Source term implementation kind must be equation, cpp or python"` and `executionPlan.cpp:204-217`'s branch on `implementation.kind`, both distinct from the separate, still-Python-only whole-node `implementation` at `executionPlan.cpp:227-231`) supports C++ fully through the existing in-process/shared-memory/pipe backends (`providerRuntime.cpp`'s `createProviderBackend`, `providerWorker.cpp`'s `createRelationshipProvider()`) -- no Python subprocess needed, matching the project's stated preference elsewhere ("no Python subprocess... engine-native..." -- `docs/proposals/causalInference.md`'s "Running it fast" section). **Open item, not resolved here**: whether every installation has a C++ toolchain configured (the app has a persisted `executionMode`/toolchain preference per its own settings store -- worth checking what that defaults to and whether causal inference should just follow it, or force C++ regardless and surface a clear error if no toolchain is configured). Python remains available as a fallback if that turns out to matter in practice; the table-lookup logic is identical either way, only the generated source's syntax differs.

**Restart safety comes for free**: the provider is a pure function of `context.simulationTime`, with no internal accumulated state, so it's naturally correct across a checkpoint/restart without needing checkpoint logic -- consistent with `RelationshipProvider` not exposing `checkpoint()`/`restore()` at all (unlike `NodeProvider`, which does, for providers that actually need memory).

**Out-of-range behavior, a real decision, not a default to skip past**: once `simulationTime` exceeds the CSV's last recorded row, there is no more recorded slope to use. Proposed: hold the last known value (emit gradient `0` past the end), and say so explicitly in the import dialog -- a run that extends meaningfully past the CSV's own recorded duration is the common case, not an edge case, for anyone actually using this to run a model forward.

**Fix the initial-value bug regardless of this feature.** `commitCausalInference()`'s `initialValue: 0` (renderer.mjs:5252) should be seeded from the CSV's first-row value for *every* newly created state, input-marked or not -- this is a general correctness fix (today, *every* newly created node from causal inference starts at 0 regardless of what the data actually shows), and it is a hard prerequisite for this feature's "exact" claim: a perfectly correct gradient integrated from the wrong starting point reproduces the true trajectory shifted by a constant offset, not the true trajectory itself.

**Mutual exclusion, generalized for any column.** Konjugate sums every source term and edge targeting the same state additively, so an accepted input alongside a self term or an incoming edge for the same column would double-count. Checking "input" for a column now unchecks *both* its self term (if any) and every accepted edge targeting it, two-way (checking an edge or self term for a column also unchecks its input), with `commitCausalInference()` re-applying the same exclusion defensively regardless of what the UI state was. This is the direct consequence of removing the root-only filter above: once any column can be replayed, the exclusion has to cover everything that could otherwise target it, not just the self term a root-only column might have had.

## Why this doesn't need a new SDK primitive

An earlier version of this design considered extending the provider SDK with a direct "set this state's value" call, instead of computing a gradient. Rejected: the engine's composition model is additive-only by design, and multiple execution backends depend on that specifically -- `docs/parallelExecution.md`: "Contributions are reduced in their stable compiled sequence... Node results are committed in deterministic order at the global boundary," identically across serial, thread-pool, and partitioned execution, which is exactly why switching backends never changes a result. A direct-set primitive isn't a contribution to be reduced, it's an overwrite, and would need its own conflict/ordering rule that holds identically across all three backends. It also isn't solver-generic: `docs/projectSchema.md:61` explicitly anticipates "future integrators" beyond explicit Euler, and a multi-stage integrator evaluates the derivative at intermediate, perturbed states within one step -- "set the value to X" has no coherent meaning there, while "here is the instantaneous rate" composes with any solver of any order. The gradient-based replay above achieves exact reproduction without needing either property to change, so there's no correctness reason to take on that risk for this feature. If a direct-set primitive is wanted for other reasons later, it should be evaluated on its own terms against those two properties, not introduced as a side effect of this work.

## Non-goals

- **A second "externally controlled, leave uncontrolled" category distinct from "input."** Considered and dropped: unchecking the input checkbox already produces "no dynamics, now with an explicit warning" -- which is exactly what a user who intends to wire something else in later wants. No separate schema concept is needed to express that.
- **Extrapolation beyond the CSV's recorded span via anything smarter than holding the last value** (e.g. fitting a trend to continue past the data). The AR(1)-style root columns this feature targets are exactly the case where a smooth extrapolation would be actively misleading -- holding constant is the honest default; a smarter one is a different, later feature if ever needed.
- **Resolving the C++-toolchain-availability question.** Flagged above as open, not designed here.

## Testing plan and what was actually done

**Numerical correctness** was verified the way the plan originally called for -- compiling `replayProviderSource`'s actual output against the real SDK header (`engine/include/konjugate/relationshipProvider.hpp`) and Euler-integrating it in a standalone harness, at substep counts 1, 2, 3, 5, 37, and 1000, checking both in-range reproduction and post-recorded-range holding. This is what found and confirmed the fix for the floating-point boundary bug described above.

**Structural/generation correctness** (embedded data ordering, no-bindings shape, the sample-count guard, brace balance) is covered by permanent tests in `tests/providerTemplate.test.mjs`. The new `addSourceTerm` `implementation` path (accept cpp/python, reject anything else, correct term shape) is covered in `tests/assistantOperations.test.mjs`. Both run under `npm test`.

**End-to-end, against the real committed-and-run model -- now a permanent regression test, closing what was originally the one gap left.** `tests/engine/causalInferenceCommitAndRun.mjs` builds a project the same way `commitCausalInference()` actually does (via `applyAssistantProposal`, not a reimplementation of its logic), encodes it as a real `.kjt`, and runs it through the actual `konjugateEngine` `validate`/`run` CLI -- wired into `scripts/testEngine.mjs` alongside `continuousTimeDrift.mjs`, so it runs on every `npm run test:engine`. Unlike `continuousTimeDrift.mjs`, which deliberately fakes root columns' behavior in a hand-rolled JS simulator to isolate the rate-transform's own substep-drift property, this test exercises the real thing end to end. Results, asserted with generous margins against the exact figures below:

- *Roots only, calibrated resolution*: downstream RMS error against the true CSV **0.896**, matching `continuousTimeDrift.mjs`'s own hand-simulated baseline (0.896) almost exactly -- the real, committed, actually-run model now reproduces what that test always assumed was achievable. Without input replay (roots left to their own self-decay term only), the same metric is **10.15** -- **11.33x worse**, because a self-decay-only root settles toward equilibrium instead of tracking its real fluctuation, and that wrong signal propagates through the whole downstream chain. Asserted as `withReplayRms < 3.0` and `withoutReplayRms > withReplayRms * 3`.
- *Any-column replay, not just roots*: additionally marking `thermalStress` as an input -- a column with real, high-confidence incoming structure (an edge from `componentTemperature`, its own quadratic self-source term) -- validates and runs cleanly, correctly drops both the edge and the self term targeting it, and reproduces `thermalStress` itself essentially exactly (RMS **0.0000**) -- direct proof the mutual-exclusion rule actually replaced its competing contributions rather than double-counting alongside them, something validation alone cannot catch (Konjugate accepts multiple contributions summed into the same state; only comparing the actual run result can catch a silent double-count). Asserted as `thermalStressRms < 0.5`.
- *Fine resolution (10 substeps/row), roots only*, checked manually but not asserted in the permanent test (kept to calibrated resolution there, to keep the suite's wall-clock cost down): downstream RMS **6.09**, a ~6.8x drift ratio -- consistent with the documented 6-7x substep-drift figure for the fitted (lagged) equations, since that limitation still applies to the columns that remain fitted rather than replayed; the replayed roots themselves stay exact at any resolution (see the harness results above).

**Comparison against the blog post's own evaluation.** [The causal-inference blog post](https://www.konjugate.com/2026/08/recovering-causal-graph-from-system.html) evaluated its recovered model with a one-step-ahead method, not forward simulation: "For each downstream node, the true data of the parent at the previous timestep was used to evaluate the equation, and the result is compared against the true data of the node at this timestep" -- and it says so explicitly: "this is not what you would see from actually running the committed model forward inside Konjugate. That uses a different execution path entirely," going on to flag that a real forward run "will have some error compounding as it would not have access to any source of truth." That gap -- an acknowledged, open question in the post itself, not a claim that forward simulation was already tried and found wanting -- is exactly what `causalInferenceCommitAndRun.mjs` now measures directly. The answer: error compounding turns out to be modest and well-controlled once root/input columns have a real, correct driving mechanism (RMS 0.896 against state magnitudes in the tens-to-hundreds range for this system), and the earlier concern was really about the *absence* of that mechanism (RMS 10.15, an 11x degradation) rather than something inherent to forward simulation itself.
