* [Digital Twin Connections](digitalTwinConnections.md) - How a running model reads the data a lab already records: Konjugate as a client of the lab's files, broker or server, the engine work that comes first, detaching into a sandbox, and proving it on a real recording
* [Live Engine Session](liveEngineSession.md) - Step 2 of the digital twin: an engine that stays running for a whole session and is driven to advance, rewind to a checkpoint with measured states replaced, and take input readings as they arrive, proved against the engine as it is
* [Prediction-Actual Comparison Window](predictionActualWindow.md) - A moving window in which a running model is reset to the measurements each time it moves, drift is watched through the size of those resets, and the speed budget keeps the model ahead of the data
* [Push Service](pushService.md) - Built: the fallback way into a live twin: a service a lab's own script sends readings to as JSON or protobuf over HTTP or a WebSocket, or over gRPC, with a named key per script, local by default and encrypted on the network
* [State Estimator](stateEstimator.md) - Built: an ensemble Kalman filter for the live twin, so readings correct the states nobody measures, the model is weighed against the sensors, and the forecast carries a band
* [The Twin's Control Room](controlRoom.md) - A live twin presented as a control room expects: a short setup naming the model, the source and the mapping (suggested by rules and memory, units converted and proposed), then a window of its own with a tile for every measured signal, an operator view by default and an engineer's to take over
* [Steering a Model by Hand](humanInputBinding.md) - Built: gamepads and joysticks, MIDI controllers and the keyboard bound to live parameters, every change recorded by its size so a run steered by hand replays exactly, bindings kept in the app's settings, and the twin's sandbox following the controls
* [Package Compatibility](packageCompatibility.md) - Minimum Konjugate version for packages, and installing the newest release the running app can use
* [Toolbox Mechanisms and Design Optimisation](toolboxMechanismsAndDesignOptimisation.md) - Toolbox-owned regions of a model rebuilt by merging, providers that solve a group of nodes and edges together, and optimisation towards a design objective with constraints
* [Model Ownership](modelOwnership.md) - Owner, copyright, license and contact details saved inside a project, with per-user defaults, a per-save override, export mapping and the privacy policy changes they need
* [Embedded Assistant Model](embeddedAssistantModel.md) - A small open model fine-tuned for the assistant and shipped inside the app through llama.cpp, with the decisions so far, the evidence from the evaluation harness, and the gates it must pass
* [Rates and Updates](ratesAndUpdates.md) - One governing equation with two kinds of state: a Rate, integrated over the step, and an Update, replaced at its end, both reading the start of the step, so every graph shape is valid, rings included, and no result depends on evaluation order; settling within a step as an option per node or subsystem, and a migration that keeps released models' numbers
* [Integrators](integrators.md) - Stages 1, 2 and 3 built, and BDF for large stiff models: Runge–Kutta 4, Adaptive (Dormand–Prince 5(4)), Stiff (Rodas4) and BDF for the whole model, in the engine, the Run dialog, the stability analysis, code export and the benchmarks, and event location for all three, so a switch written as a condition is stepped to exactly. Runge–Kutta 4, adaptive Dormand–Prince 5(4) and the stiff Rosenbrock method Rodas4, written in Konjugate's own code and applied to the whole model stage by stage, so the coupling between nodes is as accurate as the method; held programs and FMUs, Updates at the global step, checkpoints with solver state, Method in the Run dialog, and Euler node by node staying the default to the bit
* [Algebraic Constraints](algebraicConstraints.md) - Proposed, design only: implicit constraints (Kirchhoff's laws at a junction, a rigid joint, incompressible continuity, a fixed sum of fractions) as a third kind of state whose equation is 0 = the sum of its parts, found wherever Rate states are evaluated so constraints keep the method's order; semi-explicit index 1 first, with matching, blocks and the index found along the graph, higher index refused by name and later reduced by differentiation and projection; consistent initialisation; Newton per stage for Euler and Runge–Kutta and a mass matrix for Rodas4; partitions, programs, FMUs, export and the web; diagnostics in plain words; and a file that changes only where a constraint is used
* [Resets at Events](resetAtEvent.md) - Proposed, design only: setting a state's value at the instant a condition becomes true (a bouncing ball's v ← −e·v at contact, a counter, a relay with hysteresis, an integrator reset, a dose, a neuron that fires), written as a reset under the state it sets, located exactly under Runge–Kutta 4, Adaptive and Stiff and applied at substep ends under Euler, node by node; every reset at an instant reading the values just before it, cascades in rounds, and a Zeno guard that stops the run in words; Updates still at global steps, checkpoints, programs and constraints; determinism, export, FMUs and the web; a file that changes only where a reset is written, with requires; and benchmarks against exact solutions
* [Program SDK Version 2](programSdkV2.md) - Accepted, not yet built: a second C++ and Python program SDK beside the first: evaluate() only computes, memory is declared and changed only in advance() once per accepted step or on a clock, saved and restored by the engine with no hand-written checkpoint, and ports declared once with units and checked at load, so every program can take Runge–Kutta 4, Dormand–Prince and Rodas4 stages; the further hazards found in today's SDK (shared Python instances, unbound inputs reading zero, unnamed NaN errors, relationship memory never checkpointed) and the answer to each, migration with version 1 held, and a staged plan
* [One Editor for Nodes and Relationships](unifiedEntityEditors.md) - One editor shell written once; an Equations tab with one equation per state, the card's own part typed straight in and every other part a read-only chip in the reader's names; states as single lines that fold when nothing changes them; the left side as the state's order, open to higher orders; programs as one line; and the source term card gone
* [Neural Toolbox](neuralToolbox.md) - Paused: deep learning is not being explored at this point; records how networks would run under Rate and Update, why same-instant results depend on evaluation order on graphs with cycles (graph neural networks above all), and the bottleneck to solve before they run efficiently. A toolbox for neural networks as parts of a physical model: imported from ONNX or PyTorch, run as a block or opened up as neurons and weights grouped into subsystems, inspected, steered, edited and fine-tuned against the system they act on, and exported back, led by a robot arm's learned policy
* [Suggested Local Models](suggestedLocalModels.md) - Built: running the assistant on the person's own computer through Ollama, which the app links to but never downloads: measured Qwen3.5 models suggested first, any Hugging Face GGUF model as well, and the demonstration provider replaced in the tests by a fake Ollama server
