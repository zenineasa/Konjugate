# Numerical stability diagnostics

**Status: all three phases implemented.** This document captures where the original brainstorm landed -- the phase breakdown, the concrete mechanism proposed for each phase, and what a diagnostic like this can actually recommend once it fires -- so the idea survives past the conversation that produced it, and now also records what actually got built against that plan. Post-run: `src/postRunStabilityDiagnostics.mjs` (`detectInstabilityFingerprint`, `checkSubstepConvergence`, `recommendedSubstepFixProposal`), unit-tested in `tests/postRunStabilityDiagnostics.test.mjs` and verified end-to-end against the real compiled engine in `tests/engine/postRunStabilityDiagnostics.mjs` (wired into `scripts/testEngine.mjs`). Pre-run: `assessNodeStability()` (`engine/include/stabilityAnalysis.hpp`, `engine/src/stabilityAnalysis.cpp`), wired into `validateModel()` (`engine/src/modelValidator.cpp`) as the `numericsPotentiallyUnstable`/`numericsStiffModel` warning issue codes, unit-tested in `engine/tests/stabilityAnalysisTests.cpp` and verified end-to-end against the real `validate` CLI. During-run: `DuringRunStabilityMonitor` (`engine/include/duringRunStabilityMonitor.hpp`, `engine/src/duringRunStabilityMonitor.cpp`), wired into `runSimulation()`'s own main loop (`engine/src/simulationRunner.cpp`) and driven by the run configuration's own opt-in `stabilityMonitoring.nodeIds`, unit-tested in `engine/tests/duringRunStabilityMonitorTests.cpp` and verified end-to-end (including the protobuf `StabilityFindingReport` wire format) against the real `run` CLI in `tests/engine/duringRunStabilityMonitoring.mjs`. What's built across all three phases is the analysis/recommendation capability, and it now has UI on every phase: the post-run findings/apply-fix UI, and a `#runStabilityMonitoring` checkbox on `#runLaunchDialog` (`src/renderer/index.html`/`renderer.mjs`) that toggles the run configuration's own `stabilityMonitoring.nodeIds` -- checked (the default) leaves `engineAdapter.mjs`'s existing "monitor every node" behavior unchanged; unchecked sends an empty list, disabling during-run monitoring for that run only (the post-run fingerprint check is unconditional and independent of this toggle, so it still runs regardless). The pre-run warning surfaces through the existing validation-issues panel every other validator warning already uses.

## Problem

Konjugate's solver is fixed-step Explicit Euler, chosen deliberately and documented as a permanent constraint rather than a current limitation (see [Code export](../codeExport.md)'s "Importing an FMU" section: Model Exchange is refused specifically so Konjugate keeps its own fixed-step Euler in full control, never handing stepping to a host's adaptive solver). Explicit Euler is only stable for a given step size against a given system's own dynamics -- a model with fast dynamics (a stiff spring, a high-gain control loop, a small time constant relative to the chosen step) stepped too coarsely doesn't fail gracefully, it diverges, and today's only detector is the hard non-finite check already present in `finalizeContribution`/`applyAlgebraicTasks` (`engine/src/executionPlan.cpp`) -- a throw once a state has already become NaN or Inf. That's binary and late: it says nothing about a run that stays finite but is numerically garbage (a coarse-step oscillation that never blows up, just never means anything either), and it gives no guidance on *why* a run failed or what to change, only that it did.

## Proposal: three phases, ordered by cost

### Pre-run -- local linearized stability check (implemented)

At validate time, `assessNodeStability()` (`engine/include/stabilityAnalysis.hpp`, `engine/src/stabilityAnalysis.cpp`) computes a node's own local Jacobian via finite-difference perturbation (central difference) of the exact sequence `integrateNode`'s own substep loop calls -- `applyAlgebraicTasks` then `evaluateContributionTasks` then `reduceContributions` (`engine/src/executionPlan.cpp`) -- no new solver or symbolic-differentiation machinery, just repeated calls to code that already exists, perturbing one differential state at a time around the node's initial values. From that Jacobian's eigenvalues (`Eigen::EigenSolver`, since a nonlinear system's Jacobian is not generally symmetric and can have genuinely complex eigenvalues for an oscillatory unstable mode), it checks Explicit Euler's real stability condition at the node's own (substep-adjusted) step size: `|1 + stepSize·λ| ≤ 1` for every eigenvalue `λ`. A violation becomes the `numericsPotentiallyUnstable` warning-severity issue in `ValidationResult` (`engine/src/modelValidator.cpp`), computed against the document's *active run configuration* (the only concrete step size a static document has -- see "What can actually be recommended" below for the multi-configuration caveat this implies) and skipped entirely when the document has no run configuration to check against. The stiffness ratio (fastest eigenvalue magnitude over slowest, among those with negative real part) is the separate `numericsStiffModel` warning, only checked when the node is otherwise stable. **Only equation-only nodes are assessed.** A node with any programmable (cpp/python) source term, algebraic task, or its own computational-node provider is skipped (`std::nullopt`) rather than probed -- doing so safely would mean actually compiling and spawning a real provider (`ProviderRuntime`) just to validate a document, a much larger and riskier undertaking than this heuristic check; see `assessNodeStability`'s own header comment. **Only a node's differential states are perturbed and checked** -- an algebraic (`setsValue`) state is recomputed fresh every substep rather than integrated, so Explicit Euler's condition doesn't apply to it the same way; its current value still fully participates in the Jacobian (perturbing a differential state re-runs `applyAlgebraicTasks` first, so any indirect coupling through an algebraic state is captured correctly -- verified directly in `stabilityAnalysisTests.cpp` with a `y = 2x` (algebraic) / `dx/dt = -y` fixture, which the check treats identically to a direct `dx/dt = -2x`). The real limitation: this is only ever evaluated *at the initial state*, so it says nothing about a nonlinear system that starts stable and drifts into an unstable regime later -- that gap is what the during-run phase exists to close. **No per-node dismiss/silence mechanism is needed for this warning.** It's self-resolving through the very lever it suggests: raise the node's substeps enough to satisfy `|1 + stepSize·λ| ≤ 1` and the check, re-evaluated against the current setting, simply stops firing -- a warning that's still showing means the model genuinely still fails the condition, which is real information, not noise to suppress. (Checked against the codebase directly: there is no existing precedent anywhere for dismissing/acknowledging a validation warning, for this or any other issue.) The narrower case of "I've reviewed this and I'm proceeding anyway despite the numbers" is general to *any* warning, not specific to this one, so it belongs in a future general "acknowledge any validation warning" feature if one is ever built, not a bespoke mechanism invented here.

**Already surfaced in the UI, mostly for free.** Unlike the post-run phase, this one needed no new *display* mechanism at all: `ValidationResult` issues already render in the existing validation-issues panel (`src/renderer/renderer.mjs`), so the warning appears there automatically. Clicking it calls `navigateToValidationIssue()`; when the issue carries a resolved attributed parameter (see "Attribution, not just detection" below), it now deep-links straight to that parameter's own value input, in the edge editor or the node's own source-term sub-editor. For the cases where no parameter could be attributed (e.g. a bare self-referencing `dx/dt = x` with no free parameter, or `unconditionallyUnstable`), clicking still only opens the flagged node's general editor -- `location.field: "numerics"` still isn't in the generic per-kind field lookup table, so there's no field focus at all in that fallback case. A small, real, still-open gap, not a new one.

### During-run -- growth tracking, plus a trend-gated re-check (implemented)

Two tiers, meaningfully different in cost, and the second is not scheduled blindly -- it's triggered by the first, which is what keeps its cost bounded regardless of graph size (see "Bounding the during-run re-check's cost" below). Both live in `DuringRunStabilityMonitor` (`engine/include/duringRunStabilityMonitor.hpp`, `engine/src/duringRunStabilityMonitor.cpp`), constructed once per run in `runSimulation()` and driven by one call to `observeGlobalStep()` per completed global step (`engine/src/simulationRunner.cpp`, right after `states = std::move(synchronizedStates)`). Tier 1, cheap and on-by-default for every *monitored* node: an incremental version of the exact same "sustained growth" check `detectInstabilityFingerprint()` (post-run phase) runs over a complete trajectory, just evaluated one step at a time as the run proceeds instead of after the fact -- four consecutive steps of a state's own successive differences growing faster than a 5% threshold flags `duringRunGrowthTrend`, strictly more informative than today's all-or-nothing non-finite throw, and cheap since it's arithmetic on values the engine already produces. Tier 2, expensive and trend-gated, not scheduled: the moment a node's growth episode first crosses that threshold, it becomes a candidate for a fresh call to `assessNodeStability()` -- **the exact same pre-run function**, called again but now at the node's *current* state instead of only at t=0, which is what actually catches a system that starts stable and grows unstable partway through a run. Confirmed instability produces `duringRunPotentiallyUnstable`. An ongoing growth episode is only ever reported once (Tier 1) plus once (Tier 2), not on every subsequent step while it continues -- verified directly in `duringRunStabilityMonitorTests.cpp`.

**Opt-in, and scoped, via the run configuration -- not the project schema.** `stabilityMonitoring.nodeIds` (an array of node ids) is a new field on the *run configuration* JSON (`--configuration run.json`, the same file `pacing`/`providers` already live in), not the `.kjt` document itself: monitoring is about how a given run is executed, not what the model is, and the doc's own "scoped opt-in" cost-bounding point (below) wanted exactly this -- a specific node or subsystem, not only a single graph-wide flag. Absent or empty `nodeIds` (the default) makes the monitor's own `observeGlobalStep()` return immediately every step -- not even the cost of an empty check. Verified end-to-end against the real `run` CLI: an unmonitored run of a genuinely unstable model produces zero findings; the same run with `stabilityMonitoring: { nodeIds: [1] }` produces both a `duringRunGrowthTrend` and a confirming `duringRunPotentiallyUnstable` finding, timed exactly where the real trajectory crosses the threshold.

**Findings are surfaced through a real protobuf field, not JSON.** An earlier version of this pass put `stabilityFindings` into the result file's hand-built metadata JSON string, reasoning that it was additive and low-risk. That was corrected: `protocol/engineProtocol.proto` gained a proper `StabilityFindingReport` message (`node_id`, `state_id`, `code`, `message`, `global_time`) and a `repeated StabilityFindingReport stability_findings = 6;` field on `ResultFile`, matching the *exact* reasoning the .proto file's own header comment already gives for why the one-shot report messages (`ValidationReport` and friends) moved off hand-written JSON in the first place: a hand-rolled JSON string can't natively represent `Infinity`/`NaN`, and a diverging amplification factor is precisely the kind of value this feature needs to report reliably. `simulationRunner.cpp` populates the field directly (`result.add_stability_findings()`); `src/engineProtocol.mjs`'s `decodeResultFile()` decodes it by hand, field-by-field, mirroring the exact pattern already used there for `ResultCheckpoint` (nested nested-message decoding, not a call into the separate pbjs-generated `reportMessages.mjs` module, which is `engineProtocol.mjs`'s own established convention for this specific message, not something this feature should diverge from). Verified end-to-end against the real `run` CLI in `tests/engine/duringRunStabilityMonitoring.mjs`, including that `globalTime` survives the round trip as a real finite double.

#### Bounding the during-run re-check's cost (implemented as designed)

A per-node Jacobian costs roughly `O(states² )` (each state perturbed once, each perturbation re-evaluating that node's own contributions) -- fine for one suspect node, not fine multiplied across every node in a large graph on a fixed cadence. Three pieces keep it bounded instead of scaling with graph size, all three shipped exactly as designed here: (1) **trigger, don't schedule** -- a node only becomes a Tier-2 candidate once its own Tier-1 growth trend crosses a "getting suspicious" threshold (below the hard blow-up level that would already throw, but rising), so a well-behaved run pays for zero Tier-2 checks regardless of how large the graph is; cost tracks how many nodes are actually drifting, not how many nodes exist. (2) **a hard per-step budget** -- `DuringRunStabilityMonitor`'s `tier2PerStepBudget` constructor argument (default 4) caps how many nodes can be Tier-2-checked in a single `observeGlobalStep()` call; a FIFO `pendingTier2Queue_` carries any excess into later calls rather than spiking one step's cost. (3) **scoped opt-in** -- `stabilityMonitoring.nodeIds` (see above) targets a specific node or subsystem directly, not only "on for the whole graph," so someone investigating one known-suspect area never pays Tier-2 cost for the rest of the model regardless of what triggers.

### Post-run -- analysis of a completed result, no extra simulation cost (implemented)

The cheapest tier by far, since it works entirely on a result that already exists -- pure JS against an already-decoded result/report, no engine changes at all. Two concrete checks, both in `src/postRunStabilityDiagnostics.mjs`:

1. **`detectInstabilityFingerprint(result, document)`** -- a sawtooth/alternating-sign fingerprint scan on stored trajectories, the specific, recognizable signature of Explicit Euler instability as opposed to real physical oscillation. Reports sustained magnitude growth generally (substep-count-agnostic), and additionally claims the *classic* sawtooth fingerprint only when the implicated node has `substepsPerGlobalStep === 1` -- a node substepped internally can be genuinely unstable at the substep level without the sign-alternation surviving into its once-per-global-step recorded output, so claiming the specific fingerprint for a multi-substep node would be a false-confidence overclaim. This can't distinguish a numerically-unstable-but-physically-stable model from one whose underlying physics is genuinely unstable (a falling-over inverted pendulum is not a numerics bug) -- it's a heuristic finding, not a diagnosis, same as the pre-run phase's own Jacobian check would be.
2. **`checkSubstepConvergence({ executable, document, runConfiguration, nodeIds, directory })`** -- re-runs a candidate node at repeatedly doubled substep counts and compares consecutive doublings' trajectories (RMS, relative to the later run's own magnitude) until they agree within `relativeTolerance`, Richardson-extrapolation style. Answers a materially different, stronger question than "did it blow up": whether the run actually *converged* to something, versus merely stayed finite while still being numerically wrong. Bounded by `maxSubstepMultiplier` regardless of outcome. Verified directly against the real engine on a single-state exponential-decay fixture (`tests/engine/postRunStabilityDiagnostics.mjs`), with `k·globalTimeStep = 2.1` chosen to sit just past the instability boundary at `substeps=1` -- the module's default `relativeTolerance` (1%) and `maxSubstepMultiplier` (256) reflect what that verification run showed, not a guess: Explicit Euler's own first-order accuracy means consecutive doublings' agreement only improves as roughly `O(1/N)`, so reaching much tighter than ~1% agreement can genuinely need several hundred substeps even for a mild, already-stabilized case.

**`recommendedSubstepFixProposal(nodeId, substeps)`** is the "auto-apply the fix" half: rather than a new mutation path, it returns a proposal built entirely from `assistantOperations.mjs`'s existing `updateNode` operation (`{ kind: 'updateNode', nodeRef: nodeId, substepsPerGlobalStep: substeps }`), the same operation the AI assistant and any future manual edit already use to change a node's substep count -- passing it to the existing `applyAssistantProposal(document, proposal)` gets the same undo-tracked application every other assistant-driven edit already gets, for free, with zero new engine or schema machinery.

**Not yet built:** any UI. No Results Analysis panel surfaces these findings, and no "apply fix" button exists -- today this is a capability a caller (a test, a future UI, a future CLI) invokes directly, naturally at home as a new signal in the Results Analysis window once that wiring happens.

## Recommended build order

Post-run first -- cheapest, zero engine risk, works on results Konjugate can already produce today, and is useful on its own even before the other two phases exist. **Done.** Pre-run second -- a small, contained engine addition (one new perturbation-based check plus two new validator issue codes) that catches the single most common real mistake (too few substeps for a node's actual dynamics) before a run is ever started. **Done.** During-run last, and the expensive tier of it opt-in only, since it's the one phase that touches the hot loop. **Done** -- built as an isolated new class the main loop calls into at one point, rather than logic woven through the loop itself, which kept the actual hot-path change to one small `if` block (see the During-run section above); regression-tested against the full engine suite (ctest, `npm run test:engine`, `npm test`) and the interaction suite to confirm the live "Run" path was unaffected.

## What can actually be recommended (not just "shrink the timestep")

The user's question that prompted this section: is changing the step size the only lever a diagnostic like this can point at? No -- several others fall out of the same Jacobian computation or are already-existing engine capabilities that just aren't being suggested anywhere today. **Implementation status check:** the shipped `numericsPotentiallyUnstable` warning (see Pre-run above) reports that a node is unstable and by how much (the amplification factor), **which specific edge/source-term parameter is most responsible** (eigenvector-based attribution), **a concrete substep count to recommend** (`requiredSubsteps`, see the first bullet below), and **whether raising substeps can fix it at all** (`unconditionallyUnstable`, see "Distinguish a numerics problem..." below) -- all four now shipped.

- **Per-node substeps, not a global step change. Done.** `numerics.substepsPerGlobalStep` is already per-node in the schema (see [Project schema](../projectSchema.md)), so the diagnostic's first and cheapest recommendation is narrower than "shrink the global timestep everywhere" -- it names the *specific* node whose local eigenvalues are the problem and suggests raising just that node's own substep count, leaving every other node's cost untouched. **No new "substep as a percentage/fraction" schema concept was needed.** The recommendation falls out algebraically from the existing integer-count field: `assessNodeStability()` (`engine/src/stabilityAnalysis.cpp`) takes the TIGHTEST stable step size across *every* eigenvalue (not just the dominant one) -- `h ≤ -2·Re(λ)/|λ|²`, Explicit Euler's stability condition generalized to complex λ (the real-axis-only `h ≤ 2/|λ|` is this formula's special case at Im(λ)=0) -- and divides that into the run configuration's `globalTimeStep`, rounding up, giving `requiredSubsteps`. `modelValidator.cpp` folds it straight into the `numericsPotentiallyUnstable` message. One real wrinkle, left unsolved by design: a project can have multiple run configurations with different `globalTimeStep` values, and only the *active* one is checked -- a substep count stable for it isn't automatically stable for another configuration's step size. A genuinely resolution-independent node margin -- expressed as a fraction of *whatever* global step later gets chosen -- would be a real, separate schema feature; a reasonable future enhancement, not something this diagnostic needs to be useful.
- **Attribution, not just detection. Done, including precise click-to-focus.** Since the check already computes a Jacobian, the offending eigenvalue's own eigenvector (`engine/src/stabilityAnalysis.cpp`, `Eigen::EigenSolver` now requested with `computeEigenvectors=true`) identifies which of the node's own states is driving the instability; a further finite-difference sensitivity pass over that state's own contributing parameters (perturb each, measure how much that state's derivative moves) names the single strongest one. `engine/src/modelValidator.cpp` resolves the resulting `(sourceId, parameterId)` pair back to a human-facing phrase against the document and folds it into the `numericsPotentiallyUnstable` message, e.g. *"...driven mainly by the edge "Spring"'s 'stiffness' parameter..."*. This generalizes to non-linear relations for the same reason the Jacobian itself already does -- it's a numerical perturbation of whatever the node's real equations compute, not a symbolic/linear-only method -- though, like the Jacobian, it is only ever a *local* read at one operating point.

  **This bullet's original "no new UI mechanism needed" claim didn't survive contact with the actual code** -- `navigateToValidationIssue()`'s generic per-kind field lookup table only ever focused the *first* DOM match in a container, and the node editor's `sourceTerms` field had no focusable input at all. A first pass at this feature shipped text-only (the parameter named in the message, clicking still only opening the general editor) before circling back to build the real thing: `IssueAttributedParameterReport` (`protocol/engineProtocol.proto`, additive alongside -- not replacing -- the issue's own `location`), `data-parameter-id` attributes now set on every edge-parameter and source-term-parameter row (`src/renderer/renderer.mjs`), and a new branch at the top of `navigateToValidationIssue()` that, when an issue carries a resolved attributed parameter, opens the right editor (the edge editor, or the node editor followed by `openSourceTermEditor()`) and focuses that exact row's value input via `` `[data-parameter-id="${id}"] input[data-field="value"]` ``. The issue's original `location` (kind=node, field=numerics) is untouched, so nothing that reads it directly broke.
- **Convert a fast state to an algebraic one. Partially done.** If a state's own dynamics are much faster than the rest of the system it's coupled to (a classic quasi-steady-state case), the fix isn't a smaller step at all -- it's recognizing that state doesn't need to be integrated. This is exactly what `setsValue` (see [Project schema](../projectSchema.md) and [Interaction providers](../interactionProviders.md)) already exists for: turning a source term into a genuine, recomputed-fresh algebraic state removes it from the stiff ODE entirely rather than stepping around it more finely. **What shipped, honestly scoped down from "recognizes an isolated state":** `assessNodeStability()` already identifies the dominant *state* (not just the dominant *parameter*) while computing attribution (`dominantStateId`), so the existing generic advice now names it directly -- "converting `'targetTemperature'` to setsValue" instead of "converting a fast state to setsValue." What's still not built is the harder half: actually detecting that a fast state is *isolated* (weakly coupled to the rest, via the Jacobian's off-diagonal terms) before recommending this over the other two options -- today all three recommendations (raise substeps, setsValue, split node) are always offered together, un-ranked.
- **Split fast dynamics onto their own node.** Because substeps are per-node, moving a fast state onto a node of its own (rather than sharing a node -- and therefore a substep count -- with slower states) lets it be stepped finely without forcing the same cost onto everything else sharing that node today.
- **Distinguish a numerics problem from a modeling/tuning problem. Done.** A high-gain feedback loop that's unstable at any practical step size usually isn't a numerics bug at all -- it's a control-design choice (the gain itself is too aggressive) that Explicit Euler is just the messenger for. This has a precise, cheap signal already sitting in the same eigenvalue loop `requiredSubsteps` uses: for Re(λ) ≥ 0, Explicit Euler's amplification `|1+h·λ|` is ≥ 1 for *every* step size h > 0, so no substep count -- however large -- ever stabilizes that mode. `assessNodeStability()` flags this as `unconditionallyUnstable`, and `modelValidator.cpp` gives it a distinctly different message ("no substep count can stabilize this with Explicit Euler ... this looks like a modeling or gain-tuning issue rather than a numerics one") instead of the usual substep/setsValue/split-node recommendation.
- **Explicitly not recommended: switching solvers.** An implicit or adaptive-step integrator would sidestep Explicit-Euler-specific stability limits generally, but that's a deliberate non-goal already documented (see the Problem section above) -- this diagnostic's recommendations need to stay inside that constraint, not imply a future solver change is coming.

## Open questions

Every question raised during the brainstorm this document captures was resolved before it ended, each inline where it's most relevant rather than collected here: the during-run re-check's cost-bounding (under "Bounding the during-run re-check's cost"), whether the pre-run warning needs a per-node dismiss/silence mechanism (under "Pre-run -- local linearized stability check" -- it doesn't, since the check is self-resolving), and how attribution is surfaced in the UI without cluttering the issues list (under "What can actually be recommended," the "Attribution, not just detection" bullet -- it reuses the existing `location.field`/`navigateToValidationIssue` mechanism, no new UI). Nothing is left open from this pass; the next thing a real design would need is scoping and sequencing an actual implementation, not further brainstorming.

## Existing systems this builds on

- `evaluateContributionTasks`/`applyAlgebraicTasks` (`engine/src/executionPlan.cpp`) -- the exact per-substep evaluation code both the pre-run phase's Jacobian perturbation and the during-run phase's Tier-2 re-check (via the same `assessNodeStability()`) call repeatedly, rather than any new symbolic or solver machinery.
- `ValidationResult`'s issue-reporting mechanism (`engine/src/modelValidator.cpp`) -- the existing warning/error surface the shipped `numericsPotentiallyUnstable`/`numericsStiffModel` issues plug into, the same way `nodeSubstepsInvalid` and every other numerics check already does.
- `numerics.substepsPerGlobalStep` (per-node, see [Project schema](../projectSchema.md)) -- the already-existing, already-more-targeted-than-global lever the pre-run recommendation points at, now with a concrete required-count number (`requiredSubsteps`) -- see "What can actually be recommended" above.
- `setsValue` (see [Project schema](../projectSchema.md), [Interaction providers](../interactionProviders.md), and [the causal-inference input-replay proposal](causalInferenceInputReplay.md) for its own design history) -- the recommended remediation for a state whose own dynamics are the actual source of stiffness, not just something to step around more finely.
- The Results Analysis window -- the natural UI home for the post-run phase's sawtooth-fingerprint and convergence-check signals, since it already exists as where a completed run's results are inspected.
- [Code export](../codeExport.md)'s "Importing an FMU" section -- the existing, explicit statement of the fixed-step-Euler-only constraint this proposal's recommendations must stay inside.
