# Konjugate Web: a browser edition, not a permanent preview

**Status: proposal, phases 1-3 of the roadmap below done.** This document captures the brainstorm that produced the scoping decisions below, grounded in the actual current code (not assumptions about it), so an implementation attempt starts from a realistic picture rather than "compile the engine to WASM and it should mostly work." Phase 1 (see "Proposed phased roadmap" below) is now real: `npm run build:web` (`engine/CMakePresets.json`'s `web` preset) builds the complete, unmodified `konjugateEngine` binary for `wasm32-emscripten` -- not just an equation-only slice, the actual full engine including `cppToolchain.cpp`/`fmiImport.cpp`/`providerRuntime.cpp` -- as a reusable ES module (`Module.FS.writeFile`/`Module.callMain`/`Module.FS.readFile`, mirroring the real CLI contract exactly; see [Development setup](../developmentSetup.md#web-build-experimental)). Verified to produce byte-for-byte-correct protobuf output, decodable by the real, unmodified `src/engineProtocol.mjs`, in **two** environments: plain Node, and a real Chromium renderer (an Electron `BrowserWindow`, driven the same way `tests/interactionRunner.mjs` drives the desktop app's own UI) -- deliberately not just Node, since a real browser has no filesystem passthrough to lean on and an early version of this spike that worked under Node (via `-sNODERAWFS=1`, a Node-only flag) would not have loaded in a browser at all.

Phase 2 (`src/webEngineAdapter.mjs`) is also real, for the one-shot operations only (`capabilities`, `validate`, `run`, `infer`, `fit`) -- see that phase's own entry below for exactly what's covered and what isn't. Building and testing it in a real browser surfaced two further real gaps, both fixed, not routed around:

- `src/engineProtocol.mjs` -- the shared decoder every result/event ultimately goes through, used throughout the desktop app too, not just this adapter -- turned out to depend on Node's `Buffer` (`.equals()`, `.readDoubleLE()`, `Buffer.concat`, etc.) despite its own header comment already claiming to be renderer-safe. That claim held by accident: Electron's renderer happens to polyfill a minimal `Buffer` global even under `contextIsolation`, but a real standalone browser tab has none at all. Now rewritten Buffer-free (`Uint8Array`/`DataView`/`TextDecoder` only) -- verified against the full existing test suite (which covers this file already) plus this phase's own real-browser test, with zero behavior change for every existing caller (`Buffer` already *is* a `Uint8Array`, so nothing downstream needed to change).
- `src/reportProtocol.mjs`'s `protobufjs/minimal.js` dependency is CommonJS (`module.exports`/`require`), loadable via Node's own CJS/ESM interop but not by a browser at all without either an import map pointing the bare specifier at a browser build, or a bundler -- real, separate infrastructure work matching phase 3 below, not a phase 2 problem. `webEngineAdapter.mjs` now imports it lazily (only inside `validate`/`infer`/`fit`, dynamically, not at module top level) specifically so a page that only calls `run()`/`capabilities()` never pays for a problem that isn't theirs -- confirmed by testing the failure directly in a real renderer before fixing it: a static top-level import broke the whole module, including the parts that don't need it at all.

Phase 3 (`src/renderer/webShims/*`, `scripts/buildWebShell.mjs`/`serveWebShell.mjs`) is also real: `npm run build:webShell && npm run serve:webShell` serves the actual, unmodified `src/renderer/renderer.mjs` -- same file the desktop app loads, zero source changes -- against browser-native replacements for every `window.*` global `src/preload.mjs` normally injects. This closed the `protobufjs/minimal.js` gap above too: `index.html`'s importmap now maps that bare specifier at a tiny shim (`webShims/protobufjsMinimalShim.mjs`) exposing a classic-script-loaded, pre-bundled browser build of protobufjs's minimal runtime -- verified end-to-end in a real Chromium renderer (`validate()` against a bundled example decodes a real protobuf report correctly). Two scope decisions, both made deliberately rather than discovered as gaps partway through:
- **Run is a batch fallback, not live.** `renderer.mjs`'s Run button always calls the live/streaming `window.engine.start(...)`; true live streaming needs a Worker + Asyncify-style design so a blocking WASM `callMain()` can still receive pause/cancel/parameter-tweak commands mid-run -- a separate, harder project, not attempted here. Instead, `src/webEngineWorker.mjs` runs the existing one-shot `runWithWebEngine()` off the main thread, and `src/webEngineLiveShim.mjs` presents that single result through the exact same job/onComplete/readResultSeries/readResultSample/releaseResult contract a real live job uses (verified against `src/main.mjs`'s actual handlers and `src/resultSession.mjs`, which both this shim and those handlers import -- confirmed already renderer-safe). Verified end-to-end in a real renderer: `window.engine.start()` returns a jobId immediately, `onComplete` fires with a full result, `readResultSeries`/`readResultSample`/`releaseResult` all work against it. No progressive live plotting, no pause/cancel/live-parameter-tweak mid-run -- `setPacing`/`setExecutionState`/`setParameterValue` reject with a clear message instead of silently no-op'ing.
- **Project save/load covers unencrypted `.kjt` only.** `src/browserProjectCodec.mjs` adds a browser-native decoder (`DecompressionStream`-based) alongside phase 2's existing encoder; an encrypted file fails with a distinctly-catchable, clearly-worded error rather than a silent wrong answer. Drag-drop and File System Access API (`showOpenFilePicker`/`showSaveFilePicker`, falling back to `<input type=file>`/download-blob where unsupported) both reuse `renderer.mjs`'s own real `openProject()`/`saveProject()` flow (including its unsaved-changes confirmation) with zero changes to that file -- drag-drop stashes the dropped bytes and clicks the toolbar's real `#loadButton`, rather than forking or reimplementing `loadOpenedProjectFile()`.

Every other `window.*` global (`shapeLibrary`, `componentLibrary`, `examples`) that's backed by bundled, static content works for real, served as static files -- `examples`' and `componentLibrary`'s bundled listings are generated at build time by `buildWebShell.mjs` (mirrors `src/main.mjs`'s own directory-scan logic, since a browser can't scan a directory itself). Everything genuinely desktop-only (`windowControls`, `providerEditor`, `providerToolchains`, `extensions` install/uninstall, `addons`, `aiProviders`, FMU export/merge) is an honest `{available: false}` (or a no-op, where that's accurate) rather than a silent stub -- a dismissible in-page banner lists these plainly rather than leaving them to be discovered as broken buttons. Real-browser (Electron `BrowserWindow`) testing surfaced one further gap, fixed at the root: the importmap's own inline script content changed (the new `protobufjs/minimal.js` entry), which silently invalidated `index.html`'s CSP `sha256-...` hash for it -- `buildWebShell.mjs` now recomputes that hash from what's actually served, rather than carrying the desktop's original one forward.

Everything from "Python providers via Pyodide" (phase 4) onward remains proposal.

## Ambition

The inspiration is [vscode.dev](https://vscode.dev): Visual Studio Code running in a browser, reachable with no install. **The long-term goal is near feature parity with the desktop app, not a permanently smaller "preview" product.** Compilers (and therefore programmable C++/Python providers) won't be available in the first working version — that's a real, structural gap on day one — but it is a gap with a genuine path to closing, not a wall. This document treats compiler availability as the thing that arrives in a *later phase*, not as a reason to scope the whole effort down to "equation-only, forever." The one piece that stays genuinely harder even long-term is FMU import, for reasons specific to what an FMU actually is — see below.

## What already ports cleanly

The numeric core has no OS-specific dependencies at all. `Eigen`, `boost::property_tree`, the protobuf runtime, the Explicit Euler solver, expression evaluation (`executionPlan.cpp`'s `CompiledExpression::evaluate`), and the entire numerical-stability-diagnostics engine (`stabilityAnalysis.cpp`, `modelValidator.cpp`) are all pure, portable C++. Emscripten handles this class of code well.

There's a second, more structural piece of good news: **the renderer already talks to everything through a small, named set of browser-global seams, never directly to Node.** `src/preload.mjs` exposes `window.engine`, `window.projectFiles`, `window.shapeLibrary`, `window.componentLibrary`, `window.providerEditor`, `window.providerToolchains`, `window.modelClipboard`, `window.extensions`, `window.addons`, `window.aiProviders`, and a few more — fourteen `contextBridge.exposeInMainWorld` calls in total — each backed today by an `ipcRenderer.invoke` call into `src/main.mjs`. `src/renderer/renderer.mjs` itself has zero direct `node:*` imports (`contextIsolation: true`, `nodeIntegration: false` — this is already enforced, not just a convention). That means a web build's real task is **reimplementing what sits behind each of those fourteen globals**, not rewriting the renderer. A large fraction of `renderer.mjs` — model editing, the Three.js canvas, the equation editor, causal inference, digital-twin tuning UI — could plausibly be reused close to as-is if `window.engine` (and enough of the others) behave the same from its point of view.

## The engine-as-subprocess contract itself needs replacing, regardless of phase

`src/engineAdapter.mjs` — the JS-side implementation behind `window.engine` — does not talk to a library today. It writes the model to a real temp file (`encodeProjectFile` + `writeFile` into a `mkdtemp(tmpdir())` directory), `spawn()`s the `konjugateEngine` binary as a child process with CLI arguments, and reads its result back from another real file on disk. Every engine operation (`validate`, `run`, `infer`, `fit`) goes through this same spawn-and-file-exchange contract. None of `spawn`, `node:fs`, or `node:os`'s `tmpdir()` exist in a browser. This is true regardless of which phase below is in progress — even the simplest equation-only build needs a **parallel implementation of `engineAdapter.mjs`'s entire contract**, calling into an in-memory Emscripten module (buffers/virtual-FS in, buffers out) instead of a real subprocess and real files.

## Two genuinely different classes of "missing native code" — worth not conflating

It's tempting to treat "programmable providers" and "FMU import" as the same problem (both currently involve native code the browser can't run) with the same fix (get a compiler running in-browser). They aren't the same problem:

### Programmable providers: solvable later, via an in-browser toolchain

A programmable source term or relationship is **our own source code**, authored inside Konjugate, compiled fresh at validate/run time (`engine/src/cppToolchain.cpp` invokes a real compiler via `CreateProcessA`/`fork`+`exec`; `engine/src/providerRuntime.cpp` then spawns the compiled result as a separate process). Since the *source* is always available, an in-browser toolchain that compiles it to WASM instead of a native binary is a real, if substantial, path:

- **Python providers**: [Pyodide](https://pyodide.org) (CPython compiled to WASM, mature, used in production elsewhere — e.g. JupyterLite) is a well-trodden route. This is the lower-risk half of "bring compilers back."
- **C++ providers**: a WASM-hosted C++ toolchain (clang/LLVM compiled to WASM, following the general shape of projects like `wasm-clang`) is real but considerably heavier — large toolchain payloads, slower in-browser compiles, and a less mature ecosystem than Pyodide's. This should be scoped and de-risked as its own dedicated phase, not assumed to fall out of "we already have Pyodide working."

Either way, once a provider's compiled output is a WASM module rather than a native binary/process, `providerRuntime.cpp`'s pipe/shared-memory transport also needs a browser-appropriate replacement (direct in-process calls into the WASM module, most likely) — a real design task, but a bounded one.

### FMU import: harder even long-term, for a different reason

FMI import (`engine/include/konjugate/fmiDynamicLoad.hpp`, `engine/src/fmiImport.cpp`) `dlopen`s a real compiled shared library bundled inside a `.fmu` package — but critically, **that shared library was compiled by a third party, and Konjugate never has its source.** An in-browser compiler doesn't help here at all; there's nothing to (re)compile. Realistic long-term options, none of them free:

- Require the FMU author to have shipped a WASM-targeted binary inside the package — not how FMI tooling works today, and not something Konjugate can retroactively fix for existing FMUs in the wild.
- An optional local companion process the web app can connect to for FMU-specific work only (the one place this document countenances "not purely static/client-side," and only for this one feature) — plausible, but a real piece of infrastructure and a security-model question (a web page talking to a local process) worth its own design pass, not a footnote here.
- Accept FMU import as the one feature that stays desktop-only even at "near parity," and say so plainly rather than imply it's coming.

Which of these (or something else) is worth pursuing is an open question below, not a decision made by this document.

## Parallel execution and METIS

The `threadPool`/`partitioned` execution backends (`engine/src/partitionRuntime.cpp`) and the optional METIS graph-partitioning dependency (`engine/CMakeLists.txt`'s `KONJUGATE_ENABLE_METIS`) parallelize execution across real OS threads/processes. The browser path is WASM threads via `SharedArrayBuffer`, which requires the page to be served with `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` response headers. **GitHub Pages cannot set custom response headers at all** — the common workaround is a service worker that injects those headers itself (the `coi-serviceworker` pattern), which works but is real infrastructure, not a hosting-config toggle. Given the long-term ambition here (not just a v1 static page), the hosting choice deserves an explicit decision rather than defaulting to GitHub Pages by inertia — Netlify/Cloudflare Pages/Vercel support custom headers natively and would sidestep this entirely.

## The Electron shell itself has no browser equivalent

`src/main.mjs` owns native file/save dialogs, real `.kjt` file I/O (including the scrypt-based encryption path), the auto-updater, and process lifecycle (multi-window management, macOS-specific behavior). A web build needs its own answers for at least: project storage (File System Access API where available, IndexedDB as a fallback), encryption (Web Crypto's PBKDF2/AES in place of the current Node `scrypt`-based scheme — a different KDF, so an existing encrypted `.kjt` file needs an explicit compatibility decision, not a silent assumption either way), and multi-window/auto-update, which have no obvious browser equivalent at all and may simply not exist in this edition.

## Proposed phased roadmap toward parity

1. **Spike, no UI. Done.** The full `konjugateEngine` target -- not a cut-down equation-only slice, everything including the provider/FMI code -- builds and runs correctly under `wasm32-emscripten` with **zero source changes** to any existing file, via `npm run setup:web` + `npm run build:web` (see [Development setup](../developmentSetup.md#web-build-experimental)). Three real, non-obvious things were needed, all now captured in `engine/CMakeLists.txt`'s own `if(EMSCRIPTEN)` block:
   - **`-fexceptions`**: Emscripten disables C++ exceptions by default; this codebase genuinely relies on them as control flow (e.g. `executionPlan.cpp`'s `compileExpression` -- try parsing a literal number, catch means it's a symbol). Without it, a caught exception calls `abort()` instead of unwinding. This is a compile flag, not just a link flag, so it forces a full rebuild if added after the fact.
   - **`-sSTACK_SIZE=8388608`**: Emscripten's default stack (64KB) is far smaller than a native thread's and overflows immediately on this codebase's recursive JSON/expression parsing.
   - **`-sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORTED_RUNTIME_METHODS=FS,callMain -sINVOKE_RUN=0`**: makes the output a reusable ES module (`createKonjugateEngine()`) with its virtual filesystem and `main()` entry point exposed for a caller to drive explicitly, instead of an auto-running script. An earlier pass at this used `-sNODERAWFS=1` (real host filesystem passthrough) instead, since it made smoke-testing from a terminal simpler -- but that flag is Node-only and would not have loaded in a browser at all, which only surfaced once step 1 was actually re-verified in a real Chromium renderer rather than just Node. `Module.FS`/`Module.callMain` works identically in both, so there is now exactly one build shape instead of a Node-only one and a browser one.

   One new file was needed, not a source change: `engine/src/wasmPosixStubs.cpp` provides always-fail stand-ins for `sem_open`/`sem_close`/`sem_unlink` (POSIX named semaphores), the *only* undefined symbols at link time across the entire codebase -- Emscripten's libc already implements real (if sandboxed) `fork()`, `dlopen()`, `shm_open()`, and `mmap()`, everything else `providerRuntime.cpp`'s shared-memory provider transport needs. Nothing reachable from `validate`/`run` on an equation-only model calls them; if they're ever actually invoked (a provider trying to use the `sharedMemoryWorker` transport), failing loudly beats a silent wrong answer. This also means the "programmable providers don't work in the browser" limitation described elsewhere in this document is enforced by this stub failing loudly at the one remaining call path, not by excluding the code -- the full binary, unmodified, is what ships.
2. **Browser-side `window.engine`. Done for the one-shot operations.** `src/webEngineAdapter.mjs` implements `capabilities`, `validate`, `run`, `infer`, and `fit` -- every operation in `engineAdapter.mjs` that is naturally a single call in, single result out. Same shape throughout: instantiate the module from phase 1 once (reused across calls, not re-instantiated -- re-parsing a ~49MB `.wasm` every call would be real, avoidable cost), write input(s) into a fresh scratch directory in the module's own virtual filesystem, `callMain([...])` with the exact argv the desktop CLI documents (`docs/engineCli.md`), read output(s) back, clean up. Verified byte-for-byte identical results to the desktop CLI, in both Node and a real Chromium renderer, for `capabilities`+`run` in the browser (`validate`/`infer`/`fit` additionally need `protobufjs` loadable there -- see the status note above) and all five in Node.

   Two things explicitly NOT attempted here, both flagged rather than silently missing:
   - **`startEngineRun`'s live/streaming run** (`onUpdate`/pacing/cancel/live-parameter-control). `callMain()` blocks the calling thread until `main()` returns, so a live-updating run needs a Worker-based design to keep the page responsive while a simulation executes -- a separate, harder problem, not started.
   - **`checkSubstepConvergenceWithEngine`**. Its underlying `checkSubstepConvergence()` (`postRunStabilityDiagnostics.mjs`) drives a multi-run substep-doubling search itself, a shape `webEngineAdapter.mjs`'s single-shot helper isn't built for. `checkSubstepConvergenceWithWebEngine()` exists as a stub returning `{ available: false }` rather than being silently absent, but does nothing yet.

   Also out of scope, consistent with the rest of this document: plugin/FMU resolution (no browser equivalent of the local userData directory both read from, and both exist only to support the programmable-provider/FMI features already excluded here) -- a caller passes already-resolved project content. Encryption is not supported either; `webEngineAdapter.mjs`'s own `.kjt` encoder covers only the plain, unencrypted, gzip-only, no-embedded-result case.
3. **Minimal shell. Done.** `src/renderer/webShims/*` implements every `window.*` global `src/preload.mjs` exposes, against the unmodified `renderer.mjs`, served via `npm run build:webShell` + `npm run serve:webShell`. Run is a batch fallback (the whole simulation runs in a Worker, then plays back as a completed result -- no live progress or mid-run control); project save/load covers unencrypted `.kjt` via drag-drop and the File System Access API; bundled shape/component/example libraries are real; anything genuinely desktop-only is an honest `{available: false}` surfaced by a dismissible in-page banner, not a silently broken button. See the status note above for the full detail and the two scope decisions behind it. Not yet done: actually deploying this anywhere (this phase only produces `out/webShell/`, served locally) -- see the "hosting provider" decision below, and the open question on where this build should live relative to the main repo.
4. **Python providers via Pyodide.**
5. **C++ providers via a WASM toolchain** — its own dedicated design/spike, given the risk noted above.
6. **Parallel execution backends**, once a hosting decision that supports `SharedArrayBuffer` is made (see above).
7. **FMU import** — pending the open question below; may end up out of scope permanently rather than merely deferred.

Each phase is a real go/no-go checkpoint. Nothing here commits to a timeline — the point is ordering the work by genuine dependency and risk, not by assumed effort.

## Open questions

- **FMU import's long-term fate** — accept it as permanently desktop-only, or invest in a companion-process design? This is the one place this whole document doesn't have a clean answer.
- ~~**Hosting provider**~~ **Decided: GitHub Pages, revisited only at phase 6.** Nothing before phase 6 (parallel execution backends) needs `SharedArrayBuffer`, so there's no reason to take on a service-worker COOP/COEP shim -- or reconsider Netlify/Cloudflare Pages -- before that phase is actually in scope. Revisit this decision if and when phase 6 starts, not before.
- **Encrypted-project compatibility** across the Node-`scrypt` vs. Web-Crypto boundary.
- **Where this build lives relative to the main repo** — a build target in this repo, or a separate package/branch? Affects how much of the phased work risks bit-rotting against ongoing desktop-app changes as phases 4-7 stretch out over time.
