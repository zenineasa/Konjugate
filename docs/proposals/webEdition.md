# Konjugate Web: a browser edition, not a permanent preview

**Status: proposal. Phases 1-4, 6 and 7 of the roadmap below are done; phase 5's feasibility spike found a real, promising path but not yet a working compile (see its own entry).** This document captures the brainstorm that produced the scoping decisions below, grounded in the actual current code (not assumptions about it), so an implementation attempt starts from a realistic picture rather than "compile the engine to WASM and it should mostly work." Phase 1 (see "Proposed phased roadmap" below) is now real: `npm run build:web` (`engine/CMakePresets.json`'s `web` preset) builds the complete, unmodified `konjugateEngine` binary for `wasm32-emscripten` -- not just an equation-only slice, the actual full engine including `cppToolchain.cpp`/`fmiImport.cpp`/`providerRuntime.cpp` -- as a reusable ES module (`Module.FS.writeFile`/`Module.callMain`/`Module.FS.readFile`, mirroring the real CLI contract exactly; see [Development setup](../developmentSetup.md#web-build-experimental)). Verified to produce byte-for-byte-correct protobuf output, decodable by the real, unmodified `src/engineProtocol.mjs`, in **two** environments: plain Node, and a real Chromium renderer (an Electron `BrowserWindow`, driven the same way `tests/interactionRunner.mjs` drives the desktop app's own UI) -- deliberately not just Node, since a real browser has no filesystem passthrough to lean on and an early version of this spike that worked under Node (via `-sNODERAWFS=1`, a Node-only flag) would not have loaded in a browser at all.

Phase 2 (`src/webEngineAdapter.mjs`) is also real, for the one-shot operations only (`capabilities`, `validate`, `run`, `infer`, `fit`) -- see that phase's own entry below for exactly what's covered and what isn't. Building and testing it in a real browser surfaced two further real gaps, both fixed, not routed around:

- `src/engineProtocol.mjs` -- the shared decoder every result/event ultimately goes through, used throughout the desktop app too, not just this adapter -- turned out to depend on Node's `Buffer` (`.equals()`, `.readDoubleLE()`, `Buffer.concat`, etc.) despite its own header comment already claiming to be renderer-safe. That claim held by accident: Electron's renderer happens to polyfill a minimal `Buffer` global even under `contextIsolation`, but a real standalone browser tab has none at all. Now rewritten Buffer-free (`Uint8Array`/`DataView`/`TextDecoder` only) -- verified against the full existing test suite (which covers this file already) plus this phase's own real-browser test, with zero behavior change for every existing caller (`Buffer` already *is* a `Uint8Array`, so nothing downstream needed to change).
- `src/reportProtocol.mjs`'s `protobufjs/minimal.js` dependency is CommonJS (`module.exports`/`require`), loadable via Node's own CJS/ESM interop but not by a browser at all without either an import map pointing the bare specifier at a browser build, or a bundler -- real, separate infrastructure work matching phase 3 below, not a phase 2 problem. `webEngineAdapter.mjs` now imports it lazily (only inside `validate`/`infer`/`fit`, dynamically, not at module top level) specifically so a page that only calls `run()`/`capabilities()` never pays for a problem that isn't theirs -- confirmed by testing the failure directly in a real renderer before fixing it: a static top-level import broke the whole module, including the parts that don't need it at all.

Phase 3 (`src/renderer/webShims/*`, `scripts/buildWebShell.mjs`/`serveWebShell.mjs`) is also real: `npm run build:webShell && npm run serve:webShell` serves the actual, unmodified `src/renderer/renderer.mjs` -- same file the desktop app loads, zero source changes -- against browser-native replacements for every `window.*` global `src/preload.mjs` normally injects. This closed the `protobufjs/minimal.js` gap above too: `index.html`'s importmap now maps that bare specifier at a tiny shim (`webShims/protobufjsMinimalShim.mjs`) exposing a classic-script-loaded, pre-bundled browser build of protobufjs's minimal runtime -- verified end-to-end in a real Chromium renderer (`validate()` against a bundled example decodes a real protobuf report correctly). Two scope decisions, both made deliberately rather than discovered as gaps partway through:
- **Run is a batch fallback, not live -- but the actual blocker turned out narrower than "Worker + Asyncify" suggested, and the key piece of it is now confirmed working.** `renderer.mjs`'s Run button always calls the live/streaming `window.engine.start(...)`. Instead, `src/webEngineWorker.mjs` runs the existing one-shot `runWithWebEngine()` off the main thread, and `src/webEngineLiveShim.mjs` presents that single result through the exact same job/onComplete/readResultSeries/readResultSample/releaseResult contract a real live job uses (verified against `src/main.mjs`'s actual handlers and `src/resultSession.mjs`, which both this shim and those handlers import -- confirmed already renderer-safe). Verified end-to-end in a real renderer: `window.engine.start()` returns a jobId immediately, `onComplete` fires with a full result, `readResultSeries`/`readResultSample`/`releaseResult` all work against it. No progressive live plotting, no pause/cancel/live-parameter-tweak mid-run -- `setPacing`/`setExecutionState`/`setParameterValue` reject with a clear message instead of silently no-op'ing. **Follow-up research narrowed the real gap**: `engine/src/simulationRunner.cpp`'s own control-stream handling is already a non-blocking poll against a background reader thread, applying a decoded command via one direct struct mutation the very next step -- no engine changes needed there at all. The only actual blocker is getting bytes into stdin from JS while `Module.callMain()` blocks the Worker synchronously. A standalone spike (a minimal Emscripten pthread program, `-pthread`, matching the phase-6 `web-threads` build) confirmed directly, in Node, that this works: a background pthread's blocking stdin read genuinely blocks via `Atomics.wait` on a `SharedArrayBuffer`, the real JS main thread stays completely free to run its own timers/events throughout, and `Atomics.notify()` from that free main thread correctly and promptly unblocks the read with the right byte -- exactly the mechanism a live command channel needs. Not yet built: the actual `webEngineLiveRunWorker.mjs` wiring this into `encodeEngineCommand`/`FramedEngineEventDecoder` (both already portable, `src/engineProtocol.mjs`) for the `web-threads` variant specifically -- the default non-threaded `web` build keeps the batch fallback regardless, since it has no pthread stdin channel to use. **A second, separate open question surfaced while scoping that build-out, not yet spiked**: the desktop CLI's `--event-stream protobuf` writes raw binary framed messages directly to `std::cout` (`writeFramedMessage`, `engine/src/main.cpp`) -- Emscripten's `Module.print` callback (already used for the batch adapter's plain-text `capabilities` output) is line-buffered and text-only, and would corrupt binary event data containing embedded newline bytes or non-UTF8 sequences. Getting live events out safely likely needs a custom binary-capable stdout device (`FS.createDevice`, replacing Emscripten's default TTY-backed stdout) rather than `Module.print`, unverified so far -- the same "confirm it directly, don't assume" treatment the stdin question already got, not yet given.
- **Project save/load: unencrypted and encrypted `.kjt` both work now, with real desktop interoperability.** `src/browserProjectCodec.mjs` adds a browser-native decoder (`DecompressionStream`-based) alongside phase 2's existing encoder, plus real encryption support using the exact same scheme `src/projectFile.mjs` uses on desktop -- scrypt (via the vendored `scrypt-js`, since Web Crypto has no scrypt at all -- confirmed against the actual spec, not assumed) for the KDF, AES-256-GCM (natively via `SubtleCrypto`) for the cipher, same container header fields. Verified end-to-end, bidirectionally, in a real renderer: a project encrypted by desktop's Node-based `projectFile.mjs` decrypts correctly in the browser with the right password (and is correctly rejected with the wrong one), and a project encrypted in the browser decrypts correctly back through `projectFile.mjs` on the Node side -- real interoperability, not two incompatible encrypted-file populations (a PBKDF2-only approach would have created exactly that). Drag-drop and File System Access API (`showOpenFilePicker`/`showSaveFilePicker`, falling back to `<input type=file>`/download-blob where unsupported) both reuse `renderer.mjs`'s own real `openProject()`/`saveProject()` flow (including its unsaved-changes confirmation and its existing password-retry loop for `requiresPassword`) with zero changes to that file -- drag-drop stashes the dropped bytes and clicks the toolbar's real `#loadButton`, rather than forking or reimplementing `loadOpenedProjectFile()`.

Every other `window.*` global (`shapeLibrary`, `componentLibrary`, `examples`) that's backed by bundled, static content works for real, served as static files -- `examples`' and `componentLibrary`'s bundled listings are generated at build time by `buildWebShell.mjs` (mirrors `src/main.mjs`'s own directory-scan logic, since a browser can't scan a directory itself). Everything genuinely desktop-only at the time (`windowControls`, `providerEditor`, `providerToolchains`, `extensions` install/uninstall, `addons`, `aiProviders`, FMU export/merge) was an honest `{available: false}` (or a no-op, where that's accurate) rather than a silent stub -- a dismissible in-page banner lists these plainly rather than leaving them to be discovered as broken buttons (`providerEditor`/`providerToolchains` moved out of that stub set in phase 4, below). Real-browser (Electron `BrowserWindow`) testing surfaced one further gap, fixed at the root: the importmap's own inline script content changed (the new `protobufjs/minimal.js` entry), which silently invalidated `index.html`'s CSP `sha256-...` hash for it -- `buildWebShell.mjs` now recomputes that hash from what's actually served, rather than carrying the desktop's original one forward.

Phase 4 (Python providers via Pyodide) is also real: `engine/src/providerRuntime.cpp` gained a `WasmPyodideProviderBackend` (additive, `#ifdef __EMSCRIPTEN__` only -- the native desktop transport is untouched) that calls a JS-side Pyodide bridge (`src/webPythonProviderBridge.mjs`) synchronously via Emscripten's `EM_JS`, in place of the native build's `fork()`+pipe+protobuf transport, which has no meaning inside a browser tab. `engine/sdk/python/konjugate/__main__.py` was refactored (extract-function only, zero behavior change, verified against the existing CTest suite) so its per-message handlers are callable directly by a new `_webBridge.py`, reused unchanged rather than reimplemented. A minimal in-page provider editor (`src/renderer/webShims/providerEditor.mjs`, a `<dialog>` with a plain textarea and a Pyodide-backed "Validate" syntax check -- no live-as-you-type checking or syntax highlighting, deliberately deferred) satisfies `renderer.mjs`'s real `window.providerEditor` call sites with zero changes to that file, matching every earlier phase's precedent. `providerToolchains`'s Python branch now reports honestly that Pyodide is bundled (nothing to locate or browse to); its C++ branch is unchanged (`{available: false}`, phase 5's concern). Verified end-to-end in a real Chromium renderer: `validate()` on a Python-provider model does not load Pyodide at all (it never executes providers); `run()` does, correctly executing a real computational-node provider (a PI controller) and producing results matching the native CLI. One real bug caught before it shipped: `boost::property_tree`'s JSON writer quotes every value as a string with no numeric type of its own -- `_webBridge.py` tolerates numeric fields arriving as either JSON numbers or numeric strings rather than assuming either convention.

Phase 6 (parallel execution backends) is also real. Two research-then-verify findings changed the shape of the work from what "Parallel execution and METIS" below originally assumed:
- **METIS was already building for `wasm32-emscripten`** -- it only looked unavailable because the `web` preset inherited `development-no-metis`. Flipping `KONJUGATE_ENABLE_METIS`/`KONJUGATE_REQUIRE_METIS` back on for `web` (`engine/CMakePresets.json`) was the whole fix, no vcpkg work needed.
- `threadPool`/`partitioned` (`engine/include/executionBackend.hpp`) are real `std::thread` pools (`engine/include/taskExecutor.hpp`), not OS process forking -- so Emscripten's pthread support is a direct fit, not a redesign. A new `web-threads` preset and overlay vcpkg triplet (`vcpkgOverlays/triplets/wasm32-emscripten-threads.cmake` -- a real, git-tracked overlay, since the plain `wasm32-emscripten` triplet ships with vcpkg itself inside the gitignored `.tools/vcpkg` and can't be edited in place) add `-pthread` for the engine and every dependency it links against, entirely separate from the default `web` build.

A real, currently-live bug was caught and fixed along the way, independent of the threads preset: nothing previously stopped a run configuration from requesting `threadPool`/`partitioned` against the *default, non-pthread* web build, which would abort rather than fail cleanly. `engine/src/simulationRunner.cpp` now clamps this under `#if defined(__EMSCRIPTEN__) && !defined(__EMSCRIPTEN_PTHREADS__)`: an explicit request throws a clear, catchable error; an automatic selection quietly downgrades to `serial` -- mirroring the exact same fail-loud-vs-quietly-downgrade convention the code already used for node providers on the `partitioned` backend.

Testing the `web-threads` preset in a real Chromium renderer surfaced two more real bugs, both fixed: a pthread build's linear memory is a growable `SharedArrayBuffer`, which (unlike ordinary memory growth) needs its ceiling reserved up front -- `threadPool` aborted with a genuine out-of-memory error at Emscripten's default 16MB until `-sALLOW_MEMORY_GROWTH=1 -sMAXIMUM_MEMORY=1GB` were added. `partitioned` failed too, but with a misleading "pthread mutex deadlock detected" assertion instead of the same OOM message -- initially suspected to mean `-sPROXY_TO_PTHREAD=1` was needed (Emscripten's blocking-synchronization-on-the-module's-own-main-thread restriction, which the original design note below worried about), but the same memory fix resolved it too; the assertion was a confusing secondary symptom of the same root cause, not a separate architectural gap. Verified end-to-end: `serial`, `threadPool` (8 workers), and `partitioned` (7 workers) all produce byte-for-byte identical results on a 9-node example, with `threadPool`/`partitioned` roughly 8-10x faster than `serial` for that model.

**Hosting**: the default `web`/`webShell` build stays fine on GitHub Pages (unaffected by any of this). The `web-threads`/`webShellThreads` variant needs `SharedArrayBuffer`, which needs `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` response headers GitHub Pages cannot send -- **recommended: a COOP/COEP-capable host (Netlify/Cloudflare Pages) for that variant specifically**, rather than a service-worker shim on GitHub Pages, since a shim is real, fragile infrastructure for a problem a header-capable host solves for free. `scripts/serveWebShell.mjs` sends these headers unconditionally for local testing regardless of which variant it's serving. Actually standing up that hosting is separate "ship it" work, not attempted here (nothing in this project has been deployed anywhere yet).

Phase 7 (FMU import's long-term fate) is decided: permanently desktop-only. See "FMU import: harder even long-term" below for the reasoning.

Phase 5 (C++ providers via a WASM toolchain) had its feasibility spike -- **real, promising progress, but not yet a working pipeline.** [`@wasmer/sdk`](https://www.npmjs.com/package/@wasmer/sdk) (actively maintained, published days before this was written) can fetch and run a genuine, current clang 16 + lld + wasm-ld toolchain (`clang/clang@0.160000.1` off Wasmer's package registry) directly from JS, confirmed by real compiler version/diagnostic output in a hands-on test -- a materially better-maintained option than the ~2018-era demo projects (`wasm-clang`, `browsercc`) found by search alone. It compiles to `wasm32-unknown-wasi` by default (confirmed by its own linker-flag defaults), **not** Emscripten's own module format -- so the realistic target design is the one this document already anticipated: a separately-instantiated WASM module called across a JS-mediated bridge shaped like `WasmPyodideProviderBackend`'s (`EM_JS` + a `Module`-level hook), dispatching through `providerInProcessAbi.hpp`'s vtable fields, **not** true `dlopen()` into an `-sMAIN_MODULE` engine build.

**The original filesystem blocker above is now understood, with high confidence, though not yet confirmed by an actual successful compile.** Wasmer's own official example (`https://wasmer.io/posts/clang-in-browser`) and the current SDK's own README both show the missing piece directly: files supplied via `SandboxOptions.files`/written through `sandbox.fs` are mounted under a fixed `/workspace/` prefix, and a spawned command's own `argv` strings are **not** rewritten to account for that -- only `sandbox.fs`'s own API resolves paths against it transparently. The prior session's test referenced its seeded file as `/src.c` in both places, so `sandbox.fs.readFile('/src.c')` succeeded (silently resolving against `/workspace/`) while `clang-16 /src.c`'s own argv, passed straight through unmodified, looked for a literal `/src.c` that never existed. The fix is almost certainly passing `/workspace/`-prefixed paths in compiler arguments, matching every path already written via `files`/`sandbox.fs`.

That fix is unverified end-to-end, for a reason specific to *this session's own sandboxed test environment*, not the SDK or the mount theory: `@wasmer/sdk` fetches toolchain images from `cdn.wasmer.io`, and this environment throttles large downloads there severely -- a direct `curl` measurement got ~9 KB/s against a 150 MB package (clang and Python's images are both this large), which would take hours, versus ~460 KB/s against a 1.5 MB package fetched moments later from the same host. That reads as a deliberate large-download policy on this sandbox, not a real bandwidth ceiling a deployed web page's actual visitors would hit -- but it meant neither the original clang toolchain nor a small substitute package (tried specifically to re-test the mount fix cheaply) could be fetched here to confirm the fix directly: the smallest available substitute (`sharrattj/coreutils`, ~1.5 MB, downloaded fine) hit a *different*, genuine SDK bug instead -- its `.webc` image is zstd-encoded, and `@wasmer/sdk`'s own WASM-compiled core (used even via its `/node` entrypoint -- the whole SDK runs as WASM regardless of host, per its own README) cannot decode zstd content-encoding at all ("zstd content-encoding is not supported on wasm32"), a real, separate limitation worth knowing about when picking a toolchain package to depend on later, independent of this phase's own blocker.

Next step for whoever picks this back up: retry the `/workspace/`-prefixed compile in an environment without this sandbox's large-download throttling (a real browser tab is the actual target anyway, not this test harness) before assuming further architectural work is needed -- the remaining gap looks like a network/environment constraint on verification, not on the design.

**Not attempted, correctly, given the above**: any engine-side ABI bridge, `providerToolchains`'/`providerEditor`'s C++ branches, or asset-size/UX planning -- all real, separate work that only makes sense once an actual compile succeeds end to end.

## Ambition

The inspiration is [vscode.dev](https://vscode.dev): Visual Studio Code running in a browser, reachable with no install. **The long-term goal is near feature parity with the desktop app, not a permanently smaller "preview" product.** Compilers (and therefore programmable C++/Python providers) won't be available in the first working version — that's a real, structural gap on day one — but it is a gap with a genuine path to closing, not a wall. This document treats compiler availability as the thing that arrives in a *later phase*, not as a reason to scope the whole effort down to "equation-only, forever." The one piece that stays genuinely harder even long-term is FMU import, for reasons specific to what an FMU actually is — see below.

## What already ports cleanly

The numeric core has no OS-specific dependencies at all. `Eigen`, `boost::property_tree`, the protobuf runtime, the Explicit Euler solver, expression evaluation (`executionPlan.cpp`'s `CompiledExpression::evaluate`), and the entire numerical-stability-diagnostics engine (`stabilityAnalysis.cpp`, `modelValidator.cpp`) are all pure, portable C++. Emscripten handles this class of code well.

There's a second, more structural piece of good news: **the renderer already talks to everything through a small, named set of browser-global seams, never directly to Node.** `src/preload.mjs` exposes `window.engine`, `window.projectFiles`, `window.shapeLibrary`, `window.componentLibrary`, `window.providerEditor`, `window.providerToolchains`, `window.modelClipboard`, `window.extensions`, `window.addons`, `window.aiProviders`, and a few more — fourteen `contextBridge.exposeInMainWorld` calls in total — each backed today by an `ipcRenderer.invoke` call into `src/main.mjs`. `src/renderer/renderer.mjs` itself has zero direct `node:*` imports (`contextIsolation: true`, `nodeIntegration: false` — this is already enforced, not just a convention). That means a web build's real task is **reimplementing what sits behind each of those fourteen globals**, not rewriting the renderer. A large fraction of `renderer.mjs` — model editing, the Three.js canvas, the equation editor, causal inference, digital-twin tuning UI — could plausibly be reused close to as-is if `window.engine` (and enough of the others) behave the same from its point of view.

## The engine-as-subprocess contract itself needs replacing, regardless of phase

`src/engineAdapter.mjs` — the JS-side implementation behind `window.engine` — does not talk to a library today. It writes the model to a real temp file (`encodeProjectFile` + `writeFile` into a `mkdtemp(tmpdir())` directory), `spawn()`s the `konjugateEngine` binary as a child process with CLI arguments, and reads its result back from another real file on disk. Every engine operation (`validate`, `run`, `infer`, `fit`) goes through this same spawn-and-file-exchange contract. None of `spawn`, `node:fs`, or `node:os`'s `tmpdir()` exist in a browser. This is true regardless of which phase below is in progress — even the simplest equation-only build needs a **parallel implementation of `engineAdapter.mjs`'s entire contract**, calling into an in-memory Emscripten module (buffers/virtual-FS in, buffers out) instead of a real subprocess and real files.

## Two genuinely different classes of "missing native code" — worth not conflating

It's tempting to treat "programmable providers" and "FMU import" as the same problem (both currently involve native code the browser can't run) with the same fix (get a compiler running in-browser). They aren't the same problem:

### Programmable providers: solvable later, via an in-browser toolchain

A programmable source term or relationship is **our own source code**, authored inside Konjugate, compiled fresh at validate/run time (`engine/src/cppToolchain.cpp` invokes a real compiler via `CreateProcessA`/`fork`+`exec`; `engine/src/providerRuntime.cpp` then spawns the compiled result as a separate process). Since the *source* is always available, an in-browser toolchain that compiles it to WASM instead of a native binary is a real, if substantial, path:

- **Python providers**: [Pyodide](https://pyodide.org) (CPython compiled to WASM, mature, used in production elsewhere — e.g. JupyterLite) is a well-trodden route. This is the lower-risk half of "bring compilers back."
- **C++ providers**: a WASM-hosted C++ toolchain (clang/LLVM compiled to WASM, following the general shape of projects like `wasm-clang`) is real but considerably heavier — large toolchain payloads, slower in-browser compiles, and a less mature ecosystem than Pyodide's. This should be scoped and de-risked as its own dedicated phase, not assumed to fall out of "we already have Pyodide working."

Either way, once a provider's compiled output is a WASM module rather than a native binary/process, `providerRuntime.cpp`'s pipe/shared-memory transport also needs a browser-appropriate replacement (direct in-process calls into the WASM module, most likely) — a real design task, but a bounded one.

### FMU import: harder even long-term, for a different reason

FMI import (`engine/include/konjugate/fmiDynamicLoad.hpp`, `engine/src/fmiImport.cpp`) `dlopen`s a real compiled shared library bundled inside a `.fmu` package — but critically, **that shared library was compiled by a third party, and Konjugate never has its source.** An in-browser compiler doesn't help here at all — not even phase 5's, however it turns out — since there's nothing to (re)compile. Considered options:

- Require the FMU author to have shipped a WASM-targeted binary inside the package — not how FMI tooling works today, and not something Konjugate can retroactively fix for existing FMUs in the wild.
- An optional local companion process the web app can connect to for FMU-specific work only (the one place this document would have countenanced "not purely static/client-side," and only for this one feature) — architecturally plausible, but real, separate infrastructure (process lifecycle, a transport, a security-model question — a web page talking to a local process) that would need its own dedicated design pass to justify, with no demonstrated need for it yet.
- Accept FMU import as the one feature that stays desktop-only even at "near parity," and say so plainly rather than imply it's coming.

**Decided: accept FMU import as permanently desktop-only in the web edition.** The companion-process option stays architecturally possible and isn't ruled out forever, but it's speculative infrastructure with no concrete demand behind it today — worth building if and when an actual need for browser-side FMU import shows up, not ahead of one. This is the one piece of "near parity" the web edition doesn't aim for.

## Parallel execution and METIS

**Done — see the status note above for the full detail.** The `threadPool`/`partitioned` execution backends (`engine/src/partitionRuntime.cpp`) parallelize execution across real `std::thread`s (not OS processes, confirmed by direct inspection — a better fit for Emscripten's WASM-threads support than originally assumed below), and METIS graph partitioning (`engine/CMakeLists.txt`'s `KONJUGATE_ENABLE_METIS`) was already building for `wasm32-emscripten`, just disabled by preset inheritance. The browser path is WASM threads via `SharedArrayBuffer`, which requires the page to be served with `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` response headers. **GitHub Pages cannot set custom response headers at all** — the common workaround is a service worker that injects those headers itself (the `coi-serviceworker` pattern), which works but is real infrastructure, not a hosting-config toggle. **Decided: a COOP/COEP-capable host (Netlify/Cloudflare Pages) for the pthread-enabled `web-threads` build specifically**, rather than a shim — the default non-threaded build stays on GitHub Pages, unaffected.

## The Electron shell itself has no browser equivalent

`src/main.mjs` owns native file/save dialogs, real `.kjt` file I/O (including the scrypt-based encryption path), the auto-updater, and process lifecycle (multi-window management, macOS-specific behavior). A web build needs its own answers for at least: project storage (File System Access API where available, IndexedDB as a fallback) and multi-window/auto-update, which have no obvious browser equivalent at all and may simply not exist in this edition. Encryption is done: `src/browserProjectCodec.mjs` uses the vendored `scrypt-js` for the KDF (Web Crypto has no scrypt) plus native `SubtleCrypto` AES-256-GCM, matching `projectFile.mjs`'s scheme exactly rather than substituting Web Crypto's native (but structurally different) PBKDF2 -- see the phase-3 status note for the interoperability verification.

## Proposed phased roadmap toward parity

1. **Spike, no UI. Done.** The full `konjugateEngine` target -- not a cut-down equation-only slice, everything including the provider/FMI code -- builds and runs correctly under `wasm32-emscripten` with **zero source changes** to any existing file, via `npm run setup:web` + `npm run build:web` (see [Development setup](../developmentSetup.md#web-build-experimental)). Three real, non-obvious things were needed, all now captured in `engine/CMakeLists.txt`'s own `if(EMSCRIPTEN)` block:
   - **`-fexceptions`**: Emscripten disables C++ exceptions by default; this codebase genuinely relies on them as control flow (e.g. `executionPlan.cpp`'s `compileExpression` -- try parsing a literal number, catch means it's a symbol). Without it, a caught exception calls `abort()` instead of unwinding. This is a compile flag, not just a link flag, so it forces a full rebuild if added after the fact.
   - **`-sSTACK_SIZE=8388608`**: Emscripten's default stack (64KB) is far smaller than a native thread's and overflows immediately on this codebase's recursive JSON/expression parsing.
   - **`-sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORTED_RUNTIME_METHODS=FS,callMain -sINVOKE_RUN=0`**: makes the output a reusable ES module (`createKonjugateEngine()`) with its virtual filesystem and `main()` entry point exposed for a caller to drive explicitly, instead of an auto-running script. An earlier pass at this used `-sNODERAWFS=1` (real host filesystem passthrough) instead, since it made smoke-testing from a terminal simpler -- but that flag is Node-only and would not have loaded in a browser at all, which only surfaced once step 1 was actually re-verified in a real Chromium renderer rather than just Node. `Module.FS`/`Module.callMain` works identically in both, so there is now exactly one build shape instead of a Node-only one and a browser one.

   One new file was needed, not a source change: `engine/src/wasmPosixStubs.cpp` provides always-fail stand-ins for `sem_open`/`sem_close`/`sem_unlink` (POSIX named semaphores), the *only* undefined symbols at link time across the entire codebase -- Emscripten's libc already implements real (if sandboxed) `fork()`, `dlopen()`, `shm_open()`, and `mmap()`, everything else `providerRuntime.cpp`'s shared-memory provider transport needs. Nothing reachable from `validate`/`run` on an equation-only model calls them; if they're ever actually invoked (a provider trying to use the `sharedMemoryWorker` transport), failing loudly beats a silent wrong answer. This also means the "programmable providers don't work in the browser" limitation described elsewhere in this document is enforced by this stub failing loudly at the one remaining call path, not by excluding the code -- the full binary, unmodified, is what ships.
2. **Browser-side `window.engine`. Done for the one-shot operations.** `src/webEngineAdapter.mjs` implements `capabilities`, `validate`, `run`, `infer`, and `fit` -- every operation in `engineAdapter.mjs` that is naturally a single call in, single result out. Same shape throughout: instantiate the module from phase 1 once (reused across calls, not re-instantiated -- re-parsing a ~49MB `.wasm` every call would be real, avoidable cost), write input(s) into a fresh scratch directory in the module's own virtual filesystem, `callMain([...])` with the exact argv the desktop CLI documents (`docs/engineCli.md`), read output(s) back, clean up. Verified byte-for-byte identical results to the desktop CLI, in both Node and a real Chromium renderer, for `capabilities`+`run` in the browser (`validate`/`infer`/`fit` additionally need `protobufjs` loadable there -- see the status note above) and all five in Node.

   Two things explicitly NOT attempted here, both flagged rather than silently missing:
   - **`startEngineRun`'s live/streaming run** (`onUpdate`/pacing/cancel/live-parameter-control). `callMain()` blocks the calling thread until `main()` returns, so a live-updating run needs a Worker-based design to keep the page responsive while a simulation executes -- a separate, harder problem, not started.
   - **`checkSubstepConvergenceWithEngine`**. Its underlying `checkSubstepConvergence()` (`postRunStabilityDiagnostics.mjs`) drives a multi-run substep-doubling search itself, a shape `webEngineAdapter.mjs`'s single-shot helper isn't built for. `checkSubstepConvergenceWithWebEngine()` exists as a stub returning `{ available: false }` rather than being silently absent, but does nothing yet.

   Also out of scope, consistent with the rest of this document: plugin/FMU resolution (no browser equivalent of the local userData directory both read from, and both exist only to support the programmable-provider/FMI features already excluded here) -- a caller passes already-resolved project content. Encryption is not supported either; `webEngineAdapter.mjs`'s own `.kjt` encoder covers only the plain, unencrypted, gzip-only, no-embedded-result case.
3. **Minimal shell. Done.** `src/renderer/webShims/*` implements every `window.*` global `src/preload.mjs` exposes, against the unmodified `renderer.mjs`, served via `npm run build:webShell` + `npm run serve:webShell`. Run is a batch fallback (the whole simulation runs in a Worker, then plays back as a completed result -- no live progress or mid-run control; see the status note above for a follow-up spike that confirmed the actual remaining blocker); project save/load covers both unencrypted and encrypted `.kjt` (interoperable with desktop -- see the status note above) via drag-drop and the File System Access API; bundled shape/component/example libraries are real; anything genuinely desktop-only is an honest `{available: false}` surfaced by a dismissible in-page banner, not a silently broken button. See the status note above for the full detail and the two scope decisions behind it. Not yet done: actually deploying this anywhere -- `.github/workflows/webEdition.yml` builds and packages `out/webShell/` in CI but deliberately stops short of an actual deploy (see [Development setup](../developmentSetup.md#deployment-build-pipeline-only-not-live-yet)).
4. **Python providers via Pyodide. Done.** `WasmPyodideProviderBackend` (`engine/src/providerRuntime.cpp`, `#ifdef __EMSCRIPTEN__` only) replaces the native fork+pipe+protobuf transport with a synchronous `EM_JS` call into `src/webPythonProviderBridge.mjs`, which loads Pyodide (lazily -- only when a model actually has a Python provider) and calls the *unmodified* `RelationshipProvider`/`NodeProvider` SDK through a thin new JSON adapter (`engine/sdk/python/konjugate/_webBridge.py`) built on `__main__.py`'s own (refactored, behavior-preserving) per-message handlers. A minimal in-page `<dialog>` editor (`webShims/providerEditor.mjs`) covers authoring -- plain textarea, a Pyodide-backed "Validate" syntax check, no live-as-you-type checking or syntax highlighting. See the status note above for full detail. Not attempted: C++ providers (phase 5, unrelated toolchain problem) and computational-node checkpoint/restore's reachability was left unverified for the batch-run web build specifically (the underlying handlers are implemented and unit-tested, matching the native path exactly -- whether anything in the current UI can actually trigger them here is a separate question from whether they work).
5. **C++ providers via a WASM toolchain. Spiked, not delivered.** A real, actively-maintained in-browser clang 16 toolchain exists and is reachable (`@wasmer/sdk`); the filesystem-visibility gap that originally blocked a compile is now understood with high confidence (a documented `/workspace/` mount prefix missing from compiler argv) but not yet confirmed by an actual successful compile, since this session's own sandboxed test environment throttles the toolchain's large package downloads to the point of impracticality -- a verification-environment problem, not a design one. See the status note above for the full detail and the specific next step. Still open, not abandoned.
6. **Parallel execution backends. Done.** A new `web-threads` CMake preset + overlay vcpkg triplet (`vcpkgOverlays/triplets/wasm32-emscripten-threads.cmake`) build the engine with `-pthread`, entirely separate from the default `web` build. `threadPool`/`partitioned` verified correct (identical results to `serial`) and genuinely faster (~8-10x on a 9-node example) in a real Chromium renderer served with COOP/COEP headers (`scripts/serveWebShell.mjs`). The default build now fails clearly instead of aborting if asked for a backend it can't run. See the status note above for the two build-time bugs (memory growth, a misleading pthread assertion) found and fixed while verifying this.
7. **FMU import. Decided: out of scope permanently.** See "FMU import: harder even long-term" above for the reasoning — nothing to (re)compile in-browser regardless of phase 5, and the only real alternative (a local companion process) is speculative infrastructure with no demonstrated need. Accepted as the one feature the web edition doesn't aim for at "near parity," rather than left open indefinitely.

Each phase is a real go/no-go checkpoint. Nothing here commits to a timeline — the point is ordering the work by genuine dependency and risk, not by assumed effort.

## Open questions

- ~~**FMU import's long-term fate**~~ **Decided: permanently desktop-only.** See "FMU import: harder even long-term" above.
- ~~**Hosting provider**~~ **Decided (revisited at phase 6, as planned): GitHub Pages for the default `web`/`webShell` build; a COOP/COEP-capable host (Netlify/Cloudflare Pages) for the pthread-enabled `web-threads`/`webShellThreads` variant specifically**, rather than a service-worker shim on GitHub Pages for everything. - ~~**Where this build lives relative to the main repo**~~ **Decided: stays in this repo.** Everything from phases 1-7 already lives here as clearly-named build targets and source directories alongside the desktop app (`src/renderer/webShims/`, `scripts/buildWebShell.mjs`, `vcpkgOverlays/`, etc.), cleanly separated by naming/placement, with zero desktop-app regressions confirmed after every phase (`npm run dev` unaffected throughout). Splitting it into a separate package/branch now would introduce exactly the sync/drift risk this question worried about, for no concrete benefit over what's already been built and verified in-tree seven phases deep.
