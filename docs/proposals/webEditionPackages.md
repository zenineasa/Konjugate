# Add-ons and plugins in the web edition

**Status: stages 1 to 4 built, and the first eight parts of stage 5, and the rest of stage 3's visualizer permissions** (see "As built" at the end); the later stages are proposals. Before stage 1 the web edition could not install or run packages at all: `window.extensions` and `window.addons` in `src/renderer/webShims/misc.mjs` were stand-ins that returned `{ available: false }` or empty lists. `window.addons` was one until stage 3. This document says what a real implementation needs, which decisions have to be made first, and an order to build it in that gives something useful at each step. It was written from reading the code, not from a prototype, so the estimates are rough and the browser-support claims should be checked when each stage starts.

## What the desktop does, and which parts carry over

An add-on (`.kja`) is the application layer: a result visualizer, or a launcher with importers, scenarios and exports ([Add-on development](../addonDevelopment.md), [Launcher add-ons](launcherAddons.md)). A plugin (`.kjp`) is the numerical layer: relationship providers in Python or C++, and declarative component templates and examples ([Plugin development](../pluginDevelopment.md)). Both are ZIP archives with a shared `package.json` envelope, installed under `<userData>/packages/` after a review of the package's identity and permissions ([Konjugate packages](../packageDevelopment.md)), and both can be found and updated through a registry whose namespaces and Ed25519 signatures are described in [Package registry](../registry.md).

Much of that is portable already. The archive handling uses `fflate`, which runs in a browser. Manifest validation, compatibility checks ([Package compatibility](packageCompatibility.md)), version comparison, the plugin and example catalogues, and every renderer window that lists or reviews packages are plain JavaScript with no Node dependency of their own. What is Node-specific is a short list: the file system (`node:fs`, `node:path`) in `packageArchive.mjs`, `extensionStateStore.mjs`, `addonCache.mjs`, `addonFileStore.mjs` and `addonSettingsStore.mjs`; `node:crypto` for hashes and signatures; Electron dialogs for choosing a file and for the permission review (`packageInstall` in `src/main.mjs`); separate Electron windows and a preload bridge for running add-ons (`addonPreload.cjs`, `launcherPreload.cjs`); and `worker_threads` and `child_process` in `launcherHost.mjs` and `importerWorker.mjs`.

## Principles

- **One implementation of the rules.** Manifest validation, compatibility, permission names and signature checking stay in the shared modules, so a package is accepted or refused identically on the desktop and the web. The web adds storage and a runtime; it does not fork the rules.
- **A package never gets more authority than its manifest declares**, and installing one kind never grants the other's authority, exactly as on the desktop. On the web this is enforced by where the code runs (below), not by trust.
- **Refuse cleanly what cannot work.** A package that needs something the web does not have is turned away at install, saying what is missing, rather than installing and failing later. The mechanism already exists for launchers (`launcherFeatures` in `addonHost.mjs`); the web advertises a smaller set, and plugins gain a platform or runtime check.
- **No server of our own.** The web edition is static files; everything here works from the browser and from static hosting.

## Design

### Storage

Packages are kept in the browser's origin-private file system (OPFS), laid out as the desktop lays them out (`packages/addons/<id>/<version>/`, `packages/plugins/<id>/<version>/`), with the list of disabled packages in a small `state.json` beside them (the installed list is the directory itself, as on the desktop), and IndexedDB used for the same layout in a browser that cannot write a file to OPFS from the page. The Node modules above are split into pure logic and a small storage interface (read, write, list, remove, rename), with a Node implementation for the desktop and an OPFS one for the web, so the logic is shared and tested once. The page asks for `navigator.storage.persist()` when the first package is installed, because a browser may otherwise clear an origin's storage when the device is short of space, and says so in the install review if the request is refused. Packages are separate from the service worker's offline copy (`webServiceWorker.js`): turning offline use off, or an update replacing the build, never removes an installed package, and a package works offline once installed.

### The install path

A file input and drag-and-drop (the project drop handling in `projectFiles.mjs` is the model) replace the Electron file dialog; the bytes go through the same inspection as on the desktop, including the minimum-version and API-version refusal. The permission review, a native message box on the desktop, becomes an in-page dialog showing the same facts: name, publisher namespace and whether its signature verified, version, and the permissions asked for, each in plain words. Signature verification moves from `node:crypto` to WebCrypto, which is asynchronous (the shared code becomes `async` where it calls it) and which supports Ed25519 in current Chrome, Safari and Firefox; whether a small pure-JavaScript fallback is needed for older browsers is decided when this is built. A package installed from a file is not signed on the desktop either (only one fetched from the registry is checked, in `installFromRegistry`), so the check arrives with the registry in stage 4 and not before. Nothing needs a restart on the web, so `restartPending` stays false and the restart badge never shows; an installed package takes effect at once, which also means an update to a package that is in use is applied when its window is next opened and not under it.

### Running add-ons without trusting them

This is the decision that matters most. On the desktop an add-on runs in a separate sandboxed window, and an importer in a worker thread, and the importer's own source says that limits accidents and is not a hardening boundary: the trust is the person's choice to install. On the web the same code would run on the origin that also holds the person's saved models, the offline copy and every installed package, so an add-on must be kept away from all of it.

Each add-on is run in an `iframe` with `sandbox="allow-scripts"` and without `allow-same-origin`, so it has an opaque origin and cannot read the page's storage or cookies. Its files are served to the frame from OPFS through a blob or `srcdoc` document that carries a Content-Security-Policy of `default-src 'none'`, plus only the script, style and image sources it needs from its own package and, for a launcher, a `connect-src` limited to the hosts its manifest declares. The frame and the page talk only by `postMessage` through a bridge that replaces `addonPreload.cjs` and `launcherPreload.cjs`, with the same method names; the host page checks every call against the permissions the person approved before acting, exactly as `launcherHost.mjs` does in the main process, and a call without permission is refused, not queued. An importer runs as a Web Worker created inside such a frame, so it too has no access to the origin's storage, and receives only the file texts and helpers it is given, as today. A frame that stops answering is closed by the host.

The sandbox is what makes installing a file from anywhere acceptable on a public origin. It does not make a malicious add-on harmless to the data it is given on purpose (a visualizer with `results.read` sees the results), so the review dialog stays honest about permissions, and the registry's namespaces and signatures remain the way to tell a known publisher from an unknown one.

### What each kind needs

- **Declarative plugin assets (component templates, plugin-contributed examples).** Installed plugins contribute them to the same component library and examples listings the web already builds from static files, through the existing `userLibraryStore` path. No code runs, so this is the first thing to build and needs no sandbox.
- **Python providers in plugins.** The web already runs Python providers through Pyodide, so a plugin's provider source is read from OPFS and handed to that bridge in place of the desktop's `pluginResolver.mjs` reading from disk. This is the one place where the sandbox principle above does not hold: Pyodide lets Python reach the page's JavaScript, so a provider is not walled off as an add-on will be. What limits the damage is the page's Content-Security-Policy (`default-src 'self'`, so it cannot send data to another host) and that the engine runs in a worker, which has no access to the page itself; it can still read what the page's origin stores (the installed packages). The review says this plainly. Walling providers off needs the engine worker itself to run in a sandboxed frame, which is a later piece of work and is not in this proposal's stages.
- **C++ providers in plugins.** Compiling C++ in the browser works only on the threads build (clang through Wasmer), so a C++ provider is installable only where that is the edition running, and only as source or as WebAssembly; a prebuilt native binary cannot run. Plugin manifests need a way to say which runtimes a provider supports on the web (a `web` entry beside the native platforms), so the install can be refused with a reason.
- **Result visualizers (`.kja`).** The frame described above, opened in a panel; on a phone, a sheet from the bottom edge like the other panels (see [Web Edition](webEdition.md), the phone layer). The bridge carries `timeline.change`, `selection.change` and `timeline.seek` and read access to results, as `addonPreload.cjs` does. The rail that lists add-on buttons is hidden on a phone, so its entries need to be listed in the phone menu, built from `listToolstripContributions()`.
- **Launcher add-ons.** The largest piece, and the last. `scenario.run` and `data.import` map to the web engine and a worker; `files.store` and the cache map to OPFS, and resumable downloads use the `Range` technique already built for the offline copy; `project.data` and `model.open` go through the page. `network.fetch` is limited by CORS to servers that allow the web edition's origin, which many data services do not; the review says so, and a package that depends on others should be marked as desktop-only. Features that need a process on the machine (`pythonCheck`, anything through `child_process`) are not advertised.

### Finding and updating packages

The Discover side of the Extensions window (`discoverRegistry`, `installFromRegistry`, `registryImage`, `registryScreenshot`, `checkUpdates`) reads GitHub: the registry index and release metadata through the GitHub API, and the archive from a release asset. The API allows cross-origin reads but unauthenticated callers are limited to 60 requests an hour per address, and a release asset download redirects to a host that sends no CORS headers, so the browser blocks it. The simplest fix is to publish the registry index, the images and the package archives on the web edition's own static site (which already sends `Access-Control-Allow-Origin: *`), regenerated by the release workflow, and to point the web's `registryClient` at that. A package still verifies against its publisher's key, so the mirror is a convenience and not a new point of trust. Update checks then cost one small file and no API quota. A small proxy is the alternative if mirroring proves too heavy; it is not needed for the first stages.

### Projects that name a plugin

A project can pin a provider by `pluginId`, `pluginVersion` and `providerId` instead of embedding source ([Project schema](../projectSchema.md)). Opening one whose plugin is not installed should offer the install (from the mirror, or from a file) before the model is run, and say plainly which provider is missing, as the desktop does for a missing FMU; today the web has nothing to offer.

## What cannot work in a browser

FMUs, native or external-process plugin artifacts, and anything that starts a process are out of reach and stay desktop-only; the install refuses them with the reason. A package that offers both (a Python provider and a native one) installs for what the web can use. These limits are the same ones [Web Edition](webEdition.md) already states for the built-in features.

## Staged plan

1. **Storage, install window and declarative `.kjp`** (built). The storage interface and its OPFS and IndexedDB implementations, the file install with the in-page review, list, enable, disable and uninstall, and plugin-contributed templates and examples. Small, shows a real result, and needs no sandbox. Drag-and-drop install and signature checking are not in it: the second belongs with the registry (stage 4), and the first is a convenience for later.
2. **Python plugin providers**, and the prompt to install a plugin a project names (built).
3. **Sandboxed visualizer add-ons** (built): the frame, the CSP, the bridge with permission checks, the panel and phone-menu entries. This is where the security model is proven, so it carries the most tests, including a hostile package that tries to read the page's storage, reach the network and call a method it was not granted.
4. **The registry mirror, Discover and update checks** (built), with the release workflow publishing the mirror.
5. **Launcher add-ons**, feature by feature, each advertised only when it works (built so far: importing and opening a model, then baseline and scenario runs, then results export, then runs in the opened project).

Each stage is released on its own. A stage that is not built leaves its kind turned away at install with a clear message, so the web never installs a package it cannot run.

## Decisions needed before stage 1

- **Storage:** OPFS with IndexedDB for state, as above. The alternative, IndexedDB alone, copes less well with a package of many files and large assets.
- **Isolation:** sandboxed frames with an opaque origin, and a bridge with host-side permission checks. The alternative, running add-ons in the page's own origin as the desktop's importers are, is not acceptable on a public origin.
- **Distribution:** mirror the registry and packages on the web edition's own site, regenerated by the release workflow. The alternative is a proxy, which adds something to run and pay for.

## Open questions

- Whether browsers the web edition supports lack WebCrypto Ed25519, and so need a bundled fallback.
- Whether `persist()` is granted often enough on phones for installed packages to survive, and how the page should behave when it is not (most likely: install anyway and warn once).
- Whether a visualizer frame may use WebGL and a worker of its own (the Results Analysis add-on draws plots), and what CSP that needs.
- Whether the same package archive can serve both editions, or the manifest needs a per-edition section for what differs (entry files, hosts, runtimes).

## Verification

The shared logic is covered by unit tests that run the same cases against both storage implementations. The sandbox is covered by a browser test in real Chrome, driven as the web driver does ([Web Edition](webEdition.md), its test section): install a visualizer, see its button and panel, and then install the hostile package above and watch each attempt fail. On a phone, the install, the panel and the phone-menu entries are added to [the phone checklist](../phoneTestChecklist.md), since file pickers and storage limits differ on a real device.

## As built: stage 1

The Node-free half of `packageArchive.mjs` (the manifest rules, compatibility, and `inspectPackageArchive`) moved to `src/packageInspection.mjs`, which the desktop re-exports from its old place, so the desktop and the web edition run the same checks. `src/webPackageStore.mjs` is the store: `createPackageStore({ storage, appVersion })` with `inspect`, `install`, `list`, `uninstall`, `setEnabled` and `readFile`, and `pluginComponentTemplates` and `pluginExamples` for what installed plugins add, over a `storage` that is OPFS (`createOpfsStorage`), IndexedDB (`createIndexedDbStorage`, chosen by `createBrowserStorage` when a page cannot write to OPFS) or memory (`createMemoryStorage`, for tests). A package is written with its `package.json` last, so a copy cut short is never listed and is cleared by the next install of that version. `webPackageRefusal` is the one place that says what the web edition cannot run yet: any add-on, and any plugin with a relationship provider, is refused at install with the reason, before the review; a plugin whose parts are all component templates and example models installs.

In the page, `webShims/packages.mjs` is `window.extensions` (the file chooser, then `webShims/packageReview.mjs`'s `<dialog>` showing what the package adds and what it may do, then the install; Discover and registry installs say they are not available yet), and what installed plugins add reaches `window.componentLibrary.list()` and the Examples window (`projectFiles.mjs`, with thumbnails as data URLs because the page's Content-Security-Policy allows `data:` images and not `blob:`). The Extensions window's notices say "It is ready to use now" in place of "Restart Konjugate", and the phone menu has an Extensions entry; the window itself stacks its list above its detail on a phone. `fflate` is vendored into the web shell and named in its import map. Covered by `tests/webPackageStore.test.mjs` (the store, against memory storage) and, in real Chrome, a driven install of a component-and-example plugin that persisted across a reload and appeared in the library and the Examples list, with an add-on and a provider plugin refused.

## As built: stage 2

A model's reference to a plugin's provider (`implementation.kind: "plugin"`) is resolved by shared code in `src/pluginReferences.mjs`, which the desktop's `pluginResolver.mjs` now uses for its walk of the model too (its behaviour is unchanged; its tests pass as they were). The web host is `resolveProvider` and `resolveModel` in `webPackageStore.mjs`: the reference is replaced by `kind: "python"`, the provider's version and API number, and the provider's source text inline, since the web engine hands source to Pyodide directly and there is no path to give it. A missing, disabled, incompatible or wrong-runtime plugin is reported with the desktop's error codes and wording (and `PLUGIN_NOT_INSTALLED` and `PLUGIN_RUNTIME_UNSUPPORTED` for the two cases the desktop does not have). `webShims/engine.mjs` resolves a model before `validate`, `fit`, `run` and `start`, and skips opening the browser's storage for a model that names no plugin.

A plugin is now refused at install only when none of it can run here. One that mixes Python providers with C++ ones, or with component templates and examples, installs, its entry in the Extensions list carries `runnableRuntimes: ["python"]`, `pluginProviderChoices` offers only providers in those runtimes, and the review says how many of its providers will not be offered. C++ plugin providers stay refused: resolving them to inline source for the threads build's compiler looks possible but has not been tried. `webShims/packages.mjs` tells the page when anything installed changes (`konjugate:packages-changed`), and the page validates the model again, so a model that named a plugin which has just been installed stops showing the earlier "not installed" error without being touched.

Opening a project in the web edition that names plugins it cannot use shows a dialog listing them and why (not installed; installed but another version, which the dialog says could change the results; turned off; needing a newer Konjugate), with "Install a plugin file…" and, for a turned-off one, "Turn on" (`src/renderer/missingPlugins.mjs`, called at the end of `loadProjectDocument`). It lists again after an install and closes when nothing is missing. The desktop does not show it. Offering the install from the registry waits for stage 4; until then the prompt installs from a file.

As said in the design, a Python provider is not walled off from the page. The review states it. Tested in real Chrome with an example model that pins a provider from another plugin: opened without it (the dialog, and a validation error naming the plugin), installed from the dialog (the page validated again unprompted), run to "Simulation complete", then disabled (the run says to enable it). The unit tests are in `tests/webPackageStore.test.mjs`.

## As built: stage 3

A result visualizer (`.kja` with `kind: "resultVisualizer"`) installs and runs. It is opened from the same toolstrip button the desktop shows (the rail's, and on a phone an entry at the end of the menu), in a panel that is a side panel on a wide screen and a bottom sheet on a phone, one of the sheets `phoneSheets.mjs` keeps to one at a time. The frame is `<iframe sandbox="allow-scripts">` with no `allow-same-origin`, no popups, no forms and no top navigation, so its origin is opaque: it cannot read this page's storage, cookies, DOM or the installed packages. It starts from `renderer/addonFrame.html`, a static page that carries a Content-Security-Policy of `default-src 'none'` with only inline scripts and styles and `data:` images, fonts and media allowed, and a script that waits for the page to send it the add-on's document. The policy is kept when that document replaces the page, which was checked in Chrome before relying on it. The shell is a file served from the site and not a `srcdoc` or `blob:` document because those inherit the page's own policy (`script-src 'self'`), which would block the add-on's scripts.

`src/webAddonDocument.mjs` builds the add-on's document from the files in the package: each local script, stylesheet (with the `url()` it names) and image of the entry page is read from storage and placed in the page, since a frame with an opaque origin and no network cannot fetch them, and the API goes in first under the desktop's name, `window.konjugateVisualizer`, with the same methods and events as `addonPreload.cjs`. A page that refers to a file the package lacks, or to one outside it, fails to open with a message saying which. A script of `type="module"` that imports other files is not supported; the add-on is bundled to one script, as most are. `src/webAddonBridge.mjs` answers the requests: every method checks the permission the person approved at install, answers exactly as the desktop's handlers in `main.mjs` do (a read without `results.read` gets `null` or an empty list, a seek without `timeline.seek` does nothing, export, pacing and data calls without their permission are rejected), only the named methods are reachable, and the page ignores messages that do not come from the frame it made. Of the permissions a visualizer may ask for, the web grants `results.read`, `timeline.read`, `timeline.seek`, `selection.read`, `results.export` (the file is downloaded) and `settings.store` (kept in the same browser storage as the packages, per add-on, across projects and updates, and removed with the last version); one that asks for a live-run or project-data permission, or requires `projectData`, was refused at install with the reason when this was first built, and is not now (see "As built: visualizers, a run in progress and the project's data"); a launcher is a different kind of add-on. The review dialog describes the button an add-on adds, lists its permissions in words, and says it runs walled off. An add-on that is uninstalled or turned off while open is closed, and the rail and the phone menu are rebuilt whenever packages change.

What the sandbox does and does not do. It was tested in real Chrome with a hostile add-on that asks only for `results.read` (`scripts/checkWebAddonSandbox.mjs` runs it against a served build and fails if anything gets through): reading `localStorage`, `sessionStorage`, cookies and IndexedDB, reading the parent's DOM or location, opening a window, creating a worker, a WebSocket, an XHR or a fetch, and loading an image from the site all fail, and `requestPacing`, `getSettings`, `setSettings`, `getProjectData`, `setProjectData` and `exportCsv` are all rejected without their permission, as is a call to a name that is not a method (`constructor`). A frame that navigates itself away is stopped by the page's own `frame-src 'self'` unless the address is on the site itself, in which case the frame loads the app's page, which cannot run there (it has no origin, so its module scripts are refused); nothing is sent anywhere but the site's own server, and the person can close the panel at any time. Two limits remain. What an add-on is given on purpose it can see: a visualizer with `results.read` has the results and the model's node names and shapes, which is why the review lists permissions and the registry's publisher names and signatures (stage 4) remain the way to tell a known publisher from an unknown one. And the page does not watch a frame that stops answering: the panel's close button removes the frame, and a page that never becomes ready within ten seconds is removed with a message, but a frame that hangs afterwards is left to the person to close. The hint a browser may follow from a `<link rel="dns-prefetch">` that a script adds to its own document is not covered by a Content-Security-Policy and could tell a name server which host was asked about; a few bytes at most, and not changed here.

Not done in this stage: drag-and-drop install, live-run permissions (`results.live.read`, `simulation.status.read`, `simulation.pacing.*`) and `project.data`, which need the page to hand an add-on a run in progress and the project's own data, and the sandboxed `Worker` an importer will need (stage 5).

## As built: stage 4

The build writes the registry beside the app (`src/webRegistryMirror.mjs`, called from `scripts/buildWebShell.mjs`): `registry/index.json` (the entries, and for each the package files mirrored from its newest release this build can use, with the size, SHA-256 and version of each), the entries' images and screenshots, and the package files under `registry/packages/<prefix>/`. The package downloads are made only when `KONJUGATE_MIRROR_PACKAGES=1`, which the web edition workflow sets, so a local build needs no network and its index lists entries and images without packages (installing from it says the package is not available from the web edition's registry yet). The release is chosen by the desktop's own `fetchEntryArchive`, so a release that needs a newer Konjugate than this build is skipped as it is on the desktop; an entry whose release cannot be fetched is left out with a warning and does not fail the build. `registry/` is not part of the offline copy that "Use offline" saves, and is kept like any file used after that copy was made.

In the page, `window.extensions` reads it through `src/webRegistry.mjs`, which uses only `fetch` and WebCrypto: Discover (`discoverRegistry`) reads the index and the Extensions window shows the entries with their images, as it does on the desktop, from the same files; installing downloads each package of the entry, checks its size and SHA-256 against what the index recorded (a file that is not as recorded is refused), checks the publisher's signature, and shows the review dialog with what the check found before anything is stored; the update check compares the mirror's versions with what is installed from one small file, so it costs no request quota, and Update installs the mirrored version in place of the older one. Screenshots and the images are handed to the window as data URLs, as the desktop does; a video link opens only if it is one of the two YouTube forms the registry allows, and any other link a publisher wrote opens only after the person has seen it.

Signatures are checked with WebCrypto in `src/packageSignature.mjs`. The rules for which prefix covers a package, and what a signature file says, were moved from `packageArchive.mjs` to `packageInspection.mjs` and are shared; only the arithmetic (SHA-256 and Ed25519) differs, and a test signs archives with the desktop's code and checks that the web check gives the same answer for every status it can report. The check is advisory as on the desktop: the review says whether the package is signed by the publisher of its name, signed but unverifiable here (a browser without Ed25519 in WebCrypto), signed with a signature that does not hold (with the reason, and a warning not to install it), or not signed. A package installed from a file is not checked against the registry, as before, since it did not come from there.

What the mirror does and does not add to trust. The keys a signature is checked against come from the same site as the packages, so a compromise of the site could change both; the signature still means that a package was signed by the key the registry lists for its name, and the registry entries are reviewed in the repository, which is where the mirror is built from. A package fetched from the mirror at build time is the release asset the registry entry names, and the build records its hash, so what was published is what is served until the next build. The mirror is refreshed only when the web edition is built and deployed, so a publisher's new release reaches the web after the next deploy, not at once, which the update check shows as the mirror's version and not GitHub's. Two things are not done: a mirror of every release (only the newest usable one is kept, so rolling back to an older release is not offered), and a small proxy for entries whose release cannot be mirrored.

## As built: stage 5, first part

Launcher add-ons install and run, for the part of the desktop's launcher API that is built: choosing files (or the package's sample), running a declared importer, opening the model it built in the canvas, opening a declared help page, and opening a link on a declared host. A launcher that asks for anything else is refused at install with the reason: of its permissions only `data.import`, `model.open`, `pages.open` and `links.open` are granted (so no `scenario.run`, `results.export`, `analysis.infer`, `network.fetch`, `project.data` or `files.store`), of its optional features only `importProgress` is offered, and an importer with a binary file role is refused. The methods of the rest answer `{ ok: false, message }` saying so, as every desktop method answers a refusal, so a window can show it. This means that a launcher whose point is running scenarios, as the registry's toolboxes are, does not install in the web edition yet; the next parts are the scenario and baseline runs (against the web engine, with the same branch composition the desktop uses), results export, and then fetching from declared hosts, each added to the granted set only when it works.

It uses the same sandboxed frame as a visualizer, with the launcher's own API under the desktop's name, `window.konjugateLauncher`, taking the same positional arguments as `launcherPreload.cjs`. The rules for what an importer is given and what it may return were moved from `launcherHost.mjs` to `launcherImport.mjs`, which uses no Node, and both hosts use them: how a chosen file is decoded (UTF-8, UTF-16, Windows-1252), which files an importer is given, what its progress and its derived files may be, the result it must return and the size limits (the desktop's tests still pass over the moved code). `webLauncherBridge.mjs` holds the web host's side: the permission and declared-id checks, the workspace of chosen files and the model built, the derived-files handling, and the shape of every answer. A file chosen in the window is picked with the browser's own file chooser, called from the page in answer to the click in the frame, which works because a browser passes the user activation from a frame up to the page that holds it; it was checked in Chrome, and is on the phone checklist.

The importer runs in a Web Worker made inside a second sandboxed frame (`renderer/importerFrame.html`), not in the page and not in the launcher's window, so the importer has no origin, no storage and no network of its own, as the window has none. The frame's policy is the window's, plus scripts and workers from `blob:` URLs, which is how the importer's source (made a module from a Blob) and the worker that runs it are made. The importer receives the file texts and options and a `helpers` object, and what it returns is checked by the desktop's own rules. Two differences from the desktop, both for importers' authors: the helpers that need the application's own code (`applyOperations`, `reconcileEquationBindings`, `validateEquationLatex`, `readPackageJson`) are answered by the page and so return promises, which an importer must `await` (doing so on the desktop changes nothing), because a frame with no origin cannot import the application's modules and the browser's synchronous cross-thread wait is not available without cross-origin isolation; and an importer is one file, since a module made from a Blob cannot import its neighbours in the package, so one that imports others is bundled first. An importer that runs longer than two minutes is stopped and its frame removed.

Tested in real Chrome with a launcher whose importer builds a model from a file with `applyOperations`: the review lists its permissions in words and says it runs walled off; the window opened from the rail; its scenario call answered that it is not available; "Open in canvas" before an import answered that the data must be imported first; the file chooser opened from inside the frame and the chosen file reached the importer; progress reached the window; the model opened in the canvas as an unsaved copy; the help page opened in its own panel. A hostile importer's attempts to fetch, read `localStorage` or IndexedDB, use `importScripts`, read the parent's document and open a WebSocket all failed, and the importer's frame was gone afterwards. Not tested: a real launcher from the registry (none of the registered ones can install yet), and a phone.

## As built: stage 5, scenario and baseline runs

A launcher may now ask for `scenario.run`: `runBaseline` and `runScenario` work, with the desktop's arguments and answers, and `getManifest` lists the declared scenarios. Of the optional features a launcher may require, `baselineRun`, `scenarioForkTime`, `scenarioOverrides`, `suppliedPerParameter`, `parameterSchedules` and `scenarioEveryBackend` are now offered beside `importProgress`. Still refused at install: `analysis.infer`, `project.data`, `files.store` and binary file roles (the rest followed, see the "As built: stage 5" sections after this one). `openInCanvas` carries the runs into the project (see "As built: stage 5, runs in the opened project").

The rules for a run that need no Node were moved from `launcherHost.mjs` to `launcherRuns.mjs`, and both hosts use them: the checks of a window's fork time and run length, turning a declared scenario into parameter changes, the overrides and supplied data, composing a forked branch, picking series, the nearest checkpoint, and keeping one baseline per run length (the desktop's tests still pass over the moved code). `webLauncherBridge.mjs` runs them against `host.runModel`; a plain run goes to the engine in the batch worker and answers the whole decoded result, checkpoints included (`webLauncherEngine.mjs`), and the fork is the baseline's nearest checkpoint run on to the scenario's end with `startCheckpoint`, as on the desktop (`webLauncherRuns.mjs`).

Where the fork's parameter changes go depends on the page. The desktop starts the fork paused and sends each change to the engine as a command. A page can send the engine commands only when it is cross-origin isolated, which GitHub Pages cannot make it, so there are two ways, and the page picks by what it can do. On an isolated page the fork is started paused in the live-run worker and gets the same commands the desktop sends (a pause, one scheduled change each, then a resume), through the worker's control ring. On any other page the changes are written into a copy of the model as the stored schedule of each parameter they change (`interventionSchedules.mjs`), which the engine follows from the checkpoint on. The schedule is made by evaluating the changes as the engine does (of the changes that have started, the one that started last governs; a step holds, a pulse returns to its base value, a path is followed linearly then held, and a parameter's own stored schedule applies until a change takes over), and a jump is written as two samples one floating-point step apart, so that a time on or after the jump takes the new value exactly as it does from a command. A parameter's fitting bounds are left out of the copy, since the engine does not allow a scheduled parameter to be a fitting target; the page's model is not changed. A change to something that is not a shared parameter is refused by name.

The two ways were compared against the real engine: `tests/interventionSchedules.test.mjs` runs six cases (a step at the fork, a step after it, a pulse that ends on a step boundary, a path, a path with a later step over it, and a step then a pulse) once as commands, through the desktop's `runScenarioBranches`, and once written into the model, and every state at every sample agrees to a relative 1e-6. The test is skipped where the native engine is not built. In real Chrome, with a launcher whose importer returns a two-node model, the same launcher gave a baseline of 10, a step to a gain of 3 at the fork a level of 20, and a pulse 14.8, on a page served without isolation (the schedule way) and on one served with it (the command way), to the last digit; a scenario asked for before an import answered that the data must be imported first. `scripts/serveWebShell.mjs` now leaves the isolation headers off when `KONJUGATE_NO_ISOLATION=1`, to test the page GitHub Pages serves.

Not done: a run that can be stopped by the window, and models with Python providers in a fork (the batch and live workers load Pyodide as a plain run does, but a fork from a Python-provider checkpoint was not tried). Not tested: a phone, and a real launcher from the registry.

## As built: stage 5, results export

A launcher with `results.export` (and, if it requires it, `runRecord`) can call `exportResults(scenarioId, { summaryCsv })` with the desktop's arguments. A page cannot write a folder, so the files come as one zip download, `<Launcher name>-<time>.zip`, holding a folder of `results.csv` (the baseline and the named scenario's retained run, in the desktop's long format), `summary.csv` when the window gave one, `model.kjt` and `run-manifest.json`. The answer is the desktop's `{ exported, folder, files }`, with `folder` naming the zip. Two differences from the desktop: the model file is named `model.kjt` rather than `project.kjt` because it is the imported model alone, without the baseline and scenario branches the desktop embeds (the web project codec cannot yet write several result branches, so the export keeps the model alone); and the zip is made and downloaded by the page, so there is no folder chooser and the person's browser decides where it goes.

The run manifest is the desktop's, built by the same code: `buildRunManifest` was split so that the record itself (`runManifest` in `launcherRuns.mjs`, with `resultsToCsv`) uses no Node and takes the model's hash as an argument, while the desktop's `buildRunManifest` is a thin wrapper that hashes with Node (its tests still pass unchanged). The web host hashes with WebCrypto, so every chosen, sample and derived input now carries its SHA-256 and size, and the manifest records them with the importer's options, the scenario overrides and the interventions. Scenario runs are kept per scenario and entity, as on the desktop, and dropped when a new model is imported.

Tested with a launcher in real Chrome: the export was downloaded, and its four files were the right ones, with the results in the desktop's format and the manifest holding the Konjugate version, the scenario, the inputs' hashes and the hash and size of each other file.

## As built: stage 5, runs in the opened project

`openInCanvas(scenarioId)` now opens the project as the desktop does: the imported model with the baseline run as its first result branch and, when a scenario is named that has been run, its fork as a second, with the baseline as its parent, the fork time and the scenario's name as the label. With no run yet it opens the model alone, as before. The desktop encodes the runs into a project file and decodes it again; the web page needs no file, so the host hands the page the decoded results, which it registers as result sessions (the same cache a completed run and a loaded project's embedded result use, `registerCompletedResult`) and passes on as `embeddedResult` and `embeddedBranches`, the fields the canvas already restores a saved multi-branch project from. The fork holds its own run from the fork point, as the desktop's does, and each branch keeps its own identifier so the parent link resolves.

Tested in real Chrome: after a baseline and a scenario run, "Open in canvas" for that scenario opened the model with the results bar showing, and the Branches panel listing Baseline and the scenario's fork. Not done: writing such a project to a file from the web edition (the web project codec holds one result, not several branches), which is why the export still keeps the model alone. I also changed the trial banner, which still said launcher add-ons are not available: it now says those that fetch data or infer are not (later changed again, when fetching was built).

## As built: stage 5, fetching from declared hosts

A launcher may now ask for `network.fetch`, and `fetchText` and `fetchFile` work with the desktop's arguments and answers: an https address, no credentials, only a host the manifest lists in `network.hosts`, 5 MB for a file and 1 MB for text, twenty seconds. A fetched file goes into its file role as a chosen one does, with its address and time kept for the run manifest, and `getManifest` marks it fetched. The download cache is not built (`cacheInfo` and `clearCache` still answer that they are unavailable, and a launcher that lists `fetchCache` in `requires` is refused at install); a `cache` option is accepted and every fetch goes to the server, with `cached: false` in the answer.

The application's page may talk only to its own server (its policy is `default-src 'self'`), and I did not loosen that for the whole application. The request is made instead by a sandboxed frame made for it and removed when it answers (`renderer/fetchFrame.html`, `fetchRunner.mjs`): no origin, no cookies, no storage, no way into the page, a policy that allows requests to https and nothing else, and no code from any package in it, only a few fixed lines. The page checks the host list before asking, and the frame checks it again on the address asked for and, because a browser cannot stop at a redirect and look where it leads, on the address the answer came from, before it reads any of the body. The request carries no cookies and no referrer. `webFetch.mjs` holds the page's side and its messages; the limits moved to `launcherImport.mjs` so the desktop and the web share them.

What this cannot do, and the reason it is not a full replacement for the desktop: a page can read an answer only from a server that allows pages from other sites (CORS), and the frame has no origin so its requests carry `Origin: null`, which only a server that answers `*` allows. A browser reports a refusal as a failed request with no reason, so the message says the server may not allow a web page to read it, and that the desktop app can. Of the nine hosts the registry's two launchers declare, I found Nominatim and ArcGIS answering with `Access-Control-Allow-Origin: *`; FRED, Stooq, Geofabrik, BBBike and the OpenStreetMap France extracts send no such header, Overpass gave no answer to my probe, and Yahoo was rate limiting. So fetching alone does not make either registry launcher work here: the fintech toolbox also needs `analysis.infer` and its three data hosts are not readable, and the logistics toolbox also needs `files.store`, `project.data` and binary inputs. A proxy on the site's own server is the only way to reach the other hosts; it would see what people look up and is not built or planned without a decision. The review dialog now lists the hosts a launcher may fetch from and says some servers do not allow a web page to read them.

Tested in real Chrome with a launcher declaring Nominatim, FRED and Stooq: `fetchText` and `fetchFile` from Nominatim returned the answer, the file appeared in `getManifest` as fetched and imported; FRED failed with the message above; an unlisted host and an http address were refused before any request. Not tested: a phone, and a redirect from a listed host to an unlisted one against a live server (the frame's check is covered by the test that reads its source, not by a live redirect).

## As built: stage 5, kept sessions

A launcher may now ask for `project.data` and require `projectSession`, `keepSession` and `openLink`. `openInCanvas(scenarioId, { session })` attaches the launcher's entry to the model it opens, `keepSession(session)` keeps one with the open project without opening a model, and `restoreSession()` gives the window its state back and makes the input files the entry holds the pending files again, so the importer runs as before with nothing chosen or fetched again. The entry and its limits (2 MB of window state, 64 MB of inputs; binary inputs are not kept, what was derived from them is) are the desktop's: `buildSessionEntry`, `attachAddonData` and `sessionInputs` moved from `launcherHost.mjs` to `launcherSession.mjs`, which has no Node in it, and the desktop re-exports them. The one difference is the hash of an input saved without one: the web's SHA-256 is asynchronous, so the bridge fills it in before calling the shared code.

The renderer already holds a project's add-on data (`projectAddonData`, saved with the project as `addonData`, restored when a project is opened, counted as unsaved work when a launcher changes it); on the desktop the main process asks the project window for it over IPC, and on the web the page is that window, so `launcherHost.onKeepAddonData` and `onAddonDataRequest`, which the web shim had as empty functions, are now what the bridge calls directly. A result visualizer's `getProjectData` and `setProjectData` use the same entry and could be offered the same way; they are not yet (a visualizer asking for `project.data` is still refused at install).

Tested in real Chrome: a launcher with `project.data` opened a model with a session, the project was saved from the web page and opened again in a fresh page, and `restoreSession` gave back the window's state and the sample input, after which the importer ran again. Before anything was kept it answered `session: null`. Not tested: a phone, and the unsaved-work prompt after `keepSession` (it is the renderer's, shared with the desktop).

## As built: stage 5, stored files, downloads and binary inputs

A launcher may now ask for `files.store` and require `storedFiles`, `binaryInputs`, `multipleBinaryInputs`, `fetchCache` and `resumableDownloads`, and a file role may be `binary`. With these, the registry's logistics toolbox passes the install check; the desktop's `storedFiles`, `storeFiles`, `downloadFile`, `cancelDownload`, `partialDownloads`, `discardPartialDownload`, `fileSize`, `describeStoredFile`, `removeStoredFile`, `useStoredFiles`, `cacheInfo` and `clearCache` all answer as there. What is still not offered: `analysis.infer`, `nodeProviderInputs`, `pythonCheck`, `algebraicRelationships`, and `reloadFiles`.

**Where files are kept.** In the browser's private file system (OPFS), one folder per add-on under `addonFiles` (stored files) and `addonCache` (the fetch cache), behind a small `volume` interface (`webVolume.mjs`, with an in-memory version for tests and `renderer/webShims/opfsVolume.mjs` for the page). `webFileStore.mjs` and `webFileCache.mjs` are `addonFileStore.mjs` and `addonCache.mjs` for a page: the same entries, limits, checks and messages (1 GB a stored file, 512 MB and 30 days for the cache, details of at most 16 KB), and the pieces they share moved to `storedFiles.mjs`, `addonCacheLimits.mjs` and `launcherFiles.mjs`, which have no Node in them. The page asks the browser not to evict the storage, but a browser may still clear it when short of space, and a store that is full says so ("There is not enough space in this browser…"). A browser that cannot give a page a writable private file system says that stored files need a newer one. Unlike the desktop, which leaves an uninstalled add-on's stored files in a folder the person can open, the web removes them with the add-on's last version, because there is no other way for the person to reach or free them.

**Downloads.** A download is made by the same sandboxed frame as a fetch, in a second mode (`renderer/fetchFrame.html`, `fetchRunner.mjs`): the body comes back in pieces, the frame never runs more than eight pieces ahead of what the page has written, and it sends only a `Range` (the form `bytes=N-`) and an `If-Range`, nothing else. The host list is checked before the request and on the address the answer came from, before a byte is read. A download that stops is kept (`.part` and `.partial`, as on the desktop), and asking for the same address again continues it with a `Range` request when the server says the file is unchanged; otherwise, or when the server sends the whole file, it starts again. The sum a server publishes beside a file (geofabrik's `.md5`) is checked with a small incremental MD5 (`md5.mjs`), since WebCrypto has none. Unfinished downloads are dropped after a week.

**What a browser changes, and what it cannot do.** A page may read only the response headers a server exposes: `Last-Modified` and `Content-Length` always, `ETag` and `Content-Range` only if the server lists them in `Access-Control-Expose-Headers`. A download can therefore be continued only if the server gave a date or an ETag to tell the file by, and a `206` answer is taken to start where it was asked to. An `If-Range` request makes the browser send a preflight, so the server must allow that header too; a server that does not fails the continuing, and the person starts again. The same limit as for any fetch applies first: the server must allow a web page to read it at all, which the three big OpenStreetMap download hosts the logistics toolbox names do not, as far as I found. A redirect cannot be inspected before it is followed, so a redirect from a listed host to an unlisted one is made: the unlisted host receives one anonymous GET (no cookies, no referrer, no credentials) and its answer is thrown away unread, with a message naming the host. A download that is interrupted by the tab closing, as opposed to the network, loses what the browser had not yet committed to the file (the file is saved when its writer is closed, which happens on any error and on cancel).

**Binary inputs.** A binary role's files are noted when chosen (a `File` handle, nothing read) and read into memory when the importer runs with `useBinaryFiles`, then handed to the importer's worker without copying, as on the desktop; the importer gets more time by size. The desktop's limits are kept (1 GB each, 2 GB together), but a phone will often not have the memory for a file that size, and the message for a file that could not be read says so. Stored files are used as a binary role's files in place of any chosen. A binary input is not kept with a session, as on the desktop.

Tested in real Chrome against a local https server (a host name mapped to it, with CORS, Range, ETag, an MD5 file and a connection that cuts after 9 MB): a size by HEAD; a text and a download; a redirect to an unlisted host refused; the cut download kept as a partial and continued with `Range: bytes=1097728-` and the ETag, then whole and matching its MD5; a wrong sum refused; a slow download cancelled and kept as a partial; the 24 MB file stored, used as a binary role and handed to an importer as bytes; a file brought in from disk and one chosen for the binary role; the cache answering the second request without the network; and, after uninstalling the add-on, nothing left in OPFS. Not tested: a phone, a real OpenStreetMap host, a gigabyte file, a browser other than Chrome, and the launcher's own window with real map data.

## As built: visualizers, a run in progress and the project's data

A result visualizer may now ask for every permission the desktop offers: `results.live.read`, `simulation.status.read`, `simulation.pacing.read`, `simulation.pacing.control` and `project.data` join the six it had, and it may require `projectData`. Nothing the desktop offers a visualizer is refused at install any more.

**A run in progress.** The visualizer is opened from the result the page is showing, which during a live run is the run so far. The page's live engine already announces each update and the end of a run (`onWebEngineUpdate` and `onWebEngineComplete` in `webEngineLiveShim.mjs`, the same events the canvas draws from); the add-ons shim listens to them and, for an open visualizer whose session belongs to that job, hands the result to the bridge's `runUpdate`, which does what the desktop's `updateVisualizerResult` does: the session's samples, lifecycle, simulation time, available result time and pacing follow the run, and the frame is sent `samplesAvailable` with `results.live.read`, `runStatusChange` with `simulation.status.read` and `pacingChange` with `simulation.pacing.read`, each only with its own permission. A result that arrives without the live fields is taken as the finished one. `seek` is held back while the run is going, as on the desktop. `requestPacing` changes the pace of the run in progress with `simulation.pacing.control` and the page's own `setPacing`, and answers the pacing the engine took; with no permission it is refused as before, and for a run that is over it answers "The simulation is no longer running", as the desktop does.

**The project's data.** `getProjectData` and `setProjectData` keep the visualizer's own entry in the project's `addonData`, shared with launchers' sessions (the same renderer hooks, called directly because the page is the project window): `{ version: 1, addonVersion, savedAt, data }`, at most 1 MB, `null` removes it, another add-on's entry is never read or touched, and an entry of a version this host does not know is left unread. It is saved and opened with the project like a launcher's.

What differs from the desktop: the web page's live updates are the throttled ones the canvas gets (at most one every 100 ms, and the samples of a long run thinned as the canvas thins them), so a visualizer sees what the canvas sees and not every step. A live run exists only on a cross-origin isolated page (the default build when served with the headers it needs); on any other page a run is delivered whole when it ends, a visualizer is opened on the finished result, and a request to change the pace answers that the simulation is no longer running.

Tested in real Chrome with the spring-mass-damper example run online at one simulation second per second: a visualizer with all of the permissions opened mid-run and was told of the run (6 updates of each kind across it, ending with a `completed` status and 101 samples), `requestPacing` to the fastest pace took effect and was reported back as a pacing change, the same request after the run was refused, and `setProjectData` followed by `getProjectData` gave the data back. Not tested: a phone, a visualizer left open across two runs, and saving the project with a visualizer's data and opening it again (the path is the launcher sessions', which was tested).
