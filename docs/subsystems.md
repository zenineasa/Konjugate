# Subsystems

Subsystems are authored hierarchy over Konjugate's graph, not separate simulation entities. A subsystem owns a stable numeric ID, a parent subsystem ID, a name and a display position. Nodes retain their original IDs and identify the subsystem that contains them. Relationships also retain their original endpoints and IDs. Every subsystem is also a component: an instance of a definition that can be placed more than once, saved as a file of its own, kept in My library and linked to where it came from (see [Components](#components)). The design is [Subsystem components](proposals/subsystemComponents.md).

## Boundary crossings

A subsystem's boundary is not stored. Which relationships cross it is derived, whenever it is shown, from the current relationships and node membership by `subsystemBoundaryCrossings` in `src/subsystems.mjs`, the one function both the parent view and the inside view use (see [Design principles](designPrinciples.md)). A relationship crosses a subsystem's boundary when exactly one of its endpoints is inside, counting nodes in nested subsystems as inside; the other endpoint may be at the top level, in a parent subsystem or in a sibling. Each crossing names the relationship, its inside and outside node, whether the inside node is the relationship's source or target, and its direction seen from inside: incoming when the outside node is the source, outgoing when it is the target, and bidirectional for a relationship that applies its result to both ends (see [Relationship and relationship directionality](edgeDirectionality.md)). Relationship-group members are ordinary relationships here: a group spanning the boundary has one member crossing each way for every inside and outside pair. Deleted entities are left out, so adding, deleting, reconnecting or undoing a relationship, or moving a node in or out, changes the boundary at once. Multiple relationships between the same pair of nodes stay separate crossings.

Earlier versions recorded a `ports` array on each subsystem when it was created and never updated it, so the count it gave went stale as soon as a relationship was added or deleted. A file with stored ports still opens: the field is read past without being checked, even when it names a relationship that has since been deleted, and it is not written again. Konjugate no longer writes `ports`, because a derived copy saved beside the edges it is derived from can only disagree with them; an older Konjugate opening a newer file finds no ports and reads it as before, showing a count of zero on the proxy.

## Views

The parent view renders a subsystem proxy, labelled with the subsystem's name, its current number of boundary crossings and an Open button. A relationship that crosses the boundary is drawn to that proxy, while relationships whose endpoints are both inside the subsystem are hidden at the parent level. A click on the proxy selects it and opens its card; its Open button, a double click, or Open subsystem in its card or right-click menu steps inside, which shows its direct member nodes and nested subsystem proxies. The breadcrumb returns to the parent view.

Inside a subsystem, every crossing is drawn as a terminal at the side of the view, standing in for the node outside, and the relationship itself runs from that terminal to the inside node (or to the proxy of the nested subsystem holding it). Terminals for relationships whose outside node is the source (incoming) stand on the left, and those whose outside node is the target (outgoing, or the far end of a bidirectional relationship whose source is inside) on the right, ordered by the height of their inside node so that few lines cross. Each terminal is marked "→ In", "Out →" or "⇄ Both" and names the outside node, with the state the relationship binds on that node, where that node is (its subsystem path from Model) and, for an edge-group member, the group. Clicking a terminal selects its relationship and opens its editor; the ↗ beside it leaves for the view that shows the outside node, with that node selected. Terminals are laid out on entering the subsystem and whenever its boundary changes, not while nodes are dragged. A terminal can be dragged by its diamond, like a node, to anywhere in the view; where it is put is kept in the subsystem's `terminalPositions` and saved with the project, so it stays there on leaving and coming back, through undo and redo (each drag is one step, and undoing the first returns it to the automatic layout), and through save and open in both editions. A click on a diamond without dragging selects its relationship, as a click on its label does. When a relationship stops crossing the boundary (it is deleted, or a node is moved so both its ends are inside or outside), its saved position is no longer written. Copying nodes does not copy their subsystem, so a pasted relationship starts in the automatic layout; the entries name their edge in an `edgeId` field, so that once subsystems are copied with their contents the positions are renumbered with them.

Subsystem boxes and terminals follow the Nodes label control as node labels do. Compact shows a box's name and Open button, or a terminal's direction and outside node; expanded adds the detail line (a box's boundary count, a terminal's state, location and group); hidden leaves them out except while selected or pointed at. A hidden terminal keeps its diamond, which can still be pointed at, clicked and dragged. In a large view they join the pass that leaves out labels where they would overlap (`src/renderer/labelDeclutter.mjs`), boxes ranked with nodes and terminals after them, and count towards the number of labels at which that pass starts; nodes in other subsystems, which have no label on screen, no longer take room from those that do.

## Lifecycle

Every operation below is one undo step, is refused while results are shown (the model is locked then), and works the same in the desktop and the web edition. What each one touches is worked out by pure functions in `src/subsystems.mjs` (`subsystemContents`, `subsystemDeletion`, `subsystemLocations`, `subsystemMoveTargets`), which the canvas applies; their unit tests are in `tests/subsystems.test.mjs`.

- **The card.** Selecting a subsystem opens its card: its name, what it holds ("1 node · 1 subsystem inside · 2 nodes in all · 5 boundary ports · in Model"), its boundary crossings as the terminals inside name them, and the buttons Open subsystem, Dissolve subsystem and Delete subsystem. The same actions, with Rename subsystem, are on its right-click menu, and the Delete key deletes a selected subsystem.
- **Updates.** The card's Updates setting is "As each node says" (the default) or "Settle within the step": the Updates of every node in it, at any depth, are then worked out within the step, so a chain of them across its nodes settles in one pass, with "At most, sweeps of a ring" beside it. A node it settles shows "set by subsystem Name ›" on its Numerics tab, which opens the subsystem. For a component, the setting is the component's, the same in every instance, and inside a linked component it is changed where the component is edited. See [Rates and updates](proposals/ratesAndUpdates.md#across-nodes-and-over-a-subsystem).
- **Rename.** Type a new name in the card, or, while inside, click the subsystem's name in the breadcrumb and type it there (Enter keeps it, Escape leaves it). A name is trimmed and at most 120 characters; an empty one is refused.
- **Dissolve.** Dissolve subsystem puts the subsystem's own nodes and nested subsystems into its parent, as they are, and removes it. Node and relationship ids are unchanged, so plots, results, run configurations and tuning setups still find them. Nodes that were deleted while inside it are handed to the parent too, so undoing their deletion later does not put them back into a subsystem that is gone.
- **Delete.** Delete subsystem deletes the subsystem, every subsystem and node inside it at any depth, the relationships among them, and the relationships connecting them to the rest of the model, after a confirmation that counts each ("Delete “Plant”? This also deletes 2 nodes, 1 nested subsystem, 1 relationship inside it, 5 relationships connecting it to the rest of the model. Undo brings them back.").
- **Move in and out.** Right-click selected nodes for "Move into “Name”", one entry for each subsystem shown beside them, and, inside a subsystem, "Move to parent", which puts them a level up. A node's editor has a Subsystem field listing every place by path ("Model / Plant / Pump"), so a node can be moved to any level, nested ones included, in one step. Dragging nodes and dropping them on a subsystem's box moves them inside, where they were dropped, as one undo step with the drag. Relationships between moved and unmoved nodes stay as they are; those that now cross a boundary are drawn to the box outside and to a terminal inside.
- A subsystem being viewed that goes away (deleted, dissolved, or its creation undone) gives way to the nearest one still there, or the model.

Named and typed ports, exposed parameters, reusable definitions placed as several instances, and subsystems saved to their own files are a separate design, the subsystem components proposal; none of it is built yet.

Inside a subsystem, New relationship's list of ends and the relationship editor's From and To lists offer, after the nodes in view, every other node in the model under "Elsewhere in the model", named with where it is ("Heater · Model", "Sensor · Model / Controls"), so a relationship can be drawn out of a subsystem from inside it; it then ends at a terminal. While picking an end on the canvas, a terminal's diamond picks the node outside it.

## Components

Every subsystem is an instance of a component definition (`src/components.mjs`, all pure functions on project documents, so the canvas, files, the library and the tests share them). A definition, in the project's `subsystemDefinitions`, holds a sealed component document: a whole project (nodes, edges, shared parameters, edge groups, its own subsystems and definitions) with a `component` block giving its name, description and declared ports, whose ids are in its own space. A subsystem record that names a definition with `definitionId` is an instance of it. The instance's contents are kept in the project's flat graph as before, and every entity made from the definition carries `definitionKey`, its id in the definition's document; that is how expanding the definition again gives every entity the project id it had, and new ones the next free ids in document order, so the same document expands to the same ids everywhere. Subsystems nested inside an instance are records with `definitionKey` and no definition of their own in the project; their definitions live inside the outer document.

- **Opening older projects.** A project whose subsystems are plain opens with each top-level subsystem made an instance of a local definition of its own (`migrateLegacySubsystems`), whose document uses the entities' own ids, so every id and the flat graph the engine sees are unchanged. A unit test folds every shipped example into nested subsystems and checks exactly that. A new subsystem becomes an instance the same way.
- **Keeping instances in step.** The canvas edits the flat graph. After a change, the instance it was made in is written back to its definition and every other instance of it is expanded again (`syncDefinitions`); this runs when the view changes, a moment after editing stops (never while a field is being typed in), and before a save or a run, and the result is applied to the canvas entity by entity so the objects the undo history holds stay the ones on screen. Undo restores the edited instance, and the same step puts the others back. A relationship from outside to a part the definition no longer has is removed with it.
- **Place another instance** (the subsystem's card) places a second instance of the same definition beside the first, clear of everything drawn and brought into view, numbered as a component placed from a file or the library is ("Plant 2", then "Plant 3"; a name already numbered goes on from its number); the card and the breadcrumb then say "used 2 times". **Make this one separate** gives an instance a definition of its own (a copy), after which changes to it no longer reach the others.
- **Replace with its FMU…** (the card's Component section, and the box's right-click menu; [Ports at the top level](proposals/rootPorts.md), decision 10) puts an FMU in an instance's place: one exported from its component (export the component file opened as a project, with its ports, as an FMU), or any FMU whose inputs and outputs have the instance's port names. The dialog offers the FMUs of the library that match and **Choose an FMU file…**, then lists, row by row, what matches: each in port with the FMU input of its name and what it reads, each out port with the FMU output of its name and what reads it, each exposed parameter with the FMU parameter of its symbol (or name) and the value carried. Nothing is replaced while something would be lost, each said why: an in port with no FMU input of its name (or one that is an output or a parameter of the FMU), an out port with no FMU output of its name, a unit the FMU states that differs from the port's (an FMI 2.0 export by Konjugate states none, which is said), an in port set through an equation rather than from a state as it is (an FMU input reads a state), an in port read from outside or an out port set from outside, a connection to a state inside that is not a port, an edge group joining the instance to the outside, or an instance inside another component. What loses nothing is said too: an FMU input with no in port keeps the FMU's own start, an FMU output that is not a port is offered on the box, an exposed parameter with no FMU parameter of its name (or another unit) is not carried. **Replace** is one undoable change: the instance (its nodes, its relationships inside, its own parameters, and its definition when no other instance uses it) gives way to an FMU node of the same name at the same place, each relationship setting an in port becomes the FMU input of that name reading the same state, each reading an out port reads the FMU's output of that name, and each exposed parameter's value (or the shared parameter it follows) goes to the FMU's parameter. With the instance's last run kept (Close › Keep them to compare), the FMU node's run is compared with it as Compare with original compares an exported FMU: a component exported with its ports and replaced by its FMU runs to the same numbers, bit for bit with Euler. FMUs run on the desktop, so in the web edition the action says so and where to get the desktop app.
- **Ports.** A port is one state of the component offered outside, named by a key that never changes. The card lists declared ports and, for a local definition, the states something outside is connected to now (found from what is connected, not stored). Naming one, choosing its direction (in and out, in, out), or Keep as a port declares it; Make a state a port declares any state inside; a declared port can be removed. Inside, a terminal reaching a declared port says so, a declared port with nothing connected shows as an empty terminal, and the box lists its declared ports in its detail line. Saving a component to a file or the library declares every port it has, since a file has no outside to find them from.
- **Exposed parameters.** Expose a parameter (the card) offers the shared parameters used inside and the relationships' parameters and those of nodes' own equations (one of those is first made shared). Each instance then has its own copy of it: its own value, the component's default, or a shared parameter of the model it follows (every instance of a pump reading one ambient temperature). Instances store only what differs, as `parameterValues`. A shared parameter used inside and outside a subsystem becomes, when the subsystem becomes a component, an exposed parameter bound to the outside one, which leaves the numbers unchanged.
- **Symbols.** Shared parameter symbols must be unique in a project, and each instance has its own copy of every shared parameter its definition holds, so a copy that would repeat a symbol is given the first free one after it ("conductance2") and the instance's name after its own name; the definition keeps its own symbol and name.
- **Copy and paste.** Copying a selected subsystem copies its component document; pasting places it as an independent copy with a definition of its own, as pasting a node makes a new node. Copying nodes never carries keys, and a node that leaves an instance (moved out, or its instance dissolved) loses its keys, so it is never mistaken for an entity of another definition.
- **Results.** Where a state is listed out of context, a node is named by its subsystem's path when another node has the same name ("Pump 2 / Impeller"): CSV export (desktop and the command line, only for columns whose headers would otherwise repeat, so other exports are unchanged), and the state pickers of the twin and causal-inference mappings.
- **What the engine sees.** `executionProjectDocument` strips subsystems, definitions, component blocks and keys (`stripComponents`), so the engine is given the same flat graph as ever.

## Component files

**Save as component file…** (the subsystem's card and right-click menu) writes the instance's component as an ordinary `.kjt` project with a `component` block, every port declared, laid out around its own middle, with the project's ownership details; the status line says where it went, and the instance becomes linked to the file just written. Such a file opens as a project like any other and runs on its own, with nothing connected to its ports; a bar says it is a component, and saving it keeps its component block. Its ports are its [ports at the top level](#ports-at-the-top-level), drawn and edited there.

**Component from file…** (the Add menu, and the button at the top of the component library) chooses a `.kjt` and shows a review card first: the component's name and description, its ports with their units and directions, its exposed parameters with their defaults, and where it came from (file name and saved date). Place puts an instance in the view being looked at, linked to the file unless "Place as a copy" is ticked. A project with no component block offers its subsystems instead; the chosen one is placed as a copy (a linked file is one component). The desktop reads and writes through the main process (`componentOpen`, `componentUnlock`, `componentSave`, `componentRead`, `componentResolve`, `componentEditInWindow`); the web edition through its own `componentFiles` (the File System Access API where there is one, a picker and a download where not). An encrypted file asks for its password.

## Ports at the top level

A project can offer states outside at its top level, as a component's ports ([Ports at the top level](proposals/rootPorts.md)). They are the project's own `component` block, so a project with ports is a component, and a component file's ports are its ports at the top. **Add › Input port** and **Add › Output port** ask for a name and a unit and place a small node at the left or right edge of the view holding one Update state of that name, starting at 0, declared as the port; an output port's node opens with its equation ready to type. Any state can also be offered: **Offer outside** in a state's fields (opened from its line in the node's Equations tab), **Offer outside as a port** on a node's right-click menu (In, Out, In and out, or Not a port, for a node of one state), or **Make a state a port** in the Ports list, which makes it an in port when nothing reaches it and an out port when something does. A model that said no kinds says them once a port's node is added, its numbers unchanged.

Each port is drawn at the top level as a terminal, as a subsystem's inside view draws its own: in ports on the left marked "→ In", out ports on the right marked "Out →", ports both ways on the right marked "⇄ Both", with a dotted line to the node holding the port's state (or the box of the subsystem holding it). An in port nothing in the project reaches holds its start value when the project runs on its own, and its terminal says "nothing connected · stays at 20 °C", even with compact labels. Clicking a terminal selects its node and opens the Ports list on its row; a terminal can be dragged, and where it is put is kept in the block's `terminalPositions` (`{ portKey, position }` entries), one undo step each, written only when moved. Fit takes the terminals into the view.

The **Ports** button beside Parameters opens the Ports list: each port's name (blank for its node's and state's), direction and Remove, its node and state (a click selects the node), its symbol and unit, and whether anything reaches it, with the start of an unconnected in port editable in place; **＋ Input port**, **＋ Output port** and **Make a state a port** below. With no ports it says what a port is. Every change is one undo step. While results are open the list is locked and gives each port's value at the time shown; a run of a model with ports opens it once, so a component's run is read by its interface. An in port can carry a **test signal** for when the model runs on its own (stage 6): its row's **When run here** is "stays at its start", "a constant" (with its value) or "a schedule…", which opens the schedule dialog a shared parameter's schedule uses (a new one starting at the port's start, held from time zero), and its terminal then says "nothing connected · run here, set to 21 °C" or "follows its schedule". The host applies it only when this project is the one being run (the run, validation, a replay, the live twin, a fit; desktop and web), as a value-setting part on the port's state: never where the model is placed as a component, where outside drives the port, nor in its FMU, where the host drives its inputs. A signal is used on an in port, or one both ways, on an Update nothing in the model reaches; on any other it is kept and the row says why it is not used. A file carrying one says `rootPortSignals` in its `requires`, so a Konjugate that does not apply port signals refuses to run it by name rather than running it differently. Removing a port leaves its node; deleting a port's node takes the port off when the project is saved, and undoing the deletion brings it back. Removing the last port removes the block too, unless the project opened as a component (a component file keeps its block). A project without ports writes no block and is saved byte for byte as before; ports need no `requires`, since the engine never sees them.

A project with ports **is** a component, and the bar at the top of the canvas says its interface: "PID controller is a component: 2 in ports, 1 out port, 3 exposed parameters." (a component file opened as a project says the same, as does a project the moment its first port is declared). Its name is its file's, unless it opened as a component file with a name of its own. **Save** writes it with its block, so **Component from file…** in another project places it, linked, through the review card. Before saving, a change to its interface (a port removed, or its symbol, unit or direction changed; an exposed parameter removed or changed) is said on the bar in amber: "Saving changes its interface: 1 open project linked to this file (Heated room) will be asked about removing ‘measurement’." The projects named are the ones open in other windows that link the file, each window telling the desktop which component files it links; the desktop does not search the disk, and a project not open is asked when it next checks its link. A compatible change (a port renamed, one added) is taken in by every linked project when the file is saved, as for any component file. The bar's buttons, and the same two in the Ports list, use it elsewhere: **Save to my library** keeps the whole model in the library as a component (its model and block, laid out around its middle, without its ownership details or project settings), offered once it has ports, since a component without ports cannot be connected to; and **Place in another model…** (desktop) saves it first if it is new or changed, then lists the other open project windows and **A new window**: the one chosen comes to the front with the review card open, placing it linked to the file.

On the canvas a component instance with declared ports is a box with ports, as an FMU node is ([Ports at the top level](proposals/rootPorts.md), stage 5): its in ports are terminals on its box's left edge, saying "nothing connected · stays at 20 °C" or "connected", its out ports and ports both ways on its right. Dragging from an in port to a node's state (its label, a state row, or the node) or to another box's output terminal makes a one-way relationship from that state that sets the port's Update; dragging from an out port to a node's Update, or to an FMU's input, sets that Update or binds that input. A Rate, or an Update already set, is refused with why; each connection is one undoable step. Fit takes the boxes, and room for their terminals, into the view.

## My library

With one subsystem selected, **Save to my library** saves it as a component (a library entry of kind `component` holding its component document, the same document a file holds); the status line says how many ports and parameters it has. Placing it from the library goes through the same review card and is linked to the entry unless placed as a copy. Assemblies of loose nodes are saved as before when nodes are selected.

## Linked components

A component placed from a file or from My library stays linked to it (the definition's `link`), and the copy of it in the project (the definition's document) is what the project runs on, which is what lets it open and run when the file cannot be found and in the browser.

- **When links are checked.** When the project opens, when its window comes back to the front, and when any window saves a file a link names. A file link is looked for by its path relative to the project's folder first (written at every save, so a project and its components moved or cloned together keep working), then by its absolute path.
- **A compatible change** (the file's `sha256` differs, and its declared ports and exposed parameters, compared by key, are the same, renamed, added, or bound to another state of the same symbol and unit) is taken in at once as one undo step, and the status line says "Plant updated from Plant.kjt (saved 15 Nov)". A port now bound to another state takes the relationships from outside with it.
- **An interface change** (a port or exposed parameter removed, or its symbol, unit or direction changed) asks, in a bar naming what changed and what is connected to it in each instance: **Update and remove** takes the new version and removes those relationships and bindings, **Keep the old version** stays on the saved copy and shows it as behind its file, and **Detach** makes it a local copy.
- **A missing file**: the project runs on the saved copy, and the bar offers **Locate…** (choose the file; a different version is taken in as a change), **Keep using the saved copy** and **Detach**.
- **Cycles.** A component that contains, through its own links, the model it is placed in is refused with the chain named ("Outer.kjt cannot be placed here: it contains Plant.kjt, which is this model"), when placing and when a new version is taken in; nesting is limited to 16 deep.
- **Editing.** Inside a linked instance a bar says it is linked and how many times it is used, with **Edit component** and **Detach**. Edits made inside it on the canvas are put back (it is changed where it lives), and moving nodes in or out is refused with the reason. On the desktop, Edit component opens the file in a window of its own, which owns it with its own undo; when that window saves, every window linking the file takes the new version in. A library component is edited in place instead: Edit component makes it editable here, and **Save to my library** writes it back to the entry (every model linked to it follows) or **Discard changes** puts it back.
- **In the browser** a file link cannot be followed by path, so the bar says "Plant.kjt is linked to a file; the browser cannot check it for changes" and offers **Update from file…** (choose the file again) and **Detach**. Library links are followed as on the desktop.
- **Encrypted components.** Placing an encrypted component into a project that is not encrypted says that its contents will be kept unencrypted in the project, and so does saving such a project; it is not refused.

Hierarchy visibility is independent of deletion. Saving a project always includes every undeleted graph entity, including entities outside the active hierarchy view. Before validation or simulation, Electron removes subsystem metadata and sends the native engine the same flat node-and-edge graph that would exist without subsystems. The C++ validator therefore remains the source of truth and numerical behavior is unchanged.
