# FMI compatibility of Konjugate

This page is provided by Konjugate, not by the Modelica Association or the FMI Project. It says which FMI features [Konjugate](https://github.com/zenineasa/Konjugate) supports, with which tools its FMI import and export have been checked, how to repeat each check, and holds example FMUs exported by Konjugate with their reference results.

| | FMI 1.0 | FMI 2.0 | FMI 3.0 |
|---|---|---|---|
| Import (Co-Simulation) | no | yes | yes |
| Import (Model Exchange, Scheduled Execution) | no | no | no |
| Export (Co-Simulation) | no | yes | yes |
| Export (Model Exchange, Scheduled Execution) | no | no | no |
| Import of an FMU that carries only its C sources (built on import) | no | yes | yes |

FMI import and export are in the desktop app (macOS, Linux and Windows). An FMU comes into a model in one way: **Add › FMU…** (a file picked, or one already in your library) or a `.fmu` dropped on the canvas; Extensions does not install or list FMUs, and an `.fmu` picked or dropped there is answered with "FMUs are added to a model: use Add › FMU…". What an FMU is, and how its binary was made, is under About this FMU on its node's card; Settings › Providers lists the FMUs in your library and removes one no open model uses, nor can bring back with Undo; saving a project keeps the FMU its file already holds even when the library no longer has it. The web edition neither imports nor exports FMUs: its Add › FMU…, a `.fmu` dropped on its canvas and its Extensions say FMUs run in the desktop app. How import and export work is described in [Exporting a simulation as standalone code](../../docs/codeExport.md) (sections "Exporting as an FMU" and "Importing an FMU").

## Importing FMUs

Konjugate imports an FMU as a node of a model: the FMU is run in Co-Simulation, one `fmi2DoStep`/`fmi3DoStep` per substep of the node, its inputs and parameters bound to states or parameters of the model and its outputs setting states. It is initialized at the start of the run with its inputs there, and its outputs once initialized are the run's first sample, at t = 0, as FMPy reads them (before 2.1.1 the first sample was the node's own initial values); an FMU reading another FMU's output is initialized after it. An FMU that offers only Model Exchange is refused when installed, saying so, and so is an FMU with no Co-Simulation (one with Scheduled Execution only, say). An FMU added again is the library's copy only when it is the same file (the same SHA-256): a different build that kept its ID, as a newer third-party FMU may, is installed beside it under the next free version and the status line says so, so it never runs the old binary; its card says which version of the library it runs.

How these are checked. Each Reference FMU is installed and imported as the app does it: every input and parameter bound to a constant state holding the test case's value, every output bound to a state of its own; the model is run with one communication step per global step and each output compared with FMPy's co-simulation of the same FMU. The inputs, parameters, step sizes and stop times are in [cases.json](../../tests/engine/fixtures/referenceFmus/cases.json); FMPy's results are recorded in [fmpyReference.json](../../tests/engine/fixtures/referenceFmus/fmpyReference.json), written by [fmpyReference.py](../../tests/engine/fixtures/referenceFmus/fmpyReference.py) with FMPy 0.3.21. Stair asks to end the simulation at t = 9 s; Konjugate terminates it there and holds its output, as FMPy does. The Reference FMUs release zip is downloaded and checked against its SHA-256 (`b6b4a195…63b1e97`); it is not kept in this repository. The FMI 3.0 benchmark uses the four FMUs kept in [benchmarks/fmi/referenceFmus](../../benchmarks/fmi/referenceFmus) (SHA-256 of each checked) and FMPy 0.3.32's results recorded in its [reference.json](../../benchmarks/fmi/referenceFmus/reference.json).

To repeat them, from the repository root with the engine built (`npm run setup`, then `npm run build:engine`):

```sh
node tests/engine/fmiImportFidelity.mjs     # FMI 2.0: Konjugate's own FMU, then the six Reference FMUs, from t = 0
node tests/engine/fmi3ImportFidelity.mjs    # FMI 3.0: a hand-written FMI 3.0 FMU, Konjugate's own FMI 3.0 FMU, then the six Reference FMUs, from t = 0
node tests/engine/fmiStartValues.mjs        # the Reference FMUs' start values, left to the FMU and given in the file, against FMPy
node tests/engine/fmuSourceBuild.mjs        # every Co-Simulation Reference FMU built from its sources with this computer's C compiler
node tests/engine/fmuSourceImport.mjs       # the same FMUs, their binaries taken out, built on import and run against their shipped binaries
node tests/engine/pidControllerExample.mjs  # OpenModelica's PidController.fmu against FMPy, built from its sources too, and in a closed loop against Konjugate's own PI
node benchmarks/run.mjs --accuracy --only fmi/referenceFmus
```

`pidControllerExample.mjs` is one of Konjugate's release checks, and ran on four platforms in 2.1.1's (above). The other import checks above were run on Apple Silicon macOS; after 2.1.1 they became release checks too (`scripts/runReleaseChecks.mjs`), on Linux x86_64 and aarch64, macOS arm64 and Intel, and Windows. In 2.1.2's release checks they passed on Apple Silicon only. Elsewhere they compared Konjugate's run with FMPy's committed run of the Apple Silicon binaries, and the release's binaries for different platforms do not compute the same last bits: its `aarch64-darwin` binaries were compiled with fused multiply-add (Apple clang turns BouncingBall's Euler step `x += dt * dx` into one `fmadd`), its Linux and Windows binaries without, so BouncingBall's `h` at t = 0.06 is 0.9826363000000012 on the one and 0.9826363000000014 on the others, in FMPy as in Konjugate (a forward-Euler replay with and without fused multiply-add gives exactly these two values). The checks now compare Konjugate with FMPy running the same binary on the same computer (the committed FMPy run on Apple Silicon, FMPy run by the check everywhere else, and on an Intel Mac the build made there from the FMU's sources, run by both), so "bit for bit" in the table above means against FMPy on the same platform, not across platforms; this has been run on Apple Silicon and is not yet confirmed on the other platforms in a release. The Reference FMUs v0.0.42 carry no binary for Intel Macs (FMI 2.0: `aarch64-darwin`, `aarch64-linux`, `linux64`, `win64`, `win32`; FMI 3.0: `aarch64-darwin`, `aarch64-linux`, `x86_64-linux`, `x86_64-windows`, `x86-windows`, and WebAssembly, which Konjugate does not run); they carry their sources, so on an Intel Mac with a C compiler they are built on import (below). Konjugate looks for a binary under its FMI version's directory names and then under the other version's, and chooses the binary built for the computer it runs on; an FMU with none and no sources it can build is refused, naming the binaries it found.

### FMUs that carry only their sources

An FMU with no binary for this computer that carries its C sources is built on import, once the person says so (Add › FMU…, a drop on the canvas, or opening a project that keeps it, ask first, showing what will run): from the `<BuildConfiguration>` of an FMI 3.0 FMU or of an FMI 2.0.4 one's `sources/buildDescription.xml`, or, for an FMI 2.0 FMU, from its `<SourceFiles>`, with this computer's C compiler (Apple clang on macOS; `cc`, `gcc` or `clang` on Linux; MSVC's `cl.exe`, then `clang` or `gcc`, on Windows) and the FMI headers as published. The build is kept for that FMU on this computer and used until the FMU changes; Settings › Providers says the builds kept and clears them. An FMU with a binary of its own can be built from its sources on request and run in place of its binary (Build from its sources, Use its own binary, under About this FMU), and Save FMU with this computer's binary writes it out with the build added, for a computer that cannot build it. An FMU generated by OpenModelica 1.2x is built with OpenModelica's recipe (its definitions, pthreads and `libm`), chosen by its `generationTool` and the files in `sources/`, and with GCC or clang only, as OpenModelica's own toolchains: its generated C uses GNU C extensions (an empty initializer for an array of unknown size, `const size_t eqMap[] = {};`) that MSVC refuses (error C7757, as 2.1.2's release checks found on Windows), so on Windows it is built with MinGW-w64's `gcc` or LLVM's `clang` when one is installed, and otherwise refused, saying what to install; this Windows build is not yet confirmed in a release. `compilerOptions` are passed only when every flag is on a short allow-list; any other flag refuses the build, naming it. The compiler runs in a temporary folder holding a copy of `sources/`, with a five-minute limit. A language a build description names (`C99`, say) is compiled as GCC's and clang's GNU dialect of it (`-std=gnu99`), as the exporters' own CMake builds compile it: in 2.1.2 it was strict `-std=c99`, under which glibc's headers do not declare `strdup`, so on Linux every FMI 3.0 Reference FMU built on import kept its instance name and resource folder as a pointer cut to 32 bits and crashed the engine (SIGSEGV in `freeModelInstance`, or reading its resource folder), found in 2.1.2's release checks and reproduced and fixed in an arm64 Debian 12 container. How it works is in [docs/proposals/sourceFmuImport.md](../../docs/proposals/sourceFmuImport.md).

## Exporting FMUs

Konjugate exports a model as an FMI 2.0 or an FMI 3.0 Co-Simulation FMU (the export dialog's Format: "FMU (FMI 2.0 Co-Simulation)", the default, or "FMU (FMI 3.0 Co-Simulation)") with a compiled binary for the computer it is exported on. A node whose Updates are worked out once per step, and a relationship whose one equation sets a value, are exported as the engine runs them (the FMU is the engine's run bit for bit in FMPy, in both versions; checked by [kindsExportFidelity.mjs](../../tests/engine/kindsExportFidelity.mjs)). Inside `fmi2DoStep`/`fmi3DoStep` the model is stepped as the Konjugate engine steps it, with Euler node by node or, under Stiff, with Rodas4, Rodas5P or BDF, so the FMU gives the engine's numbers; both versions compile the same model code, so an FMI 3.0 FMU gives the FMI 2.0 one's numbers bit for bit. Every state is an output, every parameter a tunable parameter (a live parameter is an input; one that follows a stored schedule is computed inside the FMU), and getting, setting and serializing the FMU state (`fmi2GetFMUstate`/`fmi3GetFMUState` and their kin) are supported except under Stiff and for programs in the older program format.

An FMI 2.0 FMU says why it refuses a call (another model's GUID, a communication step that is not a whole number of its own, a state it cannot save) through the host's logger, in the `logStatusError` category, and states its fixed step in a vendor annotation, `<VendorAnnotations><Tool name="Konjugate"><CoSimulation fixedInternalStepSize="…"/></Tool></VendorAnnotations>`, which Konjugate's own import reads ([fmi2Reasons.mjs](../../tests/engine/fmi2Reasons.mjs)). Both versions start only under their own GUID or instantiationToken ([fmiIdentity.mjs](../../tests/engine/fmiIdentity.mjs)), and a fresh instance given a saved FMU state, then a parameter, steps exactly as the instance it was saved from ([fmiStateRestore.mjs](../../tests/engine/fmiStateRestore.mjs)); saving an FMI 2.0 state into a handle that already holds one updates it in place.

An FMI 3.0 FMU has the FMI 2.0 one's variables and value references as `<Float64>` variables, declares their units (`<UnitDefinitions>`, each unit by its name as written in the model), adds the independent variable `time` (after the other value references), and states `fixedInternalStepSize`, the step every communication step must be a whole number of. It has no Event Mode, no early return and no intermediate update (`hasEventMode`, `mightReturnEarlyFromDoStep`, `canReturnEarlyAfterIntermediateUpdate` and `providesIntermediateUpdate` are false): `fmi3DoStep` always takes the whole communication step, or refuses it with `fmi3Error` and says why through the logger, as it does any call it refuses.

It is one of Konjugate's release checks.

The FMI 3.0 export check ([fmi3ExportFidelity.mjs](../../tests/engine/fmi3ExportFidelity.mjs), `npm run test:fmi3ExportFidelity`) exports the three example models, the main model of the check above and that model under Rodas4, Rodas5P and BDF, both as FMI 2.0 and as FMI 3.0. FMPy validates each FMI 3.0 FMU and simulates both; every output at every communication point of the FMI 3.0 FMU must equal the FMI 2.0 FMU's bit for bit, and the Konjugate engine's run: bit for bit for the example models (and for ThermalEquilibrium with its `conductance` changed through `fmi3SetFloat64`), to within 1e-15 for the main model (its scheduled and algebraic states differ from the engine's in the last bit at a few points, the FMI 2.0 FMU's exactly as much), and under Rodas4, Rodas5P and BDF to within 1e-9 (at most 1.8e-12). Through FMPy's `FMU3Slave` an FMU state taken mid-run, serialized and deserialized gives back the outputs and `time` exactly, and the run continued from it repeats the original to the bit; a communication step of 0.15 s against an internal step of 0.1 s is refused with the reason in the log. It is one of Konjugate's release checks, beside the FMI 2.0 one.

Exported FMUs have not yet been checked on Windows with an FMI tool successfully. 2.1.2's release checks ran there and FMPy could not load any FMU exported on Windows ("Could not find module ... (or one of its dependencies)"): the export compiles with the C++ compiler on PATH, `c++`, which on GitHub's Windows runners is MinGW-w64's g++, not MSVC, and its DLL needed MinGW's runtime DLLs (`libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libwinpthread-1.dll`). Konjugate's own loader found them on PATH, so its own round trip passed, but Python's ctypes does not search PATH, nor would another tool on a computer without MinGW. After 2.1.2 an exported FMU's DLL carries that runtime itself (linked with `-static`; with MSVC, its static runtime, `/MT`), needing only Windows' own DLLs; this is not yet confirmed in a release. They have not been checked with tools other than FMPy.

What an importing tool should know about them:

- They hold a binary for macOS on Apple Silicon only (`binaries/darwin64/`, arm64, in the FMI 2.0 FMUs; `binaries/aarch64-darwin/` in the FMI 3.0 ones). Konjugate does not cross-compile and does not export source code FMUs; an FMU for another platform is made by exporting the same project on that platform, and single-platform FMUs of the same project can be combined with "Merge platform FMUs…" in the export dialog. FMI 2.0 names a binary's folder by system and bitness only, so merging an Apple Silicon and an Intel export gives one universal binary in `binaries/darwin64/`, each slice the export's own; an FMI 2.0 export on ARM Linux or Windows writes its binary under the FMI 3.0 platform tuple (`binaries/aarch64-linux/`, `aarch64-windows/`), since `linux64` and `win64` mean x86-64 ([fmuMerge.test.mjs](../../tests/fmuMerge.test.mjs)).
- The communication step must be a whole multiple of the FMU's internal step (0.1 s, 0.01 s and 0.005 s); any other step is refused with `fmi2Error` (`fmi3Error`). The `_ref.opt` step sizes are. An FMI 3.0 FMU states its internal step as `fixedInternalStepSize`.
- `modelDescription.xml` declares the experiment its `_ref.opt` gives as its `<DefaultExperiment>` (start time, stop time and step); the `_ref.opt` files give it as well. The FMI 2.0 FMUs declare no units; the FMI 3.0 ones do.
- The examples are exported with the Konjugate source after 2.0.2: Konjugate 2.0.2 itself gives two parameters with the same symbol the same name (in SpringMassDamper, `mass` twice), which `validate_fmu` reports.

### Regenerating and checking the examples

```sh
npm run generate:fmi-examples    # builds the engine, exports the FMI 2.0 and FMI 3.0 FMUs and writes their files (scripts/generateFmiExamples.mjs)
npm test                         # includes tests/fmiExamples.test.mjs (no compiler or FMI tool needed)
npm run test:fmiExamples         # builds the engine, then tests/engine/fmiExamples.mjs (needs a C++ compiler and FMPy)
```

The examples are defined in [scripts/fmiExamples.mjs](../../scripts/fmiExamples.mjs). `tests/fmiExamples.test.mjs` checks that each folder has the files above and that they follow the FMI tools page's rules, and that each FMU's `modelDescription.xml` is the one the exporter writes today; its guid (FMI 3.0: its instantiationToken) is a hash of the generated C++, so a change to code generation that would change an example fails until the examples are regenerated. `tests/engine/fmiExamples.mjs`, one of the release checks (`npm run test:release`), runs the engine again for each reference result, exports each FMU again, and validates and simulates the committed and the fresh FMU with FMPy against the reference result. When either fails after an intended change to the exporter or the engine's numbers, regenerate the examples and commit the four files of each folder.

**Publishing.** This page is published with the web edition, at [web.konjugate.com/fmi/](https://web.konjugate.com/fmi/), with each release: `.github/workflows/webEdition.yml` renders it with `node scripts/fmiPage.mjs <directory>` ([fmiPage.mjs](../../scripts/fmiPage.mjs)) into `fmi/` beside the built app, with each example's four files to download; links to the rest of the repository become links to it on GitHub, and a link to a file that is not there stops the build. `tests/fmiPage.test.mjs` (in `npm test`) builds it and checks its links.

## Not supported

- Event Mode, early return and intermediate update in an exported FMI 3.0 FMU: `fmi3DoStep` always takes the whole communication step.
- FMI 3.0 clocks, arrays and variable types other than Float64 in an exported FMU: every exported variable is a scalar Float64.
- Model Exchange, for import and export: Konjugate runs an imported FMU in Co-Simulation and exports Co-Simulation FMUs only.
- Scheduled Execution (FMI 3.0), for import and export.
- FMI 1.0, for import and export.
- Exporting source code FMUs: an export holds a compiled binary for one platform. (Importing an FMU that carries its C sources is supported, above.)
- Building on import an FMU whose sources describe Model Exchange only, that needs a `<Library>`, or, generated by OpenModelica, that needs SUNDIALS (CVODE); or with a compiler flag outside the allow-list: each is refused, saying which.
- Exporting a model that has an FMU node: the export says so.
- Exporting a model under a method other than Euler node by node and Stiff (Rodas4, Rodas5P, BDF), or with a program written in Python: refused at export, saying why.
- On import, String, Binary and Clock variables and arrays are not bound to the model: the FMU keeps its own values for them.
- Layered standards.
